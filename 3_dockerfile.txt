Практика 3. Первый Dockerfile.

До сих пор мы скачивали готовые образы. Теперь соберём свой: напишем
файл с инструкциями и получим из него образ. Файл вырастет у нас
на глазах — от трёх строк до правильного.

=========================================================================
ЧТО МЫ СДЕЛАЕМ
=========================================================================

Три строки в Dockerfile → рабочий каталог → приложение с зависимостями
и портом → контейнер не от root → две стадии сборки.

=========================================================================
ЧТО ПОНАДОБИТСЯ
=========================================================================

Машина admin со стенда практики 1 и работающий Docker. Каталог
~/docker-lab — создадим его на первом шаге. Около 1,5 ГБ места и доступ
в интернет: базовый образ весит 118 МБ, зависимости — ещё 13 МБ. Готовые
файлы курса лежат в files/03_dockerfile и понадобятся, только если
что-то не набрали руками.

#########################################################################
ЧАСТЬ 1. СОБИРАЕМ ОБРАЗ ПОСТЕПЕННО
#########################################################################

=========================================================================
ШАГ 1. САМЫЙ КОРОТКИЙ DOCKERFILE: ТРИ СТРОКИ
=========================================================================

Dockerfile — текстовый файл с инструкциями. Docker читает его сверху
вниз и на каждую инструкцию строит слой образа.

  mkdir -p ~/docker-lab/03_dockerfile/01_hello
  cd ~/docker-lab/03_dockerfile/01_hello
  vi app.py

В app.py одна строка:

  print("Привет из контейнера!")

Файл сборки называется всегда одинаково — Dockerfile, без расширения:

  vi Dockerfile

  FROM python:3.13-slim
  COPY app.py app.py
  CMD ["python", "app.py"]

FROM — базовый образ: чужая файловая система, в которой уже есть Python.
Тег 3.13-slim закреплён по версии: slim — тот же Python без компилятора
и утилит, которые приложению не нужны (шаг 8). COPY берёт файл
из каталога сборки и кладёт в образ под тем же именем. CMD — что
запускать при старте; список в квадратных скобках — exec-форма.

Собираем и запускаем. Точка в конце — каталог сборки: читать файлы
Docker имеет право только из него. Ключ -t задаёт имя и тег hello:1,
флаг --rm удаляет контейнер после завершения.

  docker build -t hello:1 .
  docker run --rm hello:1
  Привет из контейнера!
  docker images hello
  hello   1   7e2bfade15e6   5 seconds ago   118MB

Все 118 МБ — это базовый образ: наш файл добавил меньше сотни байт.

ЧТО ПРОИЗОШЛО ПО ШАГАМ

  1. docker build прочитал Dockerfile и каталог сборки;
  2. взял базовый образ python:3.13-slim, добавил слой с app.py
     и собрал из слоёв образ hello:1;
  3. docker run создал контейнер и выполнил CMD — программа напечатала
     строку и завершилась.

  ПОЧЕМУ ОБРАЗ, А НЕ ПРОСТО СКРИПТ

  Файл app.py работает и на машине. Но тогда «работает у меня»
  и «работает у коллеги» — разное: нужны та же версия Python и те же
  библиотеки. В образе программа уезжает со своим Python.

=========================================================================
ШАГ 2. ДОБАВЛЯЕМ WORKDIR: ОДНА СТРОКА — И СТАНОВИТСЯ ЛУЧШЕ
=========================================================================

В прошлом шаге файл лёг в корень файловой системы: любой созданный
приложением файл окажется там же, и разбираться, где чьи, тяжело.

  cd ~/docker-lab/03_dockerfile
  cp -r 01_hello 02_workdir && cd 02_workdir

Файл app.py не меняется, а Dockerfile становится таким:

  FROM python:3.13-slim
  WORKDIR /app
  COPY app.py .
  CMD ["python", "app.py"]

WORKDIR /app задаёт рабочий каталог для всех инструкций ниже и для
запуска: поэтому COPY app.py . кладёт файл в /app. Каталог создаётся
сам, отдельный RUN mkdir не нужен.

  docker build -t hello:2 .
  docker run --rm hello:2
  Привет из контейнера!

Посмотрим, где оказался файл. Слова после имени образа заменяют CMD:

  docker run --rm hello:2 ls -la
  drwxr-xr-x 1 root root 4096 Sep 28 08:52 .
  drwxr-xr-x 1 root root 4096 Sep 28 08:52 ..
  -rwxr-xr-x 1 root root   49 Sep 28 07:28 app.py

Мы в каталоге /app — это первая строка списка, «.». Даты у вас будут
свои, а первый столбец запомним: root. В шаге 4 мы это исправим.

ЧТО МЫ ПОЛУЧИЛИ: файл стал длиннее на одну строку, а образ — понятнее:
у приложения есть свой каталог, видимый тому, кто зайдёт внутрь.

=========================================================================
ШАГ 3. НАСТОЯЩЕЕ ПРИЛОЖЕНИЕ: ЗАВИСИМОСТИ И ПОРТ
=========================================================================

Печатать строку и завершаться — не то, ради чего ставят Docker.

  cd ~/docker-lab/03_dockerfile
  cp -r 02_workdir 03_web && cd 03_web

В app.py вместо одной строки теперь:

  from flask import Flask

  app = Flask(__name__)


  @app.route("/")
  def index():
      return "Привет из контейнера!\n"


  @app.route("/health")
  def health():
      return {"status": "ok"}


  if __name__ == "__main__":
      app.run(host="0.0.0.0", port=8000)

Рядом кладём requirements.txt — список библиотек, одна строка:

  flask

Dockerfile вырастает до семи строк:

  FROM python:3.13-slim
  WORKDIR /app
  COPY requirements.txt .
  RUN pip install --no-cache-dir -r requirements.txt
  COPY app.py .
  EXPOSE 8000
  CMD ["python", "app.py"]

RUN — команда, которая выполняется во время сборки: здесь pip ставит
Flask и библиотеки, от которых он зависит. Ключ --no-cache-dir запрещает
pip складывать скачанные архивы в образ. EXPOSE 8000 — «приложение
слушает порт 8000»: это документация, порт наружу открывает не EXPOSE,
а флаг -p при запуске (практика 5): без него curl ответит «Failed
to connect». CMD записан в exec-форме не для красоты: в shell-форме
сигнал остановки достаётся промежуточной оболочке, и docker stop
убивает контейнер по таймауту.

ПОРЯДОК СТРОК ЗДЕСЬ НЕ СЛУЧАЕН. Список зависимостей копируется
до pip install, а код — после: Docker считает кэш слоя по инструкции
и всему, что выше. Пока requirements.txt не менялся, слой с установкой
берётся готовым, сколько бы раз мы ни правили app.py.

Собираем. Первая сборка идёт дольше остальных: pip скачивает пакеты.

  docker build -t hello:3 .
  #8 [4/5] RUN pip install --no-cache-dir -r requirements.txt
  #8 DONE 11.9s

В скобках виден номер шага: Docker прошёл пять инструкций, и каждая
стала слоем. Установка заняла почти двенадцать секунд.

  ПЕРВАЯ СБОРКА ДОЛГАЯ, ВТОРАЯ МГНОВЕННАЯ

  Пакеты скачиваются из интернета ровно один раз: дальше они лежат
  в кэше сборки на машине. Повторная сборка без изменений занимает
  доли секунды, и все её шаги помечены словом CACHED.

Запускаем приложение. Слева порт машины, справа порт контейнера,
ключ -d оставляет контейнер работать в фоне:

  docker run -d --name p3-web -p 8000:8000 hello:3
  curl -s http://127.0.0.1:8000/
  Привет из контейнера!
  curl -s http://127.0.0.1:8000/health
  {"status":"ok"}

  docker images hello
  hello   3   c386972cf896   26 seconds ago   131MB

Плюс 13 МБ — это Flask со всеми зависимостями.

=========================================================================
ШАГ 4. ХОРОШО: НЕ ОТ ROOT И БЕЗ ЛИШНЕГО
=========================================================================

  docker run --rm hello:3 id
  uid=0(root) gid=0(root) groups=0(root)

Ноль — это root. Внутри контейнера он ограничен файловой системой
образа, но ядро у контейнера общее с машиной: root в контейнере может
писать куда угодно внутри образа и в примонтированные каталоги.

  cd ~/docker-lab/03_dockerfile
  cp -r 03_web 04_user && cd 04_user

Добавим в Dockerfile пользователя и переключимся на него:

  FROM python:3.13-slim
  WORKDIR /app
  COPY requirements.txt .
  RUN pip install --no-cache-dir -r requirements.txt
  COPY app.py .
  EXPOSE 8000
  RUN useradd --create-home --uid 1000 app
  USER app
  CMD ["python", "app.py"]

RUN useradd создаёт пользователя app с uid 1000 и домашним каталогом,
а USER app говорит: всё, что ниже, и запуск контейнера выполняются
от него. Создаётся пользователь до USER — команде useradd нужен root.

Заодно положим рядом .dockerignore — три строки:

  __pycache__
  *.pyc
  .env

Он перечисляет то, что не должно попадать в контекст сборки, а значит,
и в образ: кэш Python и файл с секретами. Синтаксис тот же, что
у .gitignore. Пока мы копируем файлы по именам, лишнее и так не уедет,
но COPY . . рано или поздно появится и здесь.

  docker build -t hello:4 .
  docker run --rm hello:4 id
  uid=1000(app) gid=1000(app) groups=1000(app)
  docker run --rm hello:4 whoami
  app

Размер не изменился: пользователь занимает девять килобайт.

=========================================================================
ШАГ 5. МНОГОЭТАПНАЯ СБОРКА: ДВЕ СТАДИИ
=========================================================================

В шаге 3 зависимости ставились прямо в тот образ, который мы запускаем.
А если приложению нужен компилятор? Он нужен только на время сборки,
а в готовом образе останется навсегда.

  cd ~/docker-lab/03_dockerfile
  cp -r 04_user 05_multistage && cd 05_multistage

  FROM python:3.13-slim AS builder
  WORKDIR /app
  COPY requirements.txt .
  RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

  FROM python:3.13-slim
  WORKDIR /app
  COPY --from=builder /install /usr/local
  COPY app.py .
  EXPOSE 8000
  RUN useradd --create-home --uid 1000 app
  USER app
  CMD ["python", "app.py"]

В файле теперь два FROM — две стадии. Первая, AS builder, ставит
зависимости в отдельный каталог /install: ключ --prefix говорит pip
складывать всё туда. Имя builder нужно, чтобы на стадию сослаться.
Вторая стадия начинается заново, с чистого python:3.13-slim: из первой
в неё попадает только то, что названо в COPY --from=builder.

  docker build -t hello:5 .
  #8 [builder 4/4] RUN pip install --no-cache-dir --prefix=/install
  -r requirements.txt
  #9 [stage-1 3/5] COPY --from=builder /install /usr/local

В скобках видно, к какой стадии относится шаг. Сравниваем размеры:

  docker images hello
  hello   5   5ead821135a4   2 seconds ago    123MB
  hello   4   d8479db47388   19 seconds ago   131MB
  hello   3   c386972cf896   26 seconds ago   131MB

ЧЕСТНО О ВЫИГРЫШЕ: ВОСЕМЬ МЕГАБАЙТ

Разница — восемь мегабайт, около шести процентов: компилятора у нас
не было, и в первой стадии остался только байт-код, который pip
скомпилировал для себя (12 МБ против 6,7 МБ в готовом образе).
Поставьте на место pip компилятор gcc или Node.js для сборки
фронтенда — и разница станет в сотни мегабайт.

  ЧЕГО НЕ ДЕЛАТЬ

  Не тащите в образ лишнее «на всякий случай»: компилятор, git, curl,
  vim. Всё, что попало в образ, уезжает на каждую машину с контейнером
  и лежит в реестре рядом с каждой версией, а каждая лишняя программа —
  это ещё и лишние уязвимости (практика 10).

=========================================================================
ШАГ 6. СЛОИ И КЭШ: ПОЧЕМУ ПОРЯДОК СТРОК ВАЖЕН
=========================================================================

Проверим на опыте то, о чём говорили в шаге 3. Ключ --progress=plain
печатает шаги сборки построчно. Изменим код и пересоберём:

  cd ~/docker-lab/03_dockerfile/03_web
  echo '# правка для проверки кэша' >> app.py
  docker build --progress=plain -t hello:3 .
  #8 [4/5] RUN pip install --no-cache-dir -r requirements.txt
  #8 CACHED
  #9 [5/5] COPY app.py .
  #9 DONE 0.1s

Установка осталась в кэше: requirements.txt не менялся, пересобрался
только слой с кодом. А теперь переставим строки: пусть COPY app.py .
идёт выше установки зависимостей. Скопируем каталог в /tmp/p3-bad,
поменяем порядок и соберём дважды — как есть и после правки кода:

  cd /tmp/p3-bad && docker build --progress=plain -t hello:3-bad .
  #9 [5/5] RUN pip install --no-cache-dir -r requirements.txt
  #9 DONE 13.1s
  echo '# правка для проверки кэша' >> app.py
  docker build --progress=plain -t hello:3-bad .
  #7 [3/5] COPY app.py .
  #7 DONE 0.1s
  #9 [5/5] RUN pip install --no-cache-dir -r requirements.txt
  #9 DONE 11.4s

Одиннадцать секунд вместо мгновения, хотя requirements.txt не менялся:
изменился слой выше установки, а значит, кэш всех слоёв ниже считается
недействительным. Отсюда правило:

  СВЕРХУ — ТО, ЧТО МЕНЯЕТСЯ РЕДКО. СНИЗУ — ТО, ЧТО МЕНЯЕТСЯ ЧАСТО.

  COPY requirements.txt .    ← меняется раз в месяц
  RUN pip install -r …       ← поэтому берётся из кэша
  COPY app.py .              ← меняется каждый день

Убираем за собой:

  rm -rf /tmp/p3-bad && docker rmi hello:3-bad
  cd ~/docker-lab/03_dockerfile/03_web
  sed -i '/правка для проверки кэша/d' app.py

  СЛОИ НЕ УМЕНЬШАЮТСЯ ЗАДНИМ ЧИСЛОМ

  Соблазнительно поставить что-то нужное на время сборки и удалить
  в конце: RUN apt-get install -y build-essential, а ниже
  RUN apt-get remove -y build-essential. Образ меньше не станет: вторая
  инструкция лишь записывает в свой слой пометку «этого файла здесь
  больше нет», а слой с пакетом остаётся ниже и весит столько же.

ЧАСТЬ 2. ПРОДОЛЖЕНИЕ

=========================================================================
7. ENV И ARG: ЗНАЧЕНИЯ НА ВРЕМЯ СБОРКИ И ПОСЛЕ НЕЁ
=========================================================================

ARG — переменная сборки: существует, пока идёт docker build, и в готовый
образ не попадает. ENV остаётся в образе и видна процессу внутри
контейнера.

  mkdir -p /tmp/p3-arg && cd /tmp/p3-arg
  vi Dockerfile

  FROM alpine:3.24
  ARG APP_VERSION=1.0
  ENV APP_VERSION="${APP_VERSION}"
  CMD ["sh", "-c", "echo version=$APP_VERSION"]

  docker build --build-arg APP_VERSION=2.0 -t p3-arg .
  docker run --rm p3-arg
  version=2.0

Без ключа --build-arg соберётся версия по умолчанию, 1.0. ENV остался
в образе, а ARG виден в истории сборки:

  docker image inspect p3-arg --format '{{json .Config.Env}}'
  ["PATH=/usr/local/sbin:…","APP_VERSION=2.0"]
  docker history --no-trunc p3-arg --format '{{.CreatedBy}}'
  ENV APP_VERSION=2.0
  ARG APP_VERSION=2.0

Отсюда правило: ни ARG, ни ENV не годятся для паролей (практика 9).
Убираем за собой: cd .. && rm -rf /tmp/p3-arg && docker rmi p3-arg

=========================================================================
8. ГДЕ ВЗЯТЬ ОБРАЗ И ПОЧЕМУ ТЕГ ВАЖЕН
=========================================================================

  * Тег python:3.13-slim закреплён: образ весит 118 МБ и не подменится.
  * python:3.13 — тот же Python, но с компилятором и утилитами сборки:
    1,11 ГБ, в девять раз больше.
  * python:latest — так нельзя. Слово latest означает не «последняя
    версия», а «тег по умолчанию»: завтра под ним окажется другой
    Python. Если тега нет вовсе, Docker молча подставит latest.

Так же и с библиотеками: строка flask означает «какая-нибудь версия
Flask». В рабочем проекте версию закрепляют: flask==3.1.3.

=========================================================================
ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
=========================================================================

ПРОБЛЕМА: сборка не находит Dockerfile

  ERROR: failed to build: failed to solve: failed to read dockerfile:
  open Dockerfile: no such file or directory

Файл должен называться точно Dockerfile, без расширения, и лежать
в каталоге, который передан контекстом (pwd). Назван иначе — ключ -f.

ПРОБЛЕМА: COPY не находит файл

  ERROR: failed to build: failed to solve: failed to compute cache key:
  failed to calculate checksum of ref …: "/nosuchfile.txt": not found

Файла нет в каталоге контекста либо он исключён файлом .dockerignore.

ПРОБЛЕМА: команда не найдена, код возврата 127

  docker: Error response from daemon: failed to create task for
  container: … exec: "nosuchcommand": executable file not found in $PATH

Слова после имени образа заменяют CMD (шаг 2). Команду оболочки
вызывайте явно: docker run --rm hello:4 /bin/sh -c 'echo проверка'.

ПРОБЛЕМА: контейнер сразу завершился

  p3-once  hello:1  Exited (0) 2 seconds ago

Код 0 означает, что программа отработала и завершилась сама: так и
должно быть у hello:1, она печатает строку и выходит. Контейнер живёт
ровно столько, сколько живёт его главный процесс. Что успел сказать
контейнер: docker logs p3-once.

ПРОБЛЕМА: порт уже занят

  docker: Error response from daemon: failed to set up container
  networking: driver failed programming external connectivity on
  endpoint p3-web2: Bind for 0.0.0.0:8000 failed: port is already
  allocated

Порт 8000 занят — скорее всего контейнером из шага 3: docker ps
--filter publish=8000, затем docker rm -f p3-web. Либо займите другой
порт: -p 8080:8000 — приложение останется на 8000 внутри контейнера.
