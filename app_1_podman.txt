Приложение 1. Podman: чем отличается от Docker.

ЭТО ПРИЛОЖЕНИЕ ЧИТАЮТ ПОСЛЕ ПРАКТИКИ 1 — тогда, когда встаёт вопрос
«а почему у нас не Docker». Команды Podman совпадают с командами
docker почти полностью; отличается устройство.

=========================================================================
ЧТО В ЭТОМ ПРИЛОЖЕНИИ
=========================================================================

  — чем Podman отличается по устройству и что в командах совпадает;
  — rootless по умолчанию и что из-за этого перестаёт работать;
  — когда переходить на Podman, а когда этого делать не стоит.

ВАЖНО: на стенде курса Podman не установлен. Практики 1–12 идут
на Docker, и команды ниже даны для проверки на отдельной машине.

#########################################################################
ЧАСТЬ 1. УСТРОЙСТВО, КОМАНДЫ, ROOTLESS
#########################################################################

=========================================================================
1. ЧЕМ PODMAN ОТЛИЧАЕТСЯ ОТ DOCKER
=========================================================================

Главное отличие одно, и из него следует всё остальное.

У Docker есть демон: постоянная служба dockerd, работающая от root.
Клиент docker ничего не делает сам — он передаёт запрос демону через
сокет. Контейнеры принадлежат демону: это его дочерние процессы.

У Podman демона нет. Команда podman сама создаёт контейнер и запускает
процесс: контейнер — дочерний процесс того пользователя, который
выполнил команду. Отсюда название подхода — daemonless.

  ps -eo pid,ppid,comm | grep -E 'podman|conmon|dockerd'
  podman info --format '{{.Host.Security.Rootless}}'

У Docker в списке виден dockerd — родитель всего. У Podman вместо
демона видно conmon: маленький процесс, который держит контейнер
и его журнал. Ответ true во второй команде означает rootless-режим.

ЧТО ИЗ ЭТОГО СЛЕДУЕТ

  * в модели Docker демон — самая привилегированная часть системы,
    и доступ к его сокету равен правам root (практика 12). У Podman
    такой службы нет вовсе;
  * перезапуск демона Docker останавливает контейнеры на машине,
    а у Podman перезапускать нечего;
  * но часть удобств Docker существует именно из-за демона: единый
    журнал docker events, автозапуск контейнеров после перезагрузки,
    общее хранилище образов. В Podman их собирают отдельно средствами
    systemd, и знать это должен каждый, кто выходит на дежурство.

=========================================================================
2. СОВМЕСТИМОСТЬ КОМАНД
=========================================================================

Интерфейс Podman сделан совместимым с Docker сознательно. Совпадает
почти всё, что касается повседневной работы:

  podman run -d --name web -p 8080:80 nginx:1.30-alpine
  podman ps -a
  podman exec -it web sh
  podman volume create data

Человек, прошедший практики 2–5 курса, работает с Podman сразу.
Чтобы не переучиваться вовсе, есть два пути: псевдоним
alias docker=podman либо пакет podman-docker, который ставит файл
/usr/bin/docker, вызывающий podman.

  ЧЕГО НЕ ДЕЛАТЬ: не ставьте podman-docker на машину, где уже есть
  Docker: оба пакета претендуют на одно имя команды, и вы получите
  не «удобно», а «непонятно, что выполнилось».

ЧЕМ КОМАНДЫ РАСХОДЯТСЯ — там, где у Docker участвует демон:

  * podman pod — группа контейнеров с общей сетью, которых в Docker
    нет: порты публикует под, а не контейнер;
  * podman play kube web.yaml — запуск манифеста Kubernetes без
    кластера. Поддержано подмножество API, а не весь API;
  * podman unshare — вход в пространство имён пользователя, чтобы
    посмотреть на файлы глазами контейнера;
  * podman machine — виртуальная машина с Linux на Windows и в macOS.

  ЧТО ДЕЛАТЬ С COMPOSE: Compose в Podman не встроен. Работают обёртка
  podman compose либо совместимый API:

  podman system service --time=0 \
      unix:///run/user/1000/podman/podman.sock
  export DOCKER_HOST=unix:///run/user/1000/podman/podman.sock
  docker compose up -d

  Второй путь удобен, но вы снова получили службу, слушающую сокет,
  и файл Compose заработает не целиком: проверьте его командой
  docker compose config.

=========================================================================
3. ROOTLESS: ЧТО РАБОТАЕТ, А ЧТО ПЕРЕСТАЁТ
=========================================================================

Rootless — это работа контейнеров без прав root; в Podman это режим
по умолчанию. Ядро позволяет обычному пользователю создать своё
пространство имён и внутри него быть root. Снаружи этот «root» —
обычный пользователь с диапазоном подчинённых идентификаторов:

  engineer:100000:65536
  podman unshare cat /proc/self/uid_map

uid 0 внутри — это uid 1000 снаружи, то есть root в контейнере — вы.

ЧТО ИЗ-ЗА ЭТОГО РАБОТАЕТ ИНАЧЕ

  * ПОРТЫ НИЖЕ 1024 занять без root нельзя: это ограничение ядра.
    Публикуйте на 8080 либо разрешите непривилегированные порты
    параметром ядра net.ipv4.ip_unprivileged_port_start;
  * СЕТЬ: rootless-контейнеры не настраивают iptables, поэтому порты
    публикуются в пользовательском пространстве, а часть возможностей
    (например, --ip с конкретным адресом) недоступна;
  * ОГРАНИЧЕНИЯ --memory и --cpus требуют cgroups v2: на старом ядре
    половина ограничений из практики 8 не применится без всякой ошибки;
  * ГДЕ ЛЕЖАТ ДАННЫЕ: не в /var/lib/docker, а в ~/.local/share/containers.
    Образы Docker и Podman не видят друг друга. Перенести образ можно
    файлом, формат у него общий:

  docker save app:1 -o app.tar
  podman load -i app.tar

ЧАСТЬ 2. КОГДА ПЕРЕХОДИТЬ
#########################################################################

=========================================================================
4. КОГДА ПЕРЕХОДИТЬ НА PODMAN, А КОГДА НЕ СТОИТ
=========================================================================

ПЕРЕХОД ОПРАВДАН, ЕСЛИ:

  * В КОМПАНИИ ЗАПРЕЩЁН ДЕМОН ОТ ROOT — причина организационная,
    а не техническая, и Podman готовый ответ: демона нет;
  * МАШИНА — РАБОЧАЯ СТАНЦИЯ РАЗРАБОТЧИКА: здесь группа docker
    (практика 1, шаг 4) означает права root у каждого разработчика;
  * ДИСТРИБУТИВ СЧИТАЕТ PODMAN ОСНОВНЫМ: Docker приходится ставить
    отдельно, а Podman уже есть;
  * НУЖНА ПОДГОТОВКА YAML ДЛЯ KUBERNETES БЕЗ КЛАСТЕРА.

ПЕРЕХОД НЕ ОПРАВДАН, ЕСЛИ:

  * ВСЁ ЗАВЯЗАНО НА ЭКОСИСТЕМУ DOCKER: Compose, расширения Docker
    Desktop, привычные инструменты;
  * НУЖЕН SWARM: в Podman его нет и не будет;
  * КОМАНДА НЕ ГОТОВА РАЗБИРАТЬСЯ: «контейнер не поднялся после
    перезагрузки» лечится не флагом, а службой systemd.

У Podman меньше привилегий и меньше поверхности атаки, у Docker шире
экосистема и меньше сюрпризов при переносе. Если в требованиях
написано «без root» — обсуждать нечего; если требований нет, переход
обычно приносит больше работы, чем пользы.

=========================================================================
ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
=========================================================================

ПРОБЛЕМА: podman: команда не найдена

  bash: podman: command not found

Пакет не установлен: проверьте which podman и поставьте пакет podman
из репозитория дистрибутива.

ПРОБЛЕМА: Error: short-name resolution enforced

  Error: short-name resolution enforced but cannot prompt without a TTY

Podman требует указывать реестр полностью, чтобы под коротким именем
нельзя было подсунуть чужой образ:

  podman pull docker.io/library/nginx:1.30-alpine

ПРОБЛЕМА: rootless не может занять порт 80

  Error: rootlessport cannot expose privileged port 80

Порты ниже 1024 в rootless-режиме недоступны — это ограничение ядра,
а не Podman. Публикуйте на порт выше 1024.
