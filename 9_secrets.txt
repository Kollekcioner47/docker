Практика 9. Секреты.

ЭТА ПРАКТИКА — ПРО ПАРОЛИ, КОТОРЫЕ ТЕРЯЮТ, НЕ КРАДЯ. Пароль редко
крадут: его чаще оставляют — в образе, в переменной окружения, в выводе
команды, в истории оболочки. Утечка выглядит не как взлом, а как
обычная работа: контейнер запускается, база принимает пароль, задача
закрыта.

В выводах команд значения заменены на <...>. У вас в терминале будет
видно значение целиком — в этом и смысл практики. Если показываете
занятие группе, помните: то, что на экране, — тоже утечка.


=========================================================================
ЧТО МЫ СДЕЛАЕМ
=========================================================================

Сначала посмотрим, где секрет видно:

  * переменная окружения: её печатает docker inspect, а изнутри
    контейнера она лежит в /proc/1/environ;
  * строка Dockerfile: значение ENV и ARG остаётся в образе,
    и его печатает docker history;
  * аргумент команды: его видно в docker ps --no-trunc и в ps;
  * файл из ключа --env-file: из вывода команд значение пропадает,
    а из окружения контейнера — нет.

Потом сделаем правильно: секреты Compose, суффикс _FILE у готовых
образов и секрет, который нужен только сборке.

=========================================================================
ШАГ 1. ПАРОЛЬ В ПЕРЕМЕННОЙ ОКРУЖЕНИЯ
=========================================================================

Первый способ — самый распространённый и самый плохой: секрет
передаётся контейнеру переменной окружения.

  PG_PASS='change_me_101'
  docker run -d --name p9-env -e DB_PASSWORD="${PG_PASS}" \
      alpine:3.24 sleep 300

Флаг -e передал процессу внутри контейнера переменную окружения,
а sleep 300 оставил контейнер живым, чтобы было что рассматривать.

Смотрим со стороны машины:

  docker inspect p9-env --format '{{json .Config.Env}}'

  "DB_PASSWORD=<пароль>"

Теперь изнутри контейнера:

  docker exec p9-env sh -c "tr '\0' '\n' < /proc/1/environ"

Команда читает окружение первого процесса контейнера: ядро хранит его
в файле /proc/1/environ, значения разделены нулевым байтом, поэтому tr
превращает их в обычные строки. DB_PASSWORD будет и здесь.

  ПОЧЕМУ ИМЕННО ТАК: это свойство Linux, а не недоработка Docker.
  Окружение процесса — обычные данные, и процесс того же пользователя
  читает их без спроса.

  # уберём за собой
  docker rm -f p9-env


=========================================================================
ШАГ 2. ПАРОЛЬ В ОБРАЗЕ: DOCKER HISTORY
=========================================================================

Второй способ — записать секрет прямо в Dockerfile. В каталоге практики
лежит учебный антипример с пометкой, что так делать нельзя:

  cd ~/docker-lab/files/09_secrets/plain-text
  cat Dockerfile.bad
  docker build -f Dockerfile.bad -t p9-leaky .

Docker сам предупредит о проблеме:

  SecretsUsedInArgOrEnv: Do not use ARG or ENV instructions for
  sensitive data (ENV "DB_PASSWORD")

Это не ошибка сборки: образ соберётся. Посмотрим на историю:

  docker history --no-trunc p9-leaky | grep DB_PASSWORD

  ENV DB_PASSWORD=<учебный пароль>

Значение ENV — часть метаданных образа, и оно печатается целиком.
С аргументом сборки то же самое:

  docker history --no-trunc p9-leaky | grep API_TOKEN

  ARG API_TOKEN=<учебный токен>
  RUN |1 API_TOKEN=<учебный токен> /bin/sh -c adduser -D -u 10001 app

Аргумент до контейнера не дошёл, но сборщик подставил его в команду
и записал команду целиком — значит, и он остался в образе. Маскировка
имени переменной не помогает: значение берут из метаданных образа.

  ПОЧЕМУ ИМЕННО ТАК: образ — это файл, который копируют и скачивают.
  Удалить из него ENV нельзя: можно только собрать новый образ,
  а у кого-то прежний уже лежит в кэше реестра. Второй слой
  переменную тоже не удаляет — слои неизменяемы (практика 3).


=========================================================================
ШАГ 3. ПАРОЛЬ В АРГУМЕНТАХ КОМАНДЫ
=========================================================================

Третий способ встречается в командах обслуживания баз: пароль передают
последним аргументом, как в mysql -p<пароль>.

  docker run -d --name p9-args alpine:3.24 \
      sh -c 'sleep 300; true' "${PG_PASS}"

Смотрим со стороны машины:

  docker ps --no-trunc --filter name=p9-args \
      --format '{{.Names}} | {{.Command}}'

  p9-args | "sh -c 'sleep 300; true' <пароль>"

Колонка COMMAND напечатана целиком, вместе со значением. Теперь
изнутри контейнера:

  docker exec p9-args ps -o pid,ppid,user,args

  PID  PPID  USER     COMMAND
    1     0  root     sh -c sleep 300; true <пароль>
    7     1  root     sleep 300

  ЗАЧЕМ ЭТО НУЖНО: аргументы процесса — часть его описания в ядре,
  и их видит каждый, у кого есть доступ к машине: ps на хосте,
  docker top, docker ps. Это шире, чем окружение, доступное только
  процессам того же пользователя.

  # уберём за собой
  docker rm -f p9-args


=========================================================================
ШАГ 4. --ENV-FILE: ЛУЧШЕ, НО НЕ РЕШЕНИЕ
=========================================================================

Из командной строки секрет убрать можно: Docker читает переменные
окружения из файла.

  cd ~/docker-lab
  echo "DB_PASSWORD=${PG_PASS}" > p9.env
  chmod 600 p9.env
  docker run -d --name p9-envfile --env-file p9.env \
      alpine:3.24 sleep 300

Теперь значения нет ни в выводе команд, ни в истории оболочки:

  docker ps --no-trunc --filter name=p9-envfile \
      --format '{{.Names}} | {{.Command}}'

  p9-envfile | "sleep 300"

А в контейнере оно есть — ровно там же, где было:

  docker inspect p9-envfile --format '{{json .Config.Env}}'

  "DB_PASSWORD=<пароль>"

  ПОЧЕМУ ИМЕННО ТАК: --env-file меняет не способ доставки секрета,
  а место, откуда Docker берёт значение. Переменной окружения процесса
  оно быть не перестаёт, а её видно в docker inspect и в /proc.

  # уберём за собой
  docker rm -f p9-envfile

=========================================================================
ШАГ 5. СЕКРЕТЫ COMPOSE
=========================================================================

В каталоге files/09_secrets лежат два файла Compose для одной и той же
задачи: plain-text — как делать нельзя, compose-secrets — как надо.
Начнём с антипримера.

  cd ~/docker-lab/files/09_secrets/plain-text
  cat docker-compose.yml
  docker compose config

В выводе видно всё, что Compose отправит в контейнер:

  POSTGRES_PASSWORD: <пароль>

Такой вывод прикладывают к задаче и отправляют в переписку. Запустим
и посмотрим на контейнер:

  docker compose up -d
  docker inspect p9-plain-db-1 --format '{{json .Config.Env}}'

В списке переменных — POSTGRES_PASSWORD со значением: то же, что
в шаге 1, только теперь пароль ещё и записан в файл рядом с проектом,
откуда уедет в git вместе с ним.

  docker compose down

Теперь правильный вариант: значение описано отдельным разделом
secrets, а сервис берёт его по имени. Compose монтирует значение
в контейнер файлом /run/secrets/db_password.

  cd ~/docker-lab/files/09_secrets/compose-secrets
  cat docker-compose.yml

Файла со значением в курсе нет — его создаёте вы:

  mkdir -p secrets
  printf '%s\n' 'change_me_pg_101' > secrets/db_password.txt
  chmod 600 secrets/db_password.txt

  ВАЖНО: этот файл не часть проекта. Он закрыт правами 600, не попадает
  в git и не копируется в образ: в курс входит только имя секрета.

Запускаем и смотрим:

  docker compose up -d
  docker compose ps

В выводе db в состоянии Up, app — Exited (0): сервис app прочитал
секрет, напечатал отпечаток и закончил работу. Смотрим журнал:

  docker compose logs app --no-log-prefix

  14
  c8411da6d27bd93bf8961f5545bd0039639de2e07f7acb080d332f2
  23975e148  /run/secrets/db_password

Первая строка — длина секрета в байтах, вторая — отпечаток (в выводе
он напечатан одной строкой). Значения в журнале нет: печатать секрет
в журнал нельзя, журнал живёт в системе сбора логов дольше пароля.

Теперь главная проверка — то же, что мы делали в шаге 1:

  docker inspect p9-compose-secrets-db-1 --format '{{json .Config.Env}}'

Вместо пароля в выводе стоит путь /run/secrets/db_password.

  # уберём за собой
  docker compose down


=========================================================================
ШАГ 6. СУФФИКС _FILE
=========================================================================

В compose-secrets пароль попал в контейнер файлом, а сервис db получил
переменную POSTGRES_PASSWORD_FILE — путь к этому файлу. Такую
переменную понимают официальные образы: postgres, mysql, redis
и другие. Точка входа образа читает файл до запуска базы и отдаёт
значение программе.

Сравните две строки:

  POSTGRES_PASSWORD: <пароль>                       # так нельзя
  POSTGRES_PASSWORD_FILE: /run/secrets/db_password  # так надо

Разницу видно в конфигурации, которую строит Compose:

  cd ~/docker-lab/files/09_secrets/compose-secrets
  docker compose config | grep PASSWORD

  POSTGRES_PASSWORD_FILE: /run/secrets/db_password

В конфигурации только путь. Если файла нет или он пуст, база
не запустится — разбор в конце практики, в разделе про ошибки.

  ВАЖНО: _FILE — это способ передать значение, а не хранилище
  секретов. Файл по-прежнему лежит на машине: закрывайте его правами
  и не копируйте в репозиторий.


=========================================================================
ШАГ 7. СЕКРЕТ, КОТОРЫЙ НУЖЕН ТОЛЬКО СБОРКЕ
=========================================================================

Токен для закрытого индекса пакетов нужен во время сборки и не нужен
никому потом. Для этого у BuildKit есть секреты сборки: файл
подключается к одной инструкции RUN и после неё не существует.

  cd ~/docker-lab/files/09_secrets/buildkit
  cat Dockerfile

Главное в нём — эта инструкция (сокращённо):

  RUN --mount=type=secret,id=app_token \
      TOKEN="$(cat /run/secrets/app_token)" && ...

Файл с токеном создаём сами:

  printf '%s\n' "tok_$(openssl rand -hex 6)" > /tmp/token.txt
  chmod 600 /tmp/token.txt
  docker build --secret id=app_token,src=/tmp/token.txt -t p9-buildkit .

Контейнер из этого образа печатает отпечаток токена:

  docker run --rm p9-buildkit

  d807190d5f23232b

Самого значения в образе нет. Убедимся:

  docker history --no-trunc p9-buildkit | grep "$(cat /tmp/token.txt)"

Команда не напечатает ничего — и это правильный ответ. Для этого
годами брали ARG, а он остаётся в записи о сборке, которую BuildKit
прикладывает к образу: смонтированный секрет не остаётся нигде.

  ВАЖНО: значение секрета не входит в ключ кэша сборки. Если поменять
  файл с токеном и пересобрать образ, слой RUN возьмётся из кэша:
  сборка пройдёт успешно, но отпечаток останется прежним. Нужен
  --no-cache.

  # уберём за собой
  rm -f /tmp/token.txt
  docker rmi p9-buildkit


=========================================================================
ШАГ 8. ЕСЛИ СЕКРЕТ УЖЕ УТЁК
=========================================================================

Секрет утёк, если он попал в образ, в репозиторий, в журнал или
в чужой вывод команды. Порядок действий такой:

  1. смените сам секрет: только это закрывает утечку;
  2. пересоберите образ без секрета и опубликуйте его заново;
  3. уберите значение из файлов: правка последним коммитом не поможет,
     значение останется в истории репозитория;
  4. посмотрите, куда секрет успел уехать: реестр, логи, бэкапы.

Проверить свой образ на утечку можно двумя командами:

  docker run --rm p9-leaky env
  docker history --no-trunc p9-leaky | grep -i password

  PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
  DB_PASSWORD=<учебный пароль>

Если значение видно — образ надо пересобирать.

  ЧЕГО НЕ ДЕЛАТЬ: не храните секрет рядом с кодом — ни в репозитории,
  ни в образе, ни в файле .env в том же каталоге. Ровно для этого
  и нужно хранилище секретов (Vault, Lockbox): значение выдают
  по запросу и умеют отозвать.

  # уберём за собой
  docker rmi p9-leaky
  rm -f ~/docker-lab/p9.env


=========================================================================
ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
=========================================================================

ПРОБЛЕМА: сборка антипримера предупреждает о секрете

  SecretsUsedInArgOrEnv: Do not use ARG or ENV instructions for
  sensitive data (ENV "DB_PASSWORD")

Это не поломка, а предупреждение: Docker распознал секрет по имени
переменной и сказал, что так делать нельзя. Образ соберётся, значение
в нём останется — смотрите docker history.

ПРОБЛЕМА: сборка с секретом падает

  cat: can't open '/run/secrets/app_token': No such file or directory
  ERROR: failed to build: failed to solve: process "/bin/sh -c ..."
  did not complete successfully: exit code: 1

Внутри сборки нет файла секрета — значит, его не передали ключом
--secret. Проверьте, что id совпадает:

  docker build --secret id=app_token,src=/tmp/token.txt -t p9-buildkit .

ПРОБЛЕМА: база не запускается и пишет

  Error: Database is uninitialized and superuser password is not specified.
  You must specify POSTGRES_PASSWORD to a non-empty value for the
  superuser.

Секрет до базы не доехал. Проверяйте по порядку:

  1. файл секрета создан и не пуст; проверьте его длину
     из каталога compose-secrets:
     wc -c < secrets/db_password.txt
  2. путь в POSTGRES_PASSWORD_FILE совпадает с именем секрета
     в разделе secrets: /run/secrets/db_password;
  3. в сервисе есть строка secrets со списком секретов — без неё файл
     в контейнер не попадёт.

ПРОБЛЕМА: service "app" is not running

Так отвечает docker compose exec, если контейнер уже завершился:
сервис app здесь разовый, он прочитал секрет и вышел. Нужен журнал:

  docker compose logs app --no-log-prefix

ПРОБЛЕМА: сборка не находит файл

  ERROR: failed to build: failed to solve: failed to read dockerfile:
  open Dockerfile.bad: no such file or directory

Команда выполняется не из того каталога:

  cd ~/docker-lab/files/09_secrets/plain-text
