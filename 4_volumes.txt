Практика 4. Данные: тома и монтирование.

ЭТА ПРАКТИКА ПРО ДАННЫЕ. Контейнер удаляется одной командой, и всё,
что он записал, исчезает вместе с ним. Сначала увидим это своими
глазами, потом научимся хранить данные так, чтобы они переживали
и удаление контейнера, и замену образа.


=========================================================================
ЧТО МЫ СДЕЛАЕМ
=========================================================================

Разберём три способа хранения данных — том, каталог машины и tmpfs, —
и поднимем MySQL, который переживёт удаление контейнера.

ЗАЧЕМ ЭТО НУЖНО: контейнер — это процесс, и всё, что он записывает,
живёт столько же, сколько процесс. Данные должны переживать
и перезапуск, и обновление образа, и замену контейнера.
«Удалил контейнер и потерял базу» — самая дорогая ошибка новичка.


=========================================================================
ЧТО ПОНАДОБИТСЯ
=========================================================================

  * машина admin (10.0.2.5) со стендом из практики 1; команды
    работают без sudo;
  * около 2 ГБ свободного места: образ MySQL — примерно гигабайт;
  * каталог files/04_volumes из курса.

  mkdir -p ~/docker-lab
  cp -r <курс>/files/04_volumes ~/docker-lab/
  cd ~/docker-lab/04_volumes

=========================================================================
ШАГ 1. ДАННЫЕ В КОНТЕЙНЕРЕ ЖИВУТ ДО ПЕРВОГО rm
=========================================================================

Создадим файл внутри контейнера и посмотрим, что от него останется:

  docker run --name p4-note alpine:3.24 \
      sh -c 'mkdir -p /data && echo saved > /data/note.txt && ls -l /data'

  total 4
  -rw-r--r--    1 root     root             6 ... note.txt

Теперь удалим контейнер и запустим новый — из того же образа:

  docker rm p4-note
  docker run --rm alpine:3.24 ls -l /data

  ls: /data: No such file or directory

Каталога /data в образе не было: он появился внутри контейнера
и вместе с контейнером исчез.

ПОЧЕМУ ИМЕННО ТАК: снизу — слои образа, они только для чтения
и общие для всех контейнеров этого образа; сверху — слой самого
контейнера, и он удаляется вместе с ним.


=========================================================================
ШАГ 2. ТОМ: ДАННЫЕ ПЕРЕЖИВАЮТ КОНТЕЙНЕР
=========================================================================

Том (volume) — каталог, которым управляет сам Docker:

  docker volume create p4-note-data
  docker volume ls

  DRIVER    VOLUME NAME
  local     p4-note-data

  docker volume inspect p4-note-data

  [
      {
          "CreatedAt": "2026-09-23T20:59:26Z",
          "Driver": "local",
          "Labels": null,
          "Mountpoint": "/var/lib/docker/volumes/p4-note-data/_data",
          "Name": "p4-note-data",
          "Options": null,
          "Scope": "local"
      }
  ]

Поле Mountpoint — каталог на машине, где лежат данные. Руками файлы
внутри него не удаляют: Docker ведёт учёт томов сам, а чистят их
командой docker volume rm.

Подключим том ключом -v: слева имя тома, справа путь в контейнере.

  docker run --name p4-note -v p4-note-data:/data alpine:3.24 \
      sh -c 'echo saved > /data/note.txt && ls -l /data'

  docker rm p4-note
  docker run --rm -v p4-note-data:/data alpine:3.24 cat /data/note.txt

  saved

Контейнер удалён, а файл на месте: он лежит в томе, а контейнер
только смотрит в него.

  ВАЖНО: том, которым пользуется хоть один контейнер, удалить
  нельзя — docker volume rm ответит volume is in use. Порядок всегда
  один: сначала docker rm, потом docker volume rm. Остановленного
  контейнера недостаточно: пока он существует, том занят.

  docker volume rm p4-note-data


=========================================================================
ШАГ 3. КАТАЛОГ С МАШИНЫ И TMPFS
=========================================================================

Второй способ — подключить в контейнер обычный каталог машины:

  mkdir -p data

  docker run --rm --mount type=bind,src="$PWD/data",dst=/data \
      alpine:3.24 sh -c 'echo hello > /data/from-container.txt'

  cat data/from-container.txt

  hello

Это не копия, а тот же каталог: файл из контейнера лежит на машине
обычным файлом. Записать ту же привязку можно и коротко, ключом -v
(имя:/путь) вместо --mount (type=bind,src=...,dst=...). Разница
видна на ошибке — каталога /tmp/p4-absent на машине нет:

  docker run --rm --mount type=bind,src=/tmp/p4-absent,dst=/data \
      alpine:3.24 ls -ld /data

  docker: Error response from daemon: invalid mount config for type
  "bind": bind source path does not exist: /tmp/p4-absent

А с ключом -v тот же запуск проходит: каталог создаётся сам, от root.

  docker run --rm -v /tmp/p4-absent:/data alpine:3.24 ls -ld /data

  drwxr-xr-x    2 root     root            40 ... /data

ИСПРАВЛЕНО: прежняя версия курса показывала это монтирование
на образе ubuntu:18.10. Такой образ всё ещё можно скачать, и в этом
как раз ловушка: ubuntu:18.10 — промежуточный выпуск, а не LTS,
поддержка прекращена в июле 2019 года. Образ работает и ничем
не выдаёт, что последние семь лет его никто не обновлял. Мы работаем
на alpine:3.24 — выпуске, который поддерживается.

ТРЕТИЙ СПОСОБ — TMPFS: каталог в оперативной памяти, на диск данные
не попадают вообще.

  docker run -d --name p4-tmpfs --tmpfs /tmp:size=16m \
      alpine:3.24 sleep 300

  docker exec p4-tmpfs sh -c 'echo temp > /tmp/cache.txt'
  docker exec p4-tmpfs cat /tmp/cache.txt

  temp

При остановке контейнера эти данные исчезают без следа:

  docker rm -f p4-tmpfs
  docker run --rm --tmpfs /tmp:size=16m alpine:3.24 ls -l /tmp/cache.txt

  ls: /tmp/cache.txt: No such file or directory

  ЗАЧЕМ ЭТО НУЖНО: чистить tmpfs не надо — он занимает оперативную
  память и освобождает её сам, но размер его ограничен.

ЧТО ВЫБИРАТЬ: для данных приложения и баз — том, за них отвечает
Docker; для кода и конфигурации — каталог машины, его удобно править
редактором; для временных файлов — tmpfs.


=========================================================================
ШАГ 4. MYSQL С ТОМОМ: БАЗА ПЕРЕЖИВАЕТ КОНТЕЙНЕР
=========================================================================

Сначала два файла, без которых MySQL не поднимется. Первый — схема
базы: образ выполнит init/01_schema.sql один раз, при первой
инициализации, когда каталог данных пуст. Наберём его целиком:

  cat > mysql/init/01_schema.sql <<'EOF'
  -- Начальная схема для практики 4.
  --
  -- Этот файл образ MySQL выполняет РОВНО ОДИН РАЗ: при первой
  -- инициализации, то есть когда каталог данных /var/lib/mysql пуст.
  -- Отсюда два вывода, которые проверяются в практике:
  --
  --   1. когда мы запускаем новый контейнер с тем же томом, каталог
  --      данных не пуст, и этот скрипт не выполняется: сервер просто
  --      подключается к существующим данным;
  --   2. чтобы применить правку в этом файле, нужен либо новый том,
  --      либо ручное выполнение SQL. Иначе изменения никто не заметит,
  --      и это выглядит как «файл поправил, а ничего не произошло».

  CREATE DATABASE IF NOT EXISTS notes;

  USE notes;

  CREATE TABLE IF NOT EXISTS notes (
      id         INT AUTO_INCREMENT PRIMARY KEY,
      body       VARCHAR(200) NOT NULL,
      created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
  );

  -- Текст записей здесь латиницей намеренно: клиент mysql в табличном
  -- выводе считает ширину колонки по числу байт, а кириллическая буква
  -- занимает два байта, поэтому строки в таблице разъезжаются. К данным
  -- это отношения не имеет, но читать мешает.
  INSERT INTO notes (body) VALUES ('row created by the init script');
  EOF

Второй файл — значения окружения: в курсе он лежит образцом,
files/04_volumes/.env.example. Наберём тот же текст в .env, а затем
заменим заготовки на свои значения командой nano .env:

  cat > .env <<'EOF'
  # Образец значений окружения для практики 4.
  #
  # Как пользоваться:
  #     cp .env.example .env
  # затем открыть .env и заменить заготовки на свои значения.
  #
  # Настоящего .env в репозитории курса нет и быть не должно. Дело
  # не в аккуратности: .env уезжает в git вместе с историей, а историю
  # потом не чистят. Пароль, попавший в коммит, остаётся в репозитории
  # навсегда — даже если файл после этого удалить.
  #
  # Значение ниже — заготовка, а не пароль. Рабочую строку здесь писать
  # нельзя: её скопируют в работу вместе с файлом.

  MYSQL_ROOT_PASSWORD=change_me_before_use
  MYSQL_DATABASE=notes
  MYSQL_USER=notes_app
  MYSQL_PASSWORD=change_me_too

  # ВАЖНО, И ЭТО ЧАЩАЯ ОШИБКА: MySQL читает эти переменные только при
  # ПЕРВОЙ инициализации каталога данных, то есть когда том пуст.
  # Если том уже создан, смена пароля в этом файле ничего не изменит:
  # учётные записи лежат в самом каталоге данных, а не в файле.
  # Как поступить в этом случае — раздел «Если что-то пошло не так».
  EOF

  ЗАЧЕМ ОТДЕЛЬНЫЙ ФАЙЛ: ключ --env-file читает значения из файла,
  и они не попадают в историю команд. Секретом это значение
  не делает: оно видно в docker inspect (практика 9).

Запускаем MySQL с томом и init-скриптом:

  docker run -d --name p4-mysql \
      --env-file .env \
      -p 127.0.0.1:3306:3306 \
      -v p4-mysql-data:/var/lib/mysql \
      -v "$PWD/mysql/init:/docker-entrypoint-initdb.d:ro" \
      mysql:8.4

Инициализация занимает полминуты. Признак готовности — имя первого
процесса в контейнере:

  docker exec p4-mysql cat /proc/1/comm

  bash     идёт инициализация, настоящего сервера ещё нет
  mysqld   сервер готов

Теперь заглянем в базу и добавим запись, которой нет ни в одном
файле курса (пароль клиент спросит сам):

  docker exec -it p4-mysql mysql -uroot -p

  USE notes;
  INSERT INTO notes (body) VALUES ('row added by hand');
  SELECT id, body FROM notes;
  exit

  +----+--------------------------------+
  | id | body                           |
  +----+--------------------------------+
  |  1 | row created by the init script |
  |  2 | row added by hand              |
  +----+--------------------------------+

Теперь главное — удалим контейнер целиком:

  docker rm -f p4-mysql
  docker volume ls --filter name=p4-mysql-data

  DRIVER    VOLUME NAME
  local     p4-mysql-data

Контейнера нет, том на месте. Запустим новый контейнер той же
командой (в оболочке достаточно стрелки вверх) и повторим в нём
запрос SELECT id, body FROM notes.

Обе строки на месте. Строку с идентификатором 2 не мог создать ни
образ, ни init-скрипт: она записана только в томе. И второе: скрипт
во второй раз НЕ выполнился — он идёт только на пустом каталоге.


=========================================================================
ШАГ 5. ПРАВА: ПОЧЕМУ ФАЙЛ ПРИНАДЛЕЖИТ ROOT
=========================================================================

У каждого файла в Linux есть владелец — числовой uid. Процесс
в контейнере по умолчанию работает от root, а это тот же нулевой
uid, что и на машине:

  docker run --rm -v /tmp/p4perm:/work alpine:3.24 \
      sh -c 'touch /work/root-created.txt && ls -lan /work'

  -rw-r--r--    1 0        0      0 ... root-created.txt

Нули в столбцах владельца — это root. А теперь запись в тот же
каталог от обычного пользователя:

  docker run --rm --user 1000:1000 \
      --mount type=bind,src=/tmp/p4perm,dst=/work \
      alpine:3.24 sh -c 'echo x > /work/from-user.txt'

  sh: can't create /work/from-user.txt: Permission denied

Причина не в Docker, а в правах: каталог принадлежит uid 0, а пишет
в него uid 1000. Сравниваются числа, а не имена: пользователя
с таким именем в образе может и не быть.

Запустить контейнер под своим uid — самое простое решение:

  docker run --rm --user "$(id -u):$(id -g)" \
      --mount type=bind,src="$PWD/data",dst=/data \
      alpine:3.24 sh -c 'id && echo ok > /data/file.txt'

Каталог тома отдают нужному владельцу заранее (chown 1000:1000 /data),
а пользователя для постоянной работы задают в образе — практика 10.

  ЧЕГО НЕ ДЕЛАТЬ: не решайте проблему прав через chmod 777 — это
  работает ровно до появления второго пользователя. И не запускайте
  контейнер с --privileged «чтобы не было проблем с правами»: флаг
  снимает почти всю изоляцию, это опасная привычка (практика 12).

=========================================================================
ШАГ 6. АНОНИМНЫЕ ТОМА: ПОЧЕМУ СПИСОК ТОМОВ РАСТЁТ
=========================================================================

Иногда том появляется там, где его не просили: образ объявляет его
сам. Так делает mysql:8.4 — вот его инструкция VOLUME:

  docker image inspect mysql:8.4 --format '{{json .Config.Volumes}}'

  {"/var/lib/mysql":{}}

Запустим контейнер без единого ключа -v:

  docker run -d --name p4-anon mysql:8.4
  docker inspect p4-anon --format '{{json .Mounts}}'

  [{"Type":"volume","Name":"e3acb88da837...",
    "Destination":"/var/lib/mysql", ...}]

Тома мы не просили, а он есть — с именем из шестнадцатеричных цифр.
Такой том называется анонимным. Контейнер сразу завершится (пароль
мы не задали), но том останется и после его удаления:

  docker rm -f p4-anon
  docker volume ls --filter dangling=true

  DRIVER    VOLUME NAME
  local     e3acb88da837...

  docker volume rm e3acb88da837...

Из-за таких томов список и растёт: имени у них нет, и никто
их не удаляет. А запуск с ключом --rm уносит анонимные тома вместе
с контейнером.

  ЧЕГО НЕ ДЕЛАТЬ: docker volume prune -a и docker system prune -a
  удаляют все тома, не подключённые к контейнеру, — включая
  именованные, с данными остановленной базы. Сначала посмотрите
  docker system df -v, потом удаляйте конкретное.


=========================================================================
ШАГ 7. КОПИЯ ТОМА: АРХИВ И ВОССТАНОВЛЕНИЕ
=========================================================================

Том — не резервная копия: он лежит на том же диске той же машины.
Копию снимают вспомогательным контейнером: том подключают только
на чтение, а архив кладут в каталог машины.

  mkdir -p backups
  docker rm -f p4-mysql

  docker run --rm \
      --mount type=volume,src=p4-mysql-data,dst=/data,readonly \
      --mount type=bind,src="$PWD/backups",dst=/backup \
      alpine:3.24 tar czf /backup/mysql-data.tar.gz -C /data .

  ls -lh backups/

readonly не даст испортить данные, если в команде окажется ошибка,
а архивируется содержимое каталога (tar -C /data .), а не сам каталог.

Проверим копию: удалим том и восстановим данные в новый.

  docker volume rm p4-mysql-data
  docker volume create p4-mysql-data

  docker run --rm \
      --mount type=volume,src=p4-mysql-data,dst=/data \
      --mount type=bind,src="$PWD/backups",dst=/backup \
      alpine:3.24 tar xzf /backup/mysql-data.tar.gz -C /data

Осталось поднять контейнер командой из шага 4 и убедиться, что обе
строки на месте: копию проверяют восстановлением.

  ПОЧЕМУ ИМЕННО ТАК: MySQL пишет страницы таблиц и журнал не в один
  момент, поэтому копия файлов работающей базы — состояние, которого
  на диске никогда не было: копию снимают с остановленной базы.

Уберём за собой:

  docker rm -f p4-mysql
  docker volume rm p4-mysql-data
  rm -rf data backups


=========================================================================
ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
=========================================================================

ПРОБЛЕМА: приложение не может писать в примонтированный каталог

  sh: can't create /data/file.txt: Permission denied

Каталог на машине принадлежит одному uid, а процесс в контейнере
работает от другого. Проверьте владельца каталога (ls -lan ./data)
и uid процесса (docker exec <контейнер> id) — важно число, не имя.

ПРОБЛЕМА: invalid mount config for type "bind": bind source path
does not exist

  docker: Error response from daemon: invalid mount config for type
  "bind": bind source path does not exist: /tmp/p4-absent

Так отвечает --mount, когда каталога на машине нет: ключ -v создал бы
каталог сам (от имени root), а --mount показывает опечатку сразу.
Нужен каталог — создайте его: mkdir -p ./data.

ПРОБЛЕМА: remove p4-mysql-data: volume is in use

  Error response from daemon: remove p4-mysql-data: volume is in use -
  [57c1b5ff1c3c...]

Том занят контейнером: найдите его командой docker ps -a --filter
volume=p4-mysql-data. Пока контейнер существует, том занят: сначала
docker rm, потом docker volume rm.

ПРОБЛЕМА: данные не появились в томе, хотя том подключён

Обычно путь в команде и путь, куда пишет приложение, — разные.
Смотрите, что подключено на самом деле:

  docker inspect <контейнер> --format '{{json .Mounts}}'

Поле Destination — путь ВНУТРИ контейнера; сравните его с тем, куда
пишет приложение. Отдельная ловушка: -v data:/data создаёт ТОМ
с именем data, а -v ./data:/data подключает каталог — вся разница
в одной точке в начале строки.

ПРОБЛЕМА: ERROR 1045 (28000): Access denied for user 'root'@'localhost'

  ERROR 1045 (28000): Access denied for user 'root'@'localhost'
  (using password: YES)

Пароль в .env верный, но образ читает его только при ПЕРВОЙ
инициализации: том уже создан, и учётные записи лежат внутри него,
поэтому новое значение из файла игнорируется. Путей три: вернуть
прежний пароль, сменить его через ALTER USER или создать базу заново.
