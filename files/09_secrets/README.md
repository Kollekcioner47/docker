# Готовые файлы к практике 9

Практика 9 отвечает на вопрос «как передать секрет и не потерять его
по дороге». В каталоге три набора файлов: один показывает, как секрет
утекает, два других — как передать его так, чтобы он не остался
ни в образе, ни в файле конфигурации.

| Файл | Что это |
|---|---|
| `plain-text/Dockerfile.bad` | Антипример: секрет в `ENV` и `ARG` |
| `plain-text/docker-compose.yml` | Антипример: пароль базы прямо в файле |
| `compose-secrets/docker-compose.yml` | Секрет Compose: файл и `/run/secrets` |
| `buildkit/Dockerfile` | `RUN --mount=type=secret`: секрет только сборке |

## plain-text/

Учебный антипример. В первых пяти строках каждого файла стоит пометка
`docker-course: insecure-example`: она говорит скрипту
`tools/validate_files.py`, что небезопасная конфигурация разобрана
здесь намеренно, и проверка на секреты для этих файлов пропускается.
Отключается только она: разбор YAML, закреплённые теги образов
и известность инструкций проверяются как обычно. Значения в файлах
учебные — брать их в работу нельзя.

## compose-secrets/

Правильный вариант того же примера. Значение секрета лежит в файле
`secrets/db_password.txt`, который студент создаёт себе сам: в курсе
этого файла нет, а каталог `secrets/` перечислен в `.gitignore`.
Compose монтирует значение в контейнер файлом `/run/secrets/db_password`:
сервис `db` получает его через `POSTGRES_PASSWORD_FILE`, сервис `app`
читает файл сам и печатает только длину и отпечаток значения.

## buildkit/

Секрет для сборки, а не для контейнера: токен нужен одной инструкции
`RUN` и после неё не существует. Файл с токеном тоже создаёт студент,
а в образе остаётся только его отпечаток.

## Настоящих секретов здесь нет

Ни в одном файле каталога нет настоящего пароля или токена: антипример
содержит учебные значения, а рабочие примеры берут секрет из файла,
которого в курсе нет.
