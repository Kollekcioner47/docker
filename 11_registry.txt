Практика 11. Свой реестр образов.

ДО ЭТОЙ ПРАКТИКИ ВСЕ ОБРАЗЫ ОСТАВАЛИСЬ НА МАШИНЕ: docker save и docker
load работают, но таскать файлы руками — не работа. Здесь мы поставим
свой реестр: службу, которая хранит образы и отдаёт их по сети, —
контейнер с образом registry:3.


=========================================================================
ЧТО МЫ СДЕЛАЕМ
=========================================================================

  * разберём, из чего состоит имя образа и почему push без имени
    реестра уходит на Docker Hub;
  * выпустим сертификат и файл паролей;
  * запустим registry:3 через Compose;
  * выполним docker login, docker push и docker pull;
  * удалим образ из реестра и уберём за ним место.

Свой реестр нужен потому, что образы не должны уезжать наружу, Docker Hub
не хранит приватные образы бесплатно, а свой реестр работает и без
интернета. Поднимем его контейнером из официального образа distribution.


=========================================================================
ЧТО ПОНАДОБИТСЯ
=========================================================================

  * машина admin (10.0.2.5) со стендом из практики 1;
  * файлы практики на машине:
      cp -r <курс>/files/11_registry ~/docker-lab/
  * утилиты openssl и htpasswd:
      sudo apt install -y openssl apache2-utils
  * образы alpine:3.24 и registry:3.

Узлы node1 и node2 не нужны, все команды — в каталоге практики:

  cd ~/docker-lab/11_registry


#########################################################################
ЧАСТЬ 1. БАЗОВАЯ ПРАКТИКА
#########################################################################


=========================================================================
ШАГ 1. ИМЯ ОБРАЗА РЕШАЕТ, КУДА ПОЙДЁТ PUSH
=========================================================================

Откуда образ, в имени не написано: Docker считает первую часть имени
именем пользователя на Docker Hub. Полное имя выглядит так:

  docker.io/library/alpine:3.24
  └─ реестр ─┘└─ имя ─┘└тег┘

Три части: адрес реестра, имя образа в нём и тег. Если адрес не указан,
подставляется docker.io. Наш реестр живёт по другому адресу, поэтому имя
пишут целиком:

  docker tag alpine:3.24 registry.lab.local:5000/lab/alpine:3.24

ЧЕГО НЕ ДЕЛАТЬ: не пробуйте docker push alpine:3.24 «просто проверить»:
без имени реестра Docker пойдёт на Docker Hub, потребует чужого пароля
и ответит «denied: requested access to the resource is denied».


=========================================================================
ШАГ 2. ИМЯ ДЛЯ РЕЕСТРА
=========================================================================

Реестр будет называться registry.lab.local. Имя, а не адрес, нужно
потому, что сертификат TLS выписывают на имя и клиент проверяет, что имя,
к которому он обратился, есть в сертификате.

  sudo tee -a /etc/hosts > /dev/null <<'EOF'
  10.0.2.5  registry.lab.local
  EOF

  getent hosts registry.lab.local

  10.0.2.5      registry.lab.local

ЗАЧЕМ ЭТО НУЖНО: то же имя стоит в теге образа и в имени каталога
с сертификатом. Если имя не разрешается, push отвечает «no such host».


=========================================================================
ШАГ 3. ВЫПУСКАЕМ СЕРТИФИКАТ
=========================================================================

Docker работает с реестром только по TLS: по открытому каналу уехали бы
и образы, и пароль от docker login. Выпустим сертификат сами:

  mkdir -p certs auth

  openssl req -x509 -newkey rsa:4096 -sha256 -days 825 -nodes \
      -keyout certs/registry.key -out certs/registry.crt \
      -subj "/CN=registry.lab.local" \
      -addext "subjectAltName=DNS:registry.lab.local" \
      -addext "basicConstraints=critical,CA:FALSE" \
      -addext "keyUsage=critical,digitalSignature,keyEncipherment" \
      -addext "extendedKeyUsage=serverAuth"

  * -x509 выпускает готовый сертификат, а не запрос на него;
  * -nodes оставляет ключ без пароля: реестр читает ключ при запуске;
  * subjectAltName — имя, на которое выписан сертификат; проверяет клиент
    именно его, а поле CN современные программы игнорируют.

  openssl x509 -in certs/registry.crt -noout -subject -ext subjectAltName

  subject=CN=registry.lab.local
  X509v3 Subject Alternative Name:
      DNS:registry.lab.local

ВАЖНО: certs/registry.key — это секрет. Кто получил ключ, тот может выдать
себя за ваш реестр; в репозиторий курса ключи не попадают.


=========================================================================
ШАГ 4. УЧИМ DOCKER ДОВЕРЯТЬ СЕРТИФИКАТУ
=========================================================================

Сертификат выпустили вы, и Docker про него не знает. Пока он
не установлен, демон отвечает:

  tls: failed to verify certificate: x509: certificate signed by
  unknown authority

Демон ищет сертификаты в каталоге, имя которого совпадает с именем
реестра и портом из тега:

  sudo install -d -m 0755 /etc/docker/certs.d/registry.lab.local:5000
  sudo install -m 0644 certs/registry.crt \
      /etc/docker/certs.d/registry.lab.local:5000/ca.crt

ЗАЧЕМ ЭТО НУЖНО: каталог /etc/docker/certs.d читает демон при каждом
обращении к реестру, а не клиент. Перезапускать Docker не нужно.

ИСПРАВЛЕНО: в прежней версии курса сертификат клали только в системное
хранилище (/usr/local/share/ca-certificates) — демон смотрит не туда.


=========================================================================
ШАГ 5. ФАЙЛ ПАРОЛЕЙ
=========================================================================

Пускать в реестр кого угодно нельзя: в нём лежат ваши образы. Способ
аутентификации у реестра один — файл паролей в формате htpasswd:

  htpasswd -B -c auth/htpasswd engineer

  New password:
  Re-type new password:
  Adding password for user engineer

Ключ -B включает bcrypt: медленный хеш, который дорого перебирать.

ПОЧЕМУ ПАРОЛЬ НЕ ПЕРЕДАЮТ КЛЮЧОМ: у htpasswd есть ключ -b, который
принимает пароль аргументом. Так делать нельзя: аргументы команды видны
в выводе ps и остаются в истории оболочки.

  cut -c1-12 auth/htpasswd

  engineer:$2y$

Имя пользователя видно, пароля нет. Второго добавляют той же командой
без -c: иначе файл создаётся заново.


=========================================================================
ШАГ 6. ЗАПУСКАЕМ РЕЕСТР
=========================================================================

  docker compose up -d
  docker compose ps

В выводе смотрите на три вещи: имя контейнера p11-registry, состояние
healthy и публикацию порта 10.0.2.5:5000->5000/tcp.

Файл Compose публикует порт 5000 на адрес машины admin, монтирует внутрь
настройку, сертификат и файл паролей, а данные складывает в том
registry-data.

ИСПРАВЛЕНО: путь внутри контейнера важен. В registry:3 настройка читается
из /etc/distribution/config.yml, а в registry:2 и в старых инструкциях это
было /etc/docker/registry/config.yml.

Проверим, что реестр отвечает:

  curl --silent --show-error --cacert certs/registry.crt \
      https://registry.lab.local:5000/v2/

  {"errors":[{"code":"UNAUTHORIZED","message":"authentication required",
  "detail":null}]}

Ответ 401 и UNAUTHORIZED — это правильно: сертификат принят, соединение
защищено, а без пароля реестр не пускает. Утилита curl не знает про
/etc/docker/certs.d: сертификат ей указывают ключом --cacert.


=========================================================================
ШАГ 7. ВХОД В РЕЕСТР
=========================================================================

  docker login registry.lab.local:5000 --username engineer

  Password:
  Login Succeeded

  WARNING! Your credentials are stored unencrypted in
  '/home/engineer/.docker/config.json'.

Предупреждение не про ошибку: логин и пароль сохранились в файле
~/.docker/config.json открытым текстом. В практике 9 разобрано, почему это
плохо; здесь это цена удобства. Посмотрим, что записалось:

  cat ~/.docker/config.json

В поле auth — строка из имени и пароля в base64: кодирование,
а не шифрование.


=========================================================================
ШАГ 8. PUSH: ОТПРАВЛЯЕМ ОБРАЗ
=========================================================================

  docker push registry.lab.local:5000/lab/alpine:3.24

  The push refers to repository [registry.lab.local:5000/lab/alpine]
  e2de96513ba9: Pushed
  3.24: digest: sha256:d56c381f961d307a21b3ca004cf1e391... size: 1022

Цифры у вас будут другие. Важна последняя строка — дайджест манифеста,
отпечаток образа, по которому его можно забрать, не глядя на тег.

ЗАЧЕМ ЭТО НУЖНО: тег можно переставить на другой образ, дайджест нельзя.
Строка Info про multiplatform-container в выводе Docker 29 — не ошибка:
у образа alpine есть сборки и под другие процессоры.


=========================================================================
ШАГ 9. PULL: ЗАБИРАЕМ ОБРАЗ ОБРАТНО
=========================================================================

Сначала уберём локальную копию — иначе pull ничего скачивать не станет:

  docker image rm registry.lab.local:5000/lab/alpine:3.24

  Untagged: registry.lab.local:5000/lab/alpine:3.24

Удалился только тег: слои остались, на них ссылается образ alpine:3.24.

  docker pull registry.lab.local:5000/lab/alpine:3.24

  3.24: Pulling from lab/alpine
  Digest: sha256:d56c381f961d307a21b3ca004cf1e391...
  Status: Downloaded newer image for registry.lab.local:5000/lab/alpine:3.24

Дайджест совпал с тем, что напечатал push: реестр вернул ровно то, что
получил. Так проверяют, что образ дошёл без изменений.

У реестра есть HTTP API, и посмотреть его содержимое можно без Docker:

  curl --silent --show-error --cacert certs/registry.crt -u engineer \
      https://registry.lab.local:5000/v2/_catalog

  {"repositories":["lab/alpine"]}

ЗАЧЕМ ЭТО НУЖНО: docker images показывает только локальные образы, а что
лежит в реестре — отвечает каталог _catalog. Ключ -u без пароля заставит
curl спросить пароль: в истории он не останется.

=========================================================================
ШАГ 10. УДАЛЕНИЕ ОБРАЗА И СБОРКА МУСОРА
=========================================================================

Команды «удалить образ из реестра» у Docker нет: удаление — это запрос
к API реестра по дайджесту манифеста. Узнаем дайджест:

  curl --silent --cacert certs/registry.crt -u engineer --head \
      --header 'Accept: application/vnd.oci.image.manifest.v1+json' \
      https://registry.lab.local:5000/v2/lab/alpine/manifests/3.24

  HTTP/1.1 200 OK
  Docker-Content-Digest: sha256:d56c381f961d307a21b3ca004cf1e391...

Отправим DELETE с этим дайджестом:

  curl --silent --cacert certs/registry.crt -u engineer --request DELETE \
      https://registry.lab.local:5000/v2/lab/alpine/manifests/<дайджест>

Ответ — код 202, а тег исчез: {"name":"lab/alpine","tags":null}. Место на
диске при этом не освободилось: удалилась ссылка на манифест, а слои
остались. Убирает их сборка мусора — команда самого реестра. На работающем
реестре её не запускают: пока она перебирает манифесты, реестр может
записать новый слой, который сборка сочтёт ненужным.

  docker compose stop registry
  docker compose run --rm --entrypoint /bin/registry registry \
      garbage-collect --dry-run /etc/distribution/config.yml

  0 blobs marked, 3 blobs and 0 manifests eligible for deletion

Убедившись, запускают то же самое с ключом --delete-untagged — он убирает
и манифесты, на которые не ссылается ни один тег, — и поднимают реестр:

  docker compose run --rm --entrypoint /bin/registry registry \
      garbage-collect --delete-untagged /etc/distribution/config.yml
  docker compose start registry


=========================================================================
ШАГ 11. ЧТО БЫВАЕТ БЕЗ TLS
=========================================================================

Про HTTP-реестры нужно знать: половина старых инструкций в интернете —
про них. Запустим реестр без TLS и попробуем в него войти:

  docker run -d --name p11-http -p 10.0.2.5:5001:5000 registry:3
  docker tag alpine:3.24 10.0.2.5:5001/lab/alpine:3.24
  docker push 10.0.2.5:5001/lab/alpine:3.24

  Error response from daemon: failed to resolve reference ...:
  failed to do request: Head "https://10.0.2.5:5001/v2/lab/alpine/...":
  http: server gave HTTP response to HTTPS client

Docker всегда сначала пробует HTTPS, а получив в ответ открытый HTTP,
отказывается работать. Заставить его можно, перечислив реестр
в insecure-registries в файле /etc/docker/daemon.json, — тогда образы
и пароль пойдут по сети открытым текстом.

ЧЕГО НЕ ДЕЛАТЬ: не оставляйте insecure-registries «чтобы работало»: это
временная мера для отладки.

  docker rm -f p11-http


=========================================================================
ШАГ 12. КОГДА СВОЕГО РЕЕСТРА УЖЕ МАЛО
=========================================================================

Harbor ставят, когда нужно больше, чем хранилище: кабинет в браузере,
права по проектам, проверка образов на уязвимости, копирование между
площадками. Сервисов в нём десяток, но ставится он тем же файлом Compose.

Nexus Repository Manager хранит и пакеты npm, maven, deb; материал о нём
лежит в archive/nexus/. Его образы по HTTP: insecure-registries ради
отладки.


=========================================================================
ШАГ 13. УБИРАЕМ ЗА СОБОЙ
=========================================================================

Реестр можно оставить: он ничего не ломает. Если убираете:

  docker logout registry.lab.local:5000
  docker image rm registry.lab.local:5000/lab/alpine:3.24
  docker compose down -v

Ключ -v у down удаляет и том registry-data вместе с образами. Каталог
с сертификатом тоже стоит убрать:

  sudo rm -rf /etc/docker/certs.d/registry.lab.local:5000


=========================================================================
ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
=========================================================================

ПРОБЛЕМА: x509: certificate signed by unknown authority

    tls: failed to verify certificate: x509: certificate signed by
    unknown authority

  Демон не нашёл сертификат реестра. Проверяйте по порядку:

    1. имя каталога совпадает с именем и портом из тега:
       ls -l /etc/docker/certs.d/
    2. файл внутри называется ca.crt (не .crt и не .pem):
       ls -l /etc/docker/certs.d/registry.lab.local:5000/

  Частая причина — опечатка в имени: в теге lab.local, а в каталоге lab.

ПРОБЛЕМА: http: server gave HTTP response to HTTPS client

  Реестр отвечает по открытому HTTP, а Docker ждёт TLS: значит, на этом
  порту работает реестр без сертификата или другой контейнер. Лечится
  не настройкой insecure-registries, а запуском реестра с сертификатом:
  настройка должна лежать по пути /etc/distribution/config.yml.

ПРОБЛЕМА: dial tcp: lookup registry.lab.local: no such host

  Имя реестра не разрешается. Добавьте строку в /etc/hosts, как в шаге 2:

    getent hosts registry.lab.local

ПРОБЛЕМА: push access denied ... no basic auth credentials

    push access denied, repository does not exist or may require
    authorization: authorization failed: no basic auth credentials

  Вы не вошли в реестр — или вошли, а пароль не подошёл:

    docker login registry.lab.local:5000 --username engineer

ПРОБЛЕМА: Bind for 10.0.2.5:5000 failed: port is already allocated

  Порт 5000 занят другим контейнером — обычно реестром от прошлого
  запуска. Найдите его и поднимите реестр заново:

    docker ps --filter publish=5000
    docker compose down
    docker compose up -d

ПРОБЛЕМА: configuration error: error parsing ... unsupported version

    configuration error: error parsing /etc/distribution/config.yml:
    unsupported version: ""

  В файле настройки нет первой строки version: 0.1 — без неё registry:3
  не работает. Вторая причина: файл смонтирован не туда.

    docker compose logs registry
    head -3 registry/config.yml


=========================================================================
ЧТО ДАЛЬШЕ
=========================================================================

Мы поставили свой реестр, отправили в него образ и забрали обратно.
Главное из практики — три вещи. Первая: место хранения образа записано
в его имени, поэтому push без адреса реестра уходит на Docker Hub.
Вторая: Docker работает с реестром только по TLS, а доверие сертификату
задаётся каталогом /etc/docker/certs.d на самой машине. Третья: половину
того, чего нет в командах Docker (каталог, удаление, мусор), делают
запросами к API реестра.

    равна правам root.
