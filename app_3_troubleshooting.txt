Приложение 3. Ошибки: симптом, причина, что делать.

ЭТО ПРИЛОЖЕНИЕ — СКВОЗНОЕ ПО ВСЕМУ КУРСУ. Здесь собраны самые частые
ошибки двенадцати практик. Текст ошибки приведён настоящим: узнают их
именно по тексту. Ищите поиском по строке из терминала, начиная
с первого слова Error или с характерной части сообщения.

  Формулировки меняются от выпуска к выпуску. Там, где сообщения
  различаются, ниже приведены оба варианта.

#########################################################################
ОШИБКИ ПО ТЕМАМ
#########################################################################

=========================================================================
1. ЗАПУСК, ДЕМОН И ПРАВА
=========================================================================

СИМПТОМ: отказ в доступе к сокету демона

  permission denied while trying to connect to the Docker daemon
  socket at unix:///var/run/docker.sock: connect: permission denied

ПРИЧИНА: пользователя нет в группе docker, либо группа ещё не
применилась к текущей сессии. Членство в группе docker — это права
root на машине (практика 1, шаг 4).

  id -nG
  sudo usermod -aG docker "$USER"

После usermod нужно выйти из системы и войти снова (быстрая проверка
без выхода — newgrp docker). Права на сокет через chmod 666 не меняют:
это открывает демон всем на машине.

СИМПТОМ: Cannot connect to the Docker daemon

  Cannot connect to the Docker daemon at unix:///var/run/docker.sock.
  Is the docker daemon running?

ПРИЧИНА: демон не запущен либо клиент ищет сокет не там, где демон его
создал. Это другое, чем отказ в доступе: группа здесь в порядке.

  sudo systemctl status docker --no-pager
  sudo journalctl -u docker -n 50 --no-pager
  echo "$DOCKER_HOST"

СИМПТОМ: docker: 'compose' is not a docker command

  docker: 'compose' is not a docker command.
  See 'docker --help'

ПРИЧИНА: не установлен плагин Compose. Compose v2 — это плагин CLI
(пакет docker-compose-plugin), а не отдельная программа.

  sudo apt install -y docker-compose-plugin
  docker compose version

В Engine 29.x сообщение другое: «unknown command: docker compose».
Старый docker-compose через дефис — это Compose v1, снятый
с поддержки: его нужно удалить.

СИМПТОМ: Error response from daemon: No such container

  Error response from daemon: No such container: p2-web

ПРИЧИНА: контейнера с таким именем нет: опечатка, контейнер удалён
раньше, либо команда выполнена не на той машине.

  docker ps -a
  docker ps -a --filter name=p2

=========================================================================
2. КОДЫ ВОЗВРАТА КОНТЕЙНЕРА
=========================================================================

СИМПТОМ: контейнер завершился с кодом 1

  Exited (1) 3 seconds ago

ПРИЧИНА: код 1 означает «приложение завершилось с ошибкой». Docker
здесь ни при чём — он только передал код.

  docker logs --tail 50 <имя>
  docker inspect <имя> --format '{{.Config.Cmd}}'

Если журнал пуст, приложение не успело ничего напечатать: запустите
его в интерактивном режиме — docker run --rm -it <образ> sh.

СИМПТОМ: контейнер завершился с кодом 137

  Exited (137) 2 seconds ago

ПРИЧИНА: процесс убит сигналом SIGKILL (128 + 9). Так бывает в трёх
случаях: вы сами выполнили docker kill; ядро убило контейнер из-за
нехватки памяти; контейнер не ответил на SIGTERM за отведённое время.

  docker inspect <имя> --format '{{.State.OOMKilled}}'
  docker events --since 30m --filter event=oom

Значение true — это нехватка памяти, разбор в разделе 6.

=========================================================================
3. ОБРАЗЫ И СБОРКА
=========================================================================

СИМПТОМ: образ не скачивается — manifest unknown

  Error response from daemon: manifest for alpine:3.99 not found:
  manifest unknown: manifest unknown

ПРИЧИНА: тега с таким именем в реестре нет: опечатка в версии, образ
удалён из реестра или указан не тот реестр.

  docker manifest inspect alpine:3.24

Не подставляйте latest «чтобы заработало»: в курсе теги закреплены
на поддерживаемых выпусках.

СИМПТОМ: exec format error

  exec /run.sh: exec format error

ПРИЧИНА: ядро не может исполнить программу. Либо образ собран под
другую архитектуру, либо точкой входа указан не исполняемый для Linux
файл, либо скрипт скопирован с Windows-переводами строк.

  docker image inspect <образ> --format '{{.Architecture}}'
  file run.sh

Ответ с CRLF означает Windows-переводы строк; для такого скрипта
сообщение бывает другим — «exec /run.sh: no such file or directory».

СИМПТОМ: сборка падает на COPY

  ERROR: failed to build: failed to solve: failed to compute cache key:
  "/app.py": not found

ПРИЧИНА: файла нет в контексте сборки: он лежит не там, где вы
думаете, исключён файлом .dockerignore или сборка запущена не из того
каталога. COPY видит только то, что лежит рядом с Dockerfile.

  ls -l app.py
  cat .dockerignore

СИМПТОМ: сборка падает с unknown instruction

  ERROR: failed to build: failed to solve: dockerfile parse error
  on line 2: unknown instruction: RUN2 (did you mean RUN?)

ПРИЧИНА: опечатка в имени инструкции. Разбор файла идёт до сборки,
поэтому сообщение точное: строка указана, замена предложена.

Длинную команду в Dockerfile переносят обратным слэшем, а не скобкой;
лишний && после переноса даёт ошибку синтаксиса.

СИМПТОМ: образ занят и не удаляется

  Error response from daemon: conflict: unable to remove repository
  reference "app:1" (must force) - container 695e0bac3ba0 is using
  its referenced image c9e350dad30d

ПРИЧИНА: из образа создан контейнер, пусть даже остановленный. Docker
не удаляет образ, пока на него есть ссылки.

  docker ps -a --filter ancestor=app:1
  docker rm <имя>
  docker image rm app:1

=========================================================================
4. ДАННЫЕ: ТОМА И ПРАВА
=========================================================================

СИМПТОМ: удалил контейнер — данные исчезли

Ошибки нет вовсе: после docker rm файлы просто пропали.

ПРИЧИНА: данные лежали в контейнере, а не в томе. Изменяемый слой
принадлежит контейнеру и удаляется вместе с ним (практика 4).

  docker inspect <имя> --format '{{json .Mounts}}'
  docker run -d --name p4-db -v dbdata:/var/lib/mysql mysql:8.4

СИМПТОМ: том занят и не удаляется

  Error response from daemon: remove dbdata: volume is in use - [7f70dd51]

ПРИЧИНА: том подключён к контейнеру; ссылка сохраняется, даже если
контейнер остановлен: Docker защищает данные от случайного удаления.

  docker ps -a --filter volume=dbdata
  docker rm -f <имя>
  docker volume rm dbdata

Удалённый том не восстанавливается: сначала сделайте архив.

СИМПТОМ: permission denied на примонтированном каталоге

  sh: can't create /data/file: Permission denied

ПРИЧИНА: процесс в контейнере работает от root, а каталог на хосте
принадлежит вашему пользователю. Права считаются по числам, а имена
пользователей внутри контейнера о хосте ничего не знают.

  docker exec <имя> id
  docker run --rm -u "$(id -u):$(id -g)" -v "${PWD}:/data" \
      alpine:3.24 touch /data/file

Второе решение — задать USER в образе (практика 10).

=========================================================================
5. СЕТИ, ПОРТЫ И COMPOSE
=========================================================================

СИМПТОМ: порт уже занят

  Error response from daemon: failed to set up container networking:
  Bind for 0.0.0.0:8080 failed: port is already allocated

ПРИЧИНА: порт хоста занят другим контейнером или обычной службой.
Порт внутри контейнера может повторяться сколько угодно, порт хоста —
нет.

  docker ps --format 'table {{.Names}}\t{{.Ports}}'
  sudo ss -tlnp | grep 8080

Возьмите другой порт хоста или освободите занятый.

СИМПТОМ: контейнеры не видят друг друга по имени

  ping: bad address 'p5-nginx'

ПРИЧИНА: контейнеры в сети по умолчанию (bridge). Встроенный DNS
Docker там не работает, имена контейнеров не разрешаются.

  docker network create p5-net
  docker run -d --name p5-nginx --network p5-net nginx:1.30-alpine
  docker exec p5-client ping -c 1 p5-nginx

СИМПТОМ: контейнер с nginx выходит сразу, порт не слушается

  [emerg] 1#1: host not found in upstream "backend" in
  /etc/nginx/conf.d/default.conf:4

ПРИЧИНА: nginx разрешает имена из proxy_pass при старте, а не при
запросе. Если адресат в этой сети не разрешается — он в другой сети
или ещё не поднят, — мастер-процесс завершается, и контейнер выходит
с кодом 1. Сам образ при этом исправен.

  docker compose exec nginx getent hosts backend
  docker run --rm --entrypoint nginx <образ> -t

Устойчивое решение — задать resolver 127.0.0.11 и обращаться
через переменную (proxy_pass $upstream): тогда ошибка соединения
отдаётся как 502, а контейнер стартует.

СИМПТОМ: файл Compose не разбирается

  yaml: line 3: found character that cannot start any token
  yaml: line 4: mapping values are not allowed in this context

ПРИЧИНА: отступы. YAML требует пробелов и запрещает табуляцию; номер
строки часто указывает на начало документа, поэтому проверяйте
несколько строк вокруг.

  grep -P '\t' docker-compose.yml
  docker compose config

СИМПТОМ: переменная не подставилась

  level=warning msg="The \"DB_PASSWORD\" variable is not set.
  Defaulting to a blank string."

ПРИЧИНА: в файле есть подстановка ${ПЕРЕМЕННАЯ}, а значения нет.
Compose не считает это ошибкой: он подставляет пустую строку
и продолжает, а приложение потом падает.

  cp .env.example .env
  docker compose config

Значение по умолчанию задают как ${VAR:-значение}.

СИМПТОМ: зависимый сервис не поднимается

  dependency failed to start: container notes-db-1 is unhealthy

ПРИЧИНА: сервис, от которого зависит запуск, не прошёл проверку
healthcheck. depends_on с условием service_healthy ждёт успешной
проверки, а не «контейнер запущен».

  docker compose ps
  docker compose logs db --tail 50

=========================================================================
6. SWARM И ОГРАНИЧЕНИЕ РЕСУРСОВ
=========================================================================

СИМПТОМ: This node is not a swarm manager

  Error response from daemon: This node is not a swarm manager. Use
  "docker swarm init" or "docker swarm join" to connect this node.

ПРИЧИНА: команда кластера выполнена на машине, которая в кластер
не входит. Это не сбой, а защита.

  docker info --format '{{.Swarm.LocalNodeState}}'
  docker swarm init --advertise-addr 10.0.2.5

Ответ inactive означает, что Swarm не инициализирован.

СИМПТОМ: сервис не сходится, задачи перезапускаются

  Задачи в состоянии Rejected или Restarting, число реплик не набирается.

ПРИЧИНА: причин три, и различаются они по выводу docker service ps:
образ не найден на узле; приложение падает сразу после старта; задача
не помещается из-за ограничений размещения.

  docker service ps <сервис> --no-trunc
  docker service logs <сервис> --tail 50

СИМПТОМ: контейнер падает с кодом 137, в журнале пусто

  Exited (137) 5 seconds ago

ПРИЧИНА: контейнер убит ядром из-за нехватки памяти. Решение принимает
не Docker и не приложение, а ограничитель памяти (практика 8).

  docker inspect <имя> --format '{{.State.OOMKilled}}'
  docker inspect <имя> --format '{{.HostConfig.Memory}}'
  docker stats --no-stream <имя>

СИМПТОМ: sh: can't fork: Resource temporarily unavailable

  sh: can't fork: Resource temporarily unavailable

ПРИЧИНА: исчерпан предел числа процессов. Сработал либо --pids-limit
у контейнера, либо системный предел у пользователя.

  docker inspect <имя> --format '{{.HostConfig.PidsLimit}}'
  docker stats --no-stream --format '{{.Name}} {{.PIDs}}'

=========================================================================
7. СЕКРЕТЫ И СВОЙ РЕЕСТР
=========================================================================

СИМПТОМ: пароль виден в inspect и в history

  docker inspect показывает значение переменной окружения,
  docker history — ARG и ENV из образа.

ПРИЧИНА: секрет передан через переменную окружения или аргумент
сборки. Это не секрет, а опубликованное значение (практика 9).

  docker inspect <имя> --format '{{json .Config.Env}}'

Передавайте секреты файлом (--env-file), переменной с окончанием _FILE
или секретом BuildKit. Если секрет попал в образ, образ нужно
пересобрать: слои неизменяемы.

СИМПТОМ: приложение не находит файл секрета

Файла /run/secrets/<имя> внутри контейнера нет, ошибки при запуске тоже.

ПРИЧИНА: секрет не объявлен для этого контейнера или сервиса. Само
создание секрета ничего не монтирует: монтирование описывают отдельно.

  docker exec <имя> ls -l /run/secrets/

СИМПТОМ: server gave HTTP response to HTTPS client

  Get "https://registry.lab.local:5000/v2/": http: server gave
  HTTP response to HTTPS client

ПРИЧИНА: Docker обращается к реестру по HTTPS, а реестр отвечает
по HTTP. Docker принципиально не работает с реестром без TLS.

  curl -s http://registry.lab.local:5000/v2/

Выпустите сертификат на имя хоста и положите его
в /etc/docker/certs.d/<имя:порт>/ca.crt (практика 11). Добавление
реестра в insecure-registries — только временная мера для отладки.
Родственное сообщение — «x509: certificate signed by unknown
authority»: сертификат есть, но хост ему не доверяет.

СИМПТОМ: unauthorized: authentication required

  unauthorized: authentication required
  no basic auth credentials

ПРИЧИНА: реестр требует аутентификации, а клиент её не предъявил
или предъявил неверную.

  docker login registry.lab.local:5000
  docker image ls --format '{{.Repository}}:{{.Tag}}' | grep registry

Проверьте, в какой реестр уходит запрос: имя образа должно содержать
адрес реестра, иначе образ уходит в Docker Hub.

=========================================================================
8. ХОСТ, ЖУРНАЛЫ И АУДИТ
=========================================================================

СИМПТОМ: кончилось место на диске, а образов и томов немного

  no space left on device

ПРИЧИНА: журналы контейнеров. По умолчанию Docker пишет журнал
каждого контейнера в файл и не удаляет его: контейнер, печатающий
по строке в секунду, за месяц вырастает в гигабайты.

  docker system df
  sudo du -sh /var/lib/docker/*

Убирайте осознанно: docker container prune, docker image prune.
Команду docker system prune -a без фильтра в курсе не применяют.

СИМПТОМ: аудит не показывает ничего

  ausearch -k docker_config не находит событий.

ПРИЧИНА: у правила нет ключа, правило не загружено, либо событие
произошло до включения правила. Правило без ключа бесполезно:
событие в журнал попадает, а найти его нечем.

  sudo auditctl -l
  sudo augenrules --load
  sudo ausearch -k docker_config -i

=========================================================================
ЧТО ДАЛЬШЕ
=========================================================================

Если вашей ошибки здесь нет, начните с полного текста: скопируйте
строку из терминала целиком. Дальше почти всегда помогают три команды
и события демона:

  docker ps -a
  docker inspect <имя> --format '{{json .State}}'
  docker logs --tail 50 <имя>
  docker events --since 30m

Первая ошибка в выводе — причина, остальные — следствия. Проверьте
также, что вы на той машине: в курсе три машины.

  * приложение 1 — Podman: чем отличается от Docker;
  * приложение 2 — шпаргалка по командам курса;
  * практики 1–6 — установка, контейнеры, образы, Dockerfile, данные,
    сети, Compose;
  * практики 7–12 — Swarm, ресурсы, секреты, безопасность образов,
    свой реестр, аудит хоста.
