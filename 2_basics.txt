Практика 2. Образы и контейнеры.

ЭТА ПРАКТИКА — ПРО БАЗОВЫЕ КОМАНДЫ DOCKER. Первая практика поставила
Docker и запустила один контейнер. Здесь мы разберёмся, из чего он
состоит, как им управлять и что означает код, с которым он завершился.
Все команды набираются руками: готовых скриптов в курсе нет.


=========================================================================
ЧТО МЫ СДЕЛАЕМ
=========================================================================

Разберём разницу между образом и контейнером, научимся скачивать образы
и запускать контейнеры (-d, -it, --name, --rm), пройдём контейнер
по кругу (ps, stop, start, restart, rm), посмотрим журнал, зайдём внутрь
через docker exec, разберём коды возврата 0, 1, 127 и 137, политики
перезапуска, docker inspect и уборку.

=========================================================================
ШАГ 1. ОБРАЗ И КОНТЕЙНЕР: В ЧЁМ РАЗНИЦА
=========================================================================

  ОБРАЗ — упакованная файловая система приложения вместе с настройками
  запуска. Он неизменяем: ни один контейнер его не меняет.

  КОНТЕЙНЕР — запущенный процесс: ему показали файловую систему образа
  и добавили сверху свой слой для записи.

Проверим опытом: запишем файл в контейнер и посмотрим, увидит ли его
второй контейнер из того же образа.

  docker run --rm --name p2-img-1 alpine:3.24 \
      sh -c 'echo отметка > /mark.txt; cat /mark.txt'
  отметка

  docker run --rm --name p2-img-2 alpine:3.24 ls -l /mark.txt
  ls: /mark.txt: No such file or directory

Файла нет: запись осталась в слое первого контейнера, а тот удалился
вместе с флагом --rm. Образ остался таким, каким его скачали.

ПОЧЕМУ ИМЕННО ТАК: если бы контейнер менял образ, второй запуск зависел
бы от первого. И ещё одно: контейнер живёт ровно столько, сколько живёт
его главный процесс.


=========================================================================
ШАГ 2. DOCKER PULL И ТЕГИ
=========================================================================

Образы лежат в реестре — службе, которая хранит их и отдаёт по сети.
Реестр по умолчанию — Docker Hub; про свой реестр — практика 11.

  docker pull alpine:3.24
  3.24: Pulling from library/alpine
  Status: Image is up to date for alpine:3.24
  docker.io/library/alpine:3.24

Последняя строка — полное имя: реестр, владелец, имя и тег образа.

ТЕГ — версия образа, которую выбрал тот, кто его собрал. Тег latest
означает «какой-то последний»: сегодня под ним одна сборка, завтра
другая. Поэтому в курсе он не используется.

  docker images
  REPOSITORY   TAG       IMAGE ID       CREATED      SIZE
  alpine       3.24      320994c3b997   6 days ago   8.42MB

ЧЕГО НЕ ДЕЛАТЬ: не указывайте образ без тега. Запись docker pull alpine
означает alpine:latest, и в следующий раз под ним будет другой образ.


=========================================================================
ШАГ 3. DOCKER RUN: ПЕРВЫЙ КОНТЕЙНЕР
=========================================================================

docker run создаёт контейнер из образа и сразу запускает его. Флаги,
которые нужны каждый день:

  --rm     удалить контейнер сразу после завершения;
  -d       запустить и вернуть управление;
  --name   имя вместо идентификатора (имя уникально на машине);
  -it      оставить ввод открытым и выделить терминал.

  docker run -d --name p2-sleeper alpine:3.24 sleep 300
  51c73dc8f847fe293efb84d7ea4856b74c4ab076a8fd57bc31cf01971ac6268f
  docker run --rm -it alpine:3.24 sh

Вторая команда оставит вас внутри контейнера: приглашение вида / #
означает, что вы root в Alpine. Выход — exit.

ВАЖНО: без -d команда занимает терминал до завершения процесса — это
главная причина «Docker висит».


=========================================================================
ШАГ 4. DOCKER PS: ЧТО ЗАПУЩЕНО
=========================================================================

  docker ps
  CONTAINER ID   IMAGE         STATUS         NAMES
  51c73dc8f847   alpine:3.24   Up 2 minutes   p2-sleeper

Здесь только работающие контейнеры. Остановленные видны с ключом -a:

  docker ps -a
  CONTAINER ID   STATUS                     NAMES
  3f61a8e0c4d1   Exited (0) 5 minutes ago   p2-exited

  docker ps --filter status=exited   только остановленные

ИСПРАВЛЕНО: в прежней версии курса эта команда была записана как
«docker ps a» — без дефиса. Docker отвечает «docker: 'docker ps' accepts
no arguments» и завершается с кодом 1: буква a для него не флаг,
а лишний аргумент.


=========================================================================
ШАГ 5. ОСТАНОВИТЬ, ЗАПУСТИТЬ, УДАЛИТЬ
=========================================================================

  docker stop p2-sleeper      вежливо остановить контейнер
  docker start p2-sleeper     запустить тот же контейнер снова
  docker restart p2-sleeper   остановить и запустить одной командой
  docker rm p2-sleeper        удалить остановленный контейнер
  docker rm -f p2-sleeper     удалить работающий контейнер

ОСТАНОВЛЕННЫЙ И УДАЛЁННЫЙ — РАЗНЫЕ ВЕЩИ, и путаница здесь стоит данных.
Остановленный контейнер существует целиком: имя, настройки, журнал,
записанные файлы. Его видно в docker ps -a, имя и место заняты, а stop
и start возвращают его к жизни:

  docker run -d --name p2-keep alpine:3.24 sleep 300
  docker exec p2-keep sh -c 'echo отметка > /mark.txt'
  docker stop p2-keep
  docker start p2-keep
  docker exec p2-keep cat /mark.txt
  отметка

Удалённого контейнера нет: вместе с ним исчезают его слой, журнал и имя.
  docker rm -f p2-keep
  docker start p2-keep
  Error response from daemon: No such container: p2-keep

ЗАЧЕМ ЭТО НУЖНО: отсюда правило: всё, что должно пережить контейнер,
хранят вне него — в томе. Это практика 4.


=========================================================================
ШАГ 6. ЖУРНАЛ: DOCKER LOGS
=========================================================================

Журнал контейнера — это то, что процесс напечатал в стандартный вывод
и в стандартный поток ошибок. Запустим говорящий контейнер:

  docker run -d --name p2-logs alpine:3.24 \
      sh -c 'i=0; while true; do i=$((i+1)); echo строка $i; sleep 1; done'

  docker logs --tail 2 p2-logs
  строка 4
  строка 5

  docker logs -f p2-logs          следить за журналом в реальном времени
  docker logs --since 2s p2-logs  только за последние две секунды

Ключ --tail незаменим на контейнерах, которые работают месяцами: журнал
может быть на сотни мегабайт. Ключ -f дописывает новые строки; выход —
Ctrl+C, и, в отличие от docker attach, контейнер продолжает работать.

ПОЧЕМУ В ЖУРНАЛЕ БЫВАЕТ ПУСТО: приложение пишет в свой файл внутри
контейнера, а не в вывод. Так же при мгновенной смерти от SIGKILL.


=========================================================================
ШАГ 7. DOCKER EXEC: ЗАЙТИ ВНУТРЬ
=========================================================================

  docker exec -it p2-sleeper sh

exec запускает в работающем контейнере ещё один процесс. Он видит ту же
файловую систему и ту же сеть, что и главный процесс, но главного
не касается: выход из оболочки контейнер не останавливает.

  docker exec p2-sleeper ps -o pid,ppid,comm
  PID   PPID  COMMAND
      1     0 sleep
      7     0 ps

Два процесса: главный (sleep, PID 1) и наш ps. Чужих процессов не видно.

ЧЕГО EXEC НЕ УМЕЕТ: работать в остановленном контейнере и сохранять
изменения — всё, что вы поставили через exec, исчезнет вместе
с контейнером. Всё, что должно быть в контейнере всегда, описывают
в Dockerfile — это практика 3.


=========================================================================
ШАГ 8. КОДЫ ВОЗВРАТА: 0, 1, 127, 137
=========================================================================

Когда контейнер «не работает», первый вопрос — с каким кодом он
завершился:

  docker inspect --format '{{.State.ExitCode}}' <имя>

  0     процесс завершился успешно: контейнер «вышел»;
  1     ошибку вернуло само приложение. Смотреть журнал;
  127   команды нет внутри образа: опечатка или её нет в PATH;
  137   128 + 9: процесс убит сигналом SIGKILL, который нельзя
        ни обработать, ни проигнорировать.

Проверим первые три:
  docker run --name p2-ok alpine:3.24 true
  docker run --name p2-fail alpine:3.24 sh -c 'exit 1'
  docker run --name p2-127 alpine:3.24 nosuchcommand

  docker inspect --format '{{.State.ExitCode}}' p2-ok        0
  docker inspect --format '{{.State.ExitCode}}' p2-fail      1
  docker inspect --format '{{.State.ExitCode}}' p2-127       127
  docker inspect --format '{{.State.Status}}' p2-127         created

КОД 127 — ОСОБЫЙ СЛУЧАЙ: контейнер создан, но не запущен, потому что
процесс не удалось стартовать («executable file not found in $PATH»).
У такого контейнера состояние created, а не exited.

ПОЧЕМУ 137, А НЕ 143. docker stop посылает процессу SIGTERM («завершись
аккуратно»), ждёт десять секунд и только потом посылает SIGKILL. SIGKILL
убивает мгновенно, и код получается 137. Приложения (базы данных,
веб-серверы) SIGTERM обрабатывают и завершаются с кодом 143.

  docker run -d --name p2-kill alpine:3.24 sleep 600
  docker kill p2-kill
  docker inspect --format '{{.State.ExitCode}}' p2-kill      137

ЗАЧЕМ ЭТО НУЖНО: вторая причина того же кода — кончившаяся память: ядро
убивает процесс, вышедший за разрешённый ему лимит. Различить случаи
помогает docker inspect --format '{{.State.OOMKilled}}' <имя>; true
означает нехватку памяти, разбор — практика 8.


=========================================================================
ШАГ 9. DOCKER INSPECT: ЧТО ЗА КОНТЕЙНЕР
=========================================================================

docker inspect печатает всё, что демон знает о контейнере: это сотни
строк JSON. Читать их глазами бессмысленно — нужное поле выбирают
шаблоном в стиле Go.
  docker inspect --format '{{.State.Status}}' p2-sleeper       running
  docker inspect --format '{{.Config.Image}}' p2-sleeper       alpine:3.24
  docker inspect --format '{{.RestartCount}}' p2-sleeper       0

ВАЖНО: искать нужное в JSON через grep нельзя — имя контейнера
встречается в файле несколько раз, и grep вернёт не то. Шаблон выбирает
поле по структуре. Ключ --format работает и в docker ps.

=========================================================================
ШАГ 10. УБОРКА: DF, RM, RMI, PRUNE
=========================================================================

Docker занимает место, и оно заканчивается. Посмотрим, на что:

  docker system df
  TYPE            TOTAL     ACTIVE    SIZE      RECLAIMABLE
  Images          29        13        4.215GB   2.653GB (62%)
  Containers      31        17        85.55MB   20.97MB (24%)
  Local Volumes   33        11        2.148GB   93.16MB (4%)

RECLAIMABLE — сколько можно освободить, не трогая используемое; обычно
место съедают не образы, а журналы и тома (docker system df -v).
Удаляем по имени, а не «всё подряд»:

  docker rm p2-ok p2-fail p2-127     удалить контейнеры практики
  docker rmi <образ>                 удалить ненужный образ

Образ, который использует хотя бы один контейнер — даже остановленный, —
не удалится: docker rmi ответит «conflict: unable to remove repository
reference ... container ... is using its referenced image».

Есть и командная уборка: docker container prune (остановленные
контейнеры), docker image prune (образы без тега), docker system prune.

ЧЕГО НЕ ДЕЛАТЬ: не выполняйте docker system prune «чтобы освободить
место». Команда удалит остановленные контейнеры, неиспользуемые сети,
все образы, которые не использует ни один работающий контейнер, и весь
кэш сборки — включая чужие и скачанные заранее. Отменить это нельзя.
Уборка называется по имени или по метке:

  docker container prune --filter label=docker-course.practice=2


=========================================================================
ШАГ 11. ПОЛИТИКИ ПЕРЕЗАПУСКА: --RESTART
=========================================================================

Политика перезапуска отвечает на вопрос «что делать, если процесс
завершился». Задаётся ключом --restart при запуске:

  no              не перезапускать. Значение по умолчанию;
  on-failure[:N]  перезапускать, если код возврата не 0; после N попыток
                  остановиться;
  always          перезапускать всегда;
  unless-stopped  то же, что always, но контейнер, остановленный вручную,
                  сам не поднимается.

Посмотрим на живых контейнерах: оба падают через секунду.

  docker run -d --name p2-r-of --restart on-failure:3 \
      alpine:3.24 sh -c 'sleep 1; exit 1'
  docker run -d --name p2-r-al --restart always \
      alpine:3.24 sh -c 'sleep 1; exit 1'

Через полминуты смотрим число перезапусков:
  docker inspect --format '{{.RestartCount}}' p2-r-of      3
  docker inspect --format '{{.RestartCount}}' p2-r-al      8

on-failure:3 сделал ровно три попытки и сдался: число в счётчике совпало
с заданным. always крутит контейнер бесконечно, и число у него зависит
от того, сколько вы ждали: между попытками Docker держит паузу, чтобы
падающий контейнер не съел процессор и не засорил журнал.

ЧЕГО НЕ ДЕЛАТЬ: не ставьте always одноразовым контейнерам — миграциям
и командам, которые отработали и завершились с кодом 0: такой контейнер
будет запускаться бесконечно. Сменить политику можно на ходу:
  docker update --restart unless-stopped p2-r-al

ЧЕМ ALWAYS ОТЛИЧАЕТСЯ ОТ UNLESS-STOPPED. Пока контейнер падает сам, они
ведут себя одинаково. Разница видна, когда контейнер остановили вручную
и перезагрузили машину: always запустит его снова, unless-stopped
оставит остановленным. Проверим на стенде без перезагрузки:
  docker stop p2-r-al
  docker inspect --format '{{.State.Status}}' p2-r-al      exited

Ручная остановка отменила политику. Перезапускать демон на стенде
не будем: вместе с ним остановятся контейнеры всех практик.


=========================================================================
ШАГ 12. ОДИН ПРОЦЕСС — ОДИН КОНТЕЙНЕР
=========================================================================

Правило: в контейнере должен быть один главный процесс. Тогда код
возврата и журнал относятся к одному приложению, а обновить его можно,
не трогая остальные. Несколько приложений — несколько контейнеров
в одной сети (практика 5) или файл Compose (практика 6).


=========================================================================
ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
=========================================================================

ПРОБЛЕМА: контейнер сразу завершился, и его нет в docker ps

Команда выполнилась, вывода нет, в docker ps пусто. Смотрите по порядку:
docker ps -a --last 3, затем код возврата и журнал.

  docker inspect --format '{{.State.ExitCode}}' <имя>
  docker logs <имя>

Причина почти всегда одна: контейнер живёт ровно столько, сколько живёт
его главный процесс. Чтобы заглянуть внутрь, запустите оболочку:

  docker run --rm -it alpine:3.24 sh

ПРОБЛЕМА: Conflict. The container name "/p2-sleeper" is already in use

  docker: Error response from daemon: Conflict. The container name
  "/p2-sleeper" is already in use by container "5f715bc95f59...".

Имя занято — обычно остатком прошлого запуска; у остановленного
контейнера имя тоже занято (шаг 5). Проверьте и удалите:
  docker rm -f p2-sleeper

ПРОБЛЕМА: docker: 'docker ps' accepts no arguments

Так Docker отвечает, когда в команде потерян дефис: набрано «docker ps a»
вместо docker ps -a. Буква a здесь не флаг, а лишний аргумент, и команда
завершается с кодом 1.

ИСПРАВЛЕНО: эта опечатка была в прежней версии курса, и она дорого
стоила на занятии: студент копировал строку, получал непонятный ответ
и решал, что Docker сломался.

ПРОБЛЕМА: контейнер завершился с кодом 137, а в журнале пусто

SIGKILL не обрабатывается процессом: ядро убивает его мгновенно, буферы
вывода не сбрасываются, и в журнал не попадает ничего. Проверьте флаг
OOMKilled: true — контейнеру не хватило памяти (практика 8). Если false,
процесс получил SIGKILL от docker stop или docker kill: значит,
приложение не обрабатывает SIGTERM (шаг 8).

ПРОБЛЕМА: docker pull отвечает manifest unknown

  Error response from daemon: manifest for alpine:9.99 not found:
  manifest unknown: manifest unknown

Реестр ответил и такого тега у него нет: опечатка в номере версии или
тег снят с публикации. Это не ошибка сети: при проблемах со связью ответ
другой — таймаут или TLS handshake timeout (практика 1).
