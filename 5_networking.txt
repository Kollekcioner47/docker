Практика 5. Порты и сети Docker.

ЭТА ПРАКТИКА — ПРО СЕТЬ. У Docker внутри машины своя сеть: у каждого
контейнера свой адрес, а имена контейнеров разрешает встроенный DNS.
Снаружи видно только то, что вы опубликовали ключом -p. Здесь же чаще
всего и ломается: «контейнер не видит базу», «сайт не открывается».


=========================================================================
ЧТО МЫ СДЕЛАЕМ
=========================================================================

  * опубликуем порт и разберём запись -p 127.0.0.1:8080:80 по частям:
    что здесь адрес машины, что порт машины, а что порт в контейнере;
  * убедимся опытом, что EXPOSE в Dockerfile ничего не публикует;
  * создадим свою сеть: контейнеры находят друг друга по имени, а в сети
    по умолчанию — нет;
  * увидим изоляцию сетей и разберём драйверы bridge, host и none.

ЗАЧЕМ ЭТО НУЖНО: пока приложение одно, сеть незаметна. Как только их
два — приложение и база, — начинаются вопросы: как приложение найдёт
базу, если её адрес меняется при каждом перезапуске; почему с машины
сервис открывается, а с соседнего компьютера нет. Ответы на них дают
команды из этой практики.


=========================================================================
ЧТО ПОНАДОБИТСЯ
=========================================================================

Машина admin, 10.0.2.5 — та же, что и в предыдущих практиках; второй
хост не нужен.

ОБРАЗЫ (скачаются сами, если их ещё нет):

  nginx:1.30-alpine   — сервер: слушает порт 80 и отвечает по HTTP;
  alpine:3.24         — клиент: маленький, внутри есть ping и wget.

Команды практики создают объекты с префиксом p5-: уборка никого
не заденет.

  ВАЖНО: порт публикуем только на петлевой адрес, как в шаге 2: стенд
  курса не защищён, а «на минутку открыть наружу» — плохая привычка.


#########################################################################
ЧАСТЬ 1. БАЗОВАЯ ПРАКТИКА
#########################################################################


=========================================================================
ШАГ 1. СВОЯ СЕТЬ
=========================================================================

Посмотрим, что у Docker уже есть:

  docker network ls

В выводе три сети: bridge, host и none. Они создаются при установке
Docker, и удалить их нельзя. В bridge попадает контейнер, если при
запуске не сказано ничего другого.

Создадим свою сеть — она понадобится со следующего шага:

  docker network create p5-net

Команда печатает длинный идентификатор: он нужен Docker, а нам — имя,
которое мы задали сами. Посмотрим адреса этой сети:

  docker network inspect p5-net --format '{{json .IPAM.Config}}'

  [{"Subnet":"172.18.0.0/16","Gateway":"172.18.0.1"}]

Контейнеры получат адреса из 172.18.0.0/16, а 172.18.0.1 — адрес машины
в этой сети. Подсеть Docker выбирает сам из свободных, поэтому у вас
числа могут быть другие. Запоминать их не нужно: нужна команда, которая
их показывает.

  ПОЧЕМУ ДРАЙВЕР ТОТ ЖЕ, А СЕТЬ ДРУГАЯ: docker network create без ключа
  -d создаёт сеть с драйвером bridge — как у сети по умолчанию. Разница
  не в драйвере, а в том, что это НАША сеть: своё имя, свой DNS.


=========================================================================
ШАГ 2. ПУБЛИКУЕМ ПОРТ: -p 127.0.0.1:8080:80
=========================================================================

Запустим сервер в нашей сети и опубликуем его порт:

  docker run -d \
      --name p5-nginx \
      --network p5-net \
      -p 127.0.0.1:8080:80 \
      nginx:1.30-alpine

  docker ps --format '{{.Names}} {{.Ports}}'

  p5-nginx 127.0.0.1:8080->80/tcp

  curl -I http://127.0.0.1:8080

  HTTP/1.1 200 OK
  Server: nginx/1.30.5

Стрелка в выводе — это и есть публикация: слева порт на машине, справа
порт внутри контейнера. Разберём запись по частям:

  127.0.0.1 — адрес НА МАШИНЕ, на котором открыт порт. Петлевой адрес
    означает «доступен только с самой машины»;
  8080 — порт на машине: именно его набирают в браузере и в curl;
  80 — порт ВНУТРИ контейнера, тот, который слушает nginx. Он задан
    в образе и не меняется.

  ПОЧЕМУ ИМЕННО ТАК: если написать -p 8080:80 — без адреса, — Docker
  откроет порт на 0.0.0.0, на всех интерфейсах машины, и сервис увидит
  весь стенд. Разница в шести символах, и их пишут по привычке.


=========================================================================
ШАГ 3. EXPOSE НИЧЕГО НЕ ПУБЛИКУЕТ
=========================================================================

  docker image inspect nginx:1.30-alpine \
      --format '{{json .Config.ExposedPorts}}'

  {"80/tcp":{}}

Инструкция EXPOSE 80 в Dockerfile только документирует: «слушаю 80».
Запустим такой же сервер, но НЕ будем публиковать ничего:

  docker run -d --name p5-noport --network p5-net nginx:1.30-alpine
  docker ps --filter name=p5- --format '{{.Names}} {{.Ports}}'

  p5-noport 80/tcp
  p5-nginx 127.0.0.1:8080->80/tcp

У p5-noport в колонке PORTS стоит просто 80/tcp, без стрелки: порт
объявлен в образе, но наружу не отдан. Проверим двумя командами:

  docker port p5-noport
  docker inspect p5-noport --format '{{json .NetworkSettings.Ports}}'

  {"80/tcp":null}

Первая не печатает ничего, а null во второй означает «объявлен,
но не опубликован». С машины этот сервер недоступен:

  curl -I http://127.0.0.1:80

  curl: (7) Failed to connect to 127.0.0.1 port 80: Connection refused

  ИСПРАВЛЕНО: в прежней версии курса лекция «Порты контейнеров»
  утверждала, что EXPOSE «позволяет объявить, к какому порту мы можем
  обратиться из основной ОС». Это неверно: EXPOSE только документирует
  порт, а публикует его тот, кто запускает контейнер, ключом -p.

ЗАЧЕМ EXPOSE НУЖЕН: чтобы человек, читающий образ, знал, какой порт
слушает приложение, и чтобы работал ключ -P: он публикует на случайные
порты машины все порты, объявленные в образе.


=========================================================================
ШАГ 4. КЛИЕНТ РЯДОМ: ИМЯ ВМЕСТО АДРЕСА
=========================================================================

  docker run -d \
      --name p5-client \
      --network p5-net \
      alpine:3.24 sleep infinity

Команда sleep infinity нужна, чтобы контейнер не завершился сразу:
alpine без команды запускает оболочку и, не получив ввода, выходит.

  docker exec p5-client ping -c 2 p5-nginx

  PING p5-nginx (172.18.0.2): 56 data bytes
  64 bytes from 172.18.0.2: seq=0 ttl=64 time=0.086 ms
  64 bytes from 172.18.0.2: seq=1 ttl=64 time=0.077 ms

В скобках стоит адрес, в который разрешилось ИМЯ: мы его не знали
и не указывали — его нашёл встроенный DNS Docker. Теперь по HTTP:

  docker exec p5-client wget -q -O - http://p5-nginx | head -2

  <!DOCTYPE html>
  <html>

curl в alpine нет; wget из busybox делает то же самое. Внутри сети
отвечает и сервер без публикации:

  docker exec p5-client wget -q -O - http://p5-noport | head -1

  <!DOCTYPE html>

Кто отвечает за имена внутри контейнера:

  docker exec p5-client cat /etc/resolv.conf

  nameserver 127.0.0.11

127.0.0.11 — встроенный DNS Docker. Он живёт внутри контейнера, знает
имена контейнеров своей сети и отвечает на запросы о них.

  ЗАЧЕМ ЭТО НУЖНО: приложения общаются друг с другом по имени сервиса.
  Адрес контейнера меняется при каждом перезапуске, имя — нет.


=========================================================================
ШАГ 5. В СЕТИ ПО УМОЛЧАНИЮ ИМЯ НЕ РАЗРЕШАЕТСЯ
=========================================================================

  docker run -d --name p5-isolated alpine:3.24 sleep infinity
  docker exec p5-isolated ping -c 1 -W 2 p5-nginx

  ping: bad address 'p5-nginx'

«bad address» означает: имя не разрешилось. Не «нет связи» и не «порт
закрыт» — до попытки соединения дело даже не дошло. Посмотрим, кто
отвечает за имена в этом контейнере:

  docker exec p5-isolated cat /etc/resolv.conf

  nameserver 10.0.2.1

Здесь будет адрес сервера имён вашей машины: числа зависят от стенда.
Адреса 127.0.0.11 в файле нет — и имён контейнеров этот сервер не знает.

  ПОЧЕМУ ТАК: сеть по умолчанию — самая старая часть Docker, её
  поведение сохранили ради совместимости. Встроенный DNS есть только
  у сетей, созданных вами. Нужны имена — создайте свою сеть.


=========================================================================
ШАГ 6. РАЗНЫЕ СЕТИ НЕ ВИДЯТ ДРУГ ДРУГА
=========================================================================

В шаге 5 имя не разрешилось. Проверим, что и по адресу связи нет: адрес
сервера мы видели в выводе ping — 172.18.0.2.

  docker exec p5-isolated ping -c 1 -W 2 172.18.0.2

  --- 172.18.0.2 ping statistics ---
  1 packets transmitted, 0 packets received, 100% packet loss

Это не поломка, а изоляция: сети Docker независимы, и пакет из одной
в другую не ходит, даже если контейнеры на одной машине. Подключить
контейнер к сети можно на ходу, не перезапуская его:

  docker network connect p5-net p5-isolated
  docker exec p5-isolated ping -c 1 -W 2 p5-nginx

  64 bytes from 172.18.0.2: seq=0 ttl=64 time=0.160 ms

Контейнер тот же самый — изменился только состав сетей.

  ВАЖНО: изоляция — это защита, а не препятствие. Контейнеры разных
  приложений на одной машине не видят друг друга, пока вы сами их
  не соедините. Поэтому в Compose каждому приложению делают свою сеть.


=========================================================================
ШАГ 7. УБОРКА
=========================================================================

  docker rm -f p5-nginx p5-noport p5-client p5-isolated
  docker network rm p5-net
  docker ps -a

  ЧЕГО НЕ ДЕЛАТЬ: не пользуйтесь командой docker network prune «чтобы
  наверняка»: она удаляет все сети, к которым не подключён ни один
  контейнер, — в том числе чужие лаборатории и остановленные проекты.


=========================================================================
ШАГ 8. ТОТ ЖЕ СТЕНД ОДНИМ ФАЙЛОМ
=========================================================================

Стенд шагов 1–6 лежит готовым файлом: files/05_networking/app-network.yml.
Compose разбирается в практике 6; наберём его в ~/docker-lab целиком:

  cat > app-network.yml <<'EOF'
  # Лаборатория практики 5 в виде файла Compose.
  #
  # Это тот же стенд, который собирается командами docker в практике: своя
  # сеть, сервер с публикацией на петлевой адрес, клиент рядом и третий
  # контейнер в сети по умолчанию. Подробно Compose разбирается в практике 6.
  #
  # Поля version: в файле нет намеренно: в Compose v2 оно устарело,
  # а версию схема определяется по составу ключей.

  name: p5-lab

  services:

    # Веб-сервер. Он один публикуется наружу, и только на петлевой адрес:
    # приложению учебного стенда незачем слушать все интерфейсы машины.
    web:
      image: nginx:1.30-alpine
      container_name: p5-nginx
      networks:
        - app-net
      ports:
        # Формат «адрес хоста:порт хоста:порт контейнера». Без адреса
        # в начале Docker опубликовал бы порт на 0.0.0.0, то есть на всех
        # интерфейсах машины, включая внешний.
        - "127.0.0.1:8080:80"

    # Клиент в той же сети. Он не публикуется вообще: в этом и смысл —
    # доступ к серверу нужен изнутри сети, а не снаружи.
    client:
      image: alpine:3.24
      container_name: p5-client
      command: ["sleep", "infinity"]
      networks:
        - app-net

    # Третий контейнер — в сети по умолчанию. Он нужен ровно затем, чтобы
    # своими глазами увидеть: в сети bridge имена контейнеров не
    # разрешаются, DNS Docker работает только в сетях, созданных вами.
    isolated:
      image: alpine:3.24
      container_name: p5-isolated
      command: ["sleep", "infinity"]
      # network_mode: bridge — это и есть сеть по умолчанию. Указывать
      # её одновременно в разделе networks нельзя: это разные способы
      # подключения, и Compose на такое сочетание ругается.
      network_mode: bridge

  networks:
    app-net:
      driver: bridge
      # Имя сети задаём явно, иначе Compose соберёт его из имени проекта:
      # p5-lab_app-net. Явное имя удобнее в командах docker network inspect.
      name: p5-net
  EOF

  docker compose -f app-network.yml up -d
  docker exec p5-client ping -c 1 -W 2 p5-nginx

  64 bytes from 172.18.0.2: seq=0 ttl=64 time=0.234 ms

Поведение то же, что в шагах 4 и 5: имена разрешаются в своей сети,
а не в сети по умолчанию (p5-isolated — проверьте сами).

  docker compose -f app-network.yml down

ЧАСТЬ 2. ПРОДОЛЖЕНИЕ: ДРАЙВЕРЫ И ЧАСТЫЕ ОШИБКИ
#########################################################################


=========================================================================
8. ДРАЙВЕРЫ СЕТЕЙ: BRIDGE, HOST, NONE
=========================================================================

BRIDGE — то, чем мы пользовались всю практику. У каждого контейнера
свой адрес и своё сетевое пространство имён, между собой они общаются
через виртуальный коммутатор на машине, а наружу выходят через сеть
машины. Это выбор по умолчанию и правильный выбор почти всегда.

HOST — контейнер работает в сети машины: своих адресов у него нет.

  docker run --rm --network host alpine:3.24 ip -4 addr show

В выводе — интерфейсы самой машины, включая docker0. Порт приложения
занимает порт машины (ключ -p здесь не работает), два контейнера с одним
портом не уживутся, изоляции по сети нет вовсе: стенду это не нужно.

NONE — сети нет: остаётся только петлевой интерфейс.

  docker run --rm --network none alpine:3.24 \
      wget -q -T 2 -O /dev/null http://172.18.0.2

  wget: can't connect to remote host (172.18.0.2): Network unreachable

Так запускают то, чему сеть не нужна: обработку файлов, вычисления,
задачу по расписанию. Обратиться наружу такой контейнер не может, даже
если внутри что-то пойдёт не так.

Остальные драйверы — одной строкой: overlay соединяет контейнеры
на разных машинах и включается только в Swarm (практика 7), macvlan
даёт контейнеру адрес из физической сети.

  ЧЕГО НЕ ДЕЛАТЬ: не берите драйвер host «чтобы не разбираться
  с портами»: это отключает изоляцию и занимает порты машины.


=========================================================================
9. ЧЕГО НЕ ДЕЛАТЬ С ПОРТАМИ И СЕТЯМИ
=========================================================================

  * не публикуйте на 0.0.0.0 то, что не должно быть видно снаружи: базу,
    панель администратора, отладочный порт публикуют на 127.0.0.1;
  * не прописывайте адреса контейнеров в /etc/hosts вручную: это
    работает ровно до первого перезапуска, для этого и есть свой DNS.


=========================================================================
ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
=========================================================================

ПРОБЛЕМА: порт занят, контейнер не запускается

  docker: Error response from daemon: failed to set up container
  networking: driver failed programming external connectivity on
  endpoint p5-nginx: Bind for 127.0.0.1:8080 failed: port is already
  allocated

  1. найдите, кто держит порт: docker ps --filter publish=8080;
  2. это ваш контейнер — удалите его: docker rm -f <имя>. Порт занят
     службой машины — смотрите, кто слушает: sudo ss -tlnp | grep :8080;
  3. возьмите другой порт на машине: -p 127.0.0.1:8082:80.

  Почему так: порт на машине один, и два контейнера не могут слушать
  один и тот же порт одного и того же адреса — как и две обычные
  программы. Контейнер, который не смог запуститься, остаётся
  в состоянии Created: уберите его, иначе имя будет занято.

ПРОБЛЕМА: nginx не стартует — host not found in upstream

  nginx: [emerg] host not found in upstream "p5-nginx-old"
  in /etc/nginx/conf.d/default.conf:4

  Воспроизведём. Создайте в каталоге ~/docker-lab файл upstream.conf:

  cat > upstream.conf <<'EOF'
  server {
      listen 80;
      location / {
          proxy_pass http://p5-nginx-old:80;
      }
  }
  EOF

  Запустите nginx с ним вместо штатного конфига:

  docker run -d --name p5-badproxy \
      -v "$PWD/upstream.conf:/etc/nginx/conf.d/default.conf:ro" \
      nginx:1.30-alpine

  Контейнера в docker ps не будет, а причина видна в журнале:

  docker logs p5-badproxy | tail -2

  Почему так: имя из proxy_pass nginx разрешает при запуске, а не при
  запросе, а такого контейнера в сети нет — стартовать нечему. Имя
  в конфигурации должно совпадать с именем контейнера в той же сети.

  docker rm -f p5-badproxy
  rm upstream.conf

ПРОБЛЕМА: в контейнере не разрешается имя другого контейнера

  ping: bad address 'p5-nginx'

  1. в одной ли сети контейнеры: docker network inspect p5-net
     --format '{{range .Containers}}{{.Name}} {{end}}';
  2. какая сеть у контейнера: docker inspect p5-isolated \
     --format '{{json .NetworkSettings.Networks}}';
  3. кто отвечает за имена: docker exec p5-client cat /etc/resolv.conf —
     здесь должна быть строка nameserver 127.0.0.11; если вместо неё
     адрес сервера имён вашей сети, контейнер в сети по умолчанию;
  4. не опечатка ли в имени: подставляется имя контейнера, а не hostname.

  Почему так: имена контейнеров знает только встроенный DNS Docker,
  а он есть лишь у сетей, созданных вами.

ПРОБЛЕМА: контейнер не видит другой контейнер и по адресу

  1 packets transmitted, 0 packets received, 100% packet loss

  Самая частая причина — контейнеры в разных сетях. Проверьте, что
  адрес взят у того контейнера, к которому вы обращаетесь (он виден
  в выводе ping по имени), и что контейнер запущен: docker ps.

ПРОБЛЕМА: порт объявлен в образе, а снаружи не открывается

  docker port p5-nginx

  Пустой вывод означает, что порт не опубликован: контейнер запущен
  без ключа -p, а в Dockerfile есть только EXPOSE (шаг 3). Если вывод
  не пуст, смотрите адрес публикации:

  docker inspect p5-nginx --format '{{json .NetworkSettings.Ports}}'

  HostIp 127.0.0.1 означает, что порт открыт только с самой машины.
  И помните: снаружи адресов 172.18.0.x не существует.
