=========================================================================
ШАГ 1. КОНТЕЙНЕР — НЕ ПЕСОЧНИЦА
=========================================================================

  docker run --rm alpine:3.24 cat /proc/version
  uname -r

Ответ первой команды — версия ядра вашей машины: своего ядра
у контейнера нет, поэтому строки совпадут. Второй взгляд на то же
самое — со стороны хоста:

  docker run -d --name p12-threat alpine:3.24 sleep 300
  docker top p12-threat

  UID    PID    PPID   C   STIME   TTY   TIME      CMD
  root   3907   3885   0   20:09   ?     00:00:00  sleep 300

Это обычный процесс в списке процессов машины, запущенный от root.

  docker rm -f p12-threat

  изолируется      процессы, сеть, файловая система, хостнейм,
                   ресурсы: память, процессор, число процессов
  не изолируется   ядро — оно общее для хоста и всех контейнеров,
                   часть /proc и /sys, время, сам демон Docker

ЗАЧЕМ ЭТО НУЖНО: изоляция ограничивает, куда может дотянуться
код, но не отменяет прав. Поэтому ядро надо обновлять, а защищать
надо не контейнер, а сокет демона.


=========================================================================
ШАГ 2. СОКЕТ ДЕМОНА И ГРУППА docker
=========================================================================

Только Linux-хост. Сокет демона — это файл:

  ls -l /var/run/docker.sock

  srw-rw---- 1 root docker 0 ... /var/run/docker.sock

Права rw у владельца и у группы, остальным — ничего. Владелец
root, группа docker: вот откуда берётся «доступ без sudo». Кто
может записать команду в сокет, тот может попросить демон сделать
что угодно, а демон работает от root.

  getent group docker
  id -nG

  ВАЖНО: членство в группе применяется при входе в систему:
  добавили пользователя, а он вошёл раньше — docker у него
  по-прежнему попросит sudo (практика 1, шаг 4).

  ЧЕГО НЕ ДЕЛАТЬ: не пробрасывайте сокет демона внутрь
  контейнера: такой контейнер получает те же права, что участник
  группы docker, то есть root на машине. Так готовые панели
  и сборщики становятся точкой входа. Открытый порт 2375 — это
  тот же root, только по сети и без пароля.


=========================================================================
ШАГ 3. НЕ ЗАПУСКАТЬ КОНТЕЙНЕРЫ ОТ ROOT
=========================================================================

  docker run --rm alpine:3.24 id

  uid=0(root) gid=0(root) groups=0(root),1(bin),2(daemon),...

root. Так устроено почти во всех готовых образах: инструкции USER
в Dockerfile нет, а по умолчанию процесс запускается от uid 0.
Запустим от другого пользователя:

  docker run --rm --user 1000:1000 alpine:3.24 id

  uid=1000 gid=1000 groups=1000

ПОЧЕМУ ЭТО ВАЖНО, ЕСЛИ КОНТЕЙНЕР И ТАК ИЗОЛИРОВАН: root внутри —
это root в общем ядре. Если в приложении найдётся уязвимость,
злоумышленник начнёт не с нуля, а с root. Задают пользователя
в образе (практика 10), а проверить его можно так:

  docker inspect <имя> --format '{{.Config.User}}'


=========================================================================
ШАГ 4. ОГРАНИЧЕНИЕ ПРАВ КОНТЕЙНЕРА
=========================================================================

Права root в Linux — это набор отдельных разрешений: cap_chown
разрешает менять владельца файла, cap_sys_admin — монтировать.
Docker выдаёт контейнеру фиксированный набор:

  docker run --rm alpine:3.24 grep Cap /proc/self/status

  CapEff: 00000000a80425fb

Уберём всё:

  docker run --rm --cap-drop ALL alpine:3.24 grep Cap /proc/self/status

  CapEff: 0000000000000000

  docker run --rm --read-only alpine:3.24 touch /test

  touch: /test: Read-only file system

Корень приложению нужен только на чтение, а вредоносный код
пишет туда первым делом. Временные файлы дают точечно:

  docker run --rm --read-only --tmpfs /tmp alpine:3.24 \
      sh -c 'touch /tmp/ok && echo tmpfs-works'

  tmpfs-works

ПОЧЕМУ ИМЕННО ТАК: «сначала убрать всё, потом добавить нужное»
надёжнее, чем «убрать то, что кажется лишним»: второе требует
точно знать, что нужно приложению. Программы вроде sudo и su
повышают права сами, и от них закрывает один флаг:

  docker run --rm --security-opt no-new-privileges:true \
      alpine:3.24 grep NoNewPrivs /proc/self/status

  NoNewPrivs: 1

  ЧЕГО НЕ ДЕЛАТЬ: не добавляйте флаг --privileged, снимающий
  эти ограничения разом, «чтобы заработало»: это отключение
  изоляции, а не «немного больше прав». Кроме capabilities, Docker
  включает фильтр системных вызовов seccomp.


=========================================================================
ШАГ 5. ЧТО ЗАПУСКАЛОСЬ НА МАШИНЕ: СОБЫТИЯ И INSPECT
=========================================================================

У демона есть собственный журнал — поток событий о том, что Docker
делал с контейнерами, образами, сетями и томами. Выход — Ctrl+C,
но для аудита так не годится: события нужно сохранять. Соберём
журнал в файл, выполним несколько действий и посмотрим на него:

  docker events --filter container=p12-events \
      --format '{{.Type}} {{.Action}} {{.Actor.Attributes.name}}' \
      > /tmp/p12-events.log &

  docker run -d --name p12-events alpine:3.24 sleep 60
  docker exec p12-events echo hello
  docker stop p12-events
  docker rm p12-events

  kill %1
  cat /tmp/p12-events.log

  container create p12-events
  container start p12-events
  container exec_create: echo hello p12-events
  container kill p12-events
  container die p12-events
  container destroy p12-events

Это история контейнера от рождения до удаления: видно и то, что
внутрь заходили командой docker exec. Событие kill означает, что
контейнер остановлен: сначала посылается SIGTERM, а если процесс
не вышел — SIGKILL, он же даёт код возврата 137 (практика 2).

  ВАЖНО: журнал событий живёт в памяти демона: после перезапуска
  демона прошлые события пропадают. В событиях нет и имени
  пользователя, создавшего контейнер: на вопрос «кто это сделал»
  отвечает только аудит (шаг 7).


=========================================================================
ШАГ 6. ЖУРНАЛЫ КОНТЕЙНЕРОВ И МЕСТО НА ДИСКЕ
=========================================================================

Отдельно от событий демона есть журналы контейнеров — то, что
приложение печатает в стандартный вывод и поток ошибок.

  docker run -d --name p12-logs alpine:3.24 \
      sh -c 'while true; do echo logline; sleep 1; done'

  docker logs --tail 3 p12-logs
  docker logs --timestamps --tail 2 p12-logs
  docker logs -f p12-logs

Это последние строки, строки с временем и поток -f (выход — Ctrl+C).

Журнал каждого контейнера — обычный файл на хосте:

  docker inspect p12-logs --format '{{.LogPath}}'

  /var/lib/docker/containers/5540e502.../5540e502...-json.log

ПОЧЕМУ БЕЗ ОГРАНИЧЕНИЯ ЖУРНАЛ ЗАПОЛНЯЕТ ДИСК: json-file не удаляет
старые записи, и контейнер, который печатает по строке в секунду,
за месяц накапливает журнал на гигабайты. Первым признаком
становится не ошибка Docker, а «no space left on device» у совсем
другого приложения:

  sudo du -sh /var/lib/docker/containers

Ограничение задаётся при запуске:

  docker run -d --name p12-logs-limited --log-opt max-size=1m \
      --log-opt max-file=2 alpine:3.24 \
      sh -c 'while true; do echo logline; sleep 1; done'

  ВАЖНО: контейнер удалён — журнал удалён вместе с ним. Если
  журнал нужен для разбора, его выгружают заранее.

  docker rm -f p12-logs p12-logs-limited


=========================================================================
ШАГ 7. AUDITD: АУДИТ ХОСТА
=========================================================================

Только Linux-хост. Отвечать на вопросы «что произошло» (шаг 5)
и «что писало приложение» (шаг 6) мы умеем, а на вопрос «кто
именно это сделал» — нет: демон работает от root, а пользователь,
отправивший команду, нигде не сохраняется. Ответ даёт подсистема
аудита ядра Linux.

  sudo apt update
  sudo apt install -y auditd

Правила лежат в /etc/audit/rules.d/, журнал — в
/var/log/audit/audit.log, а правила для Docker — в
files/12_host_security/audit/docker.rules:

  sudo cp files/12_host_security/audit/docker.rules \
      /etc/audit/rules.d/99-docker.rules

  sudo augenrules --load
  sudo auditctl -l | grep docker

  -w /etc/docker -p wa -k docker_config

Наблюдать (-w) за каталогом, срабатывать на запись и изменение
атрибутов (-p wa), помечать событие ключом (-k). Ключ — имя, по
которому событие ищут: без него событие в журнал попадёт, а найти
его будет нечем.

  -a always,exit -F path=/usr/bin/dockerd -F perm=x \
      -F auid>=1000 -F auid!=unset -k docker_exec

Правило срабатывает при запуске программы (-F perm=x). Здесь важно
поле auid — идентификатор того, кто вошёл в систему: в отличие
от uid, он сохраняется при sudo. Если engineer повысил права
и запустил dockerd, в событии будет видно auid engineer. Третье
правило наблюдает за сокетом: -w /run/docker.sock -p rwa
-k docker_socket.

  sudo ausearch -k docker_config -ts recent
  sudo ausearch -k docker_exec -ts today -i

Опция -i переводит номера uid и gid в имена, -ts задаёт начало
периода. Проверить правила можно сразу: создайте файл в
наблюдаемом каталоге (sudo touch /etc/docker/p12-audit-test) и
поищите событие — потом удалите файл.

  ЗАЧЕМ ЭТО НУЖНО: аудит настраивают до происшествия, а не после.
  Если правила добавлены сегодня, про события вчерашней ночи они
  ничего не знают.

8. ОТКУДА ВЗЯЛСЯ ЭТОТ КОНТЕЙНЕР
=========================================================================

Утро понедельника: на машине admin работает контейнер, которого
никто не признаёт своим, а в списке он появился в выходные.

ПРАВИЛО ПЕРВОЕ: НЕ УДАЛЯТЬ — docker rm уничтожит журнал
и связь событий, а остановить контейнер можно.

  docker stop p12-suspicious

  docker run -d --name p12-suspicious \
      --label owner=unknown --label created_by=script \
      alpine:3.24 sleep 600

  docker inspect p12-suspicious --format '
  Создан: {{.Created}}
  Запущен: {{.State.StartedAt}}
  Метки: {{json .Config.Labels}}
  Пользователь: {{if .Config.User}}{{.Config.User}}{{else}}(root){{end}}'

  Создан: 2026-09-23T21:01:09.852904859Z
  Запущен: 2026-09-23T21:01:15.377860550Z
  Метки: {"created_by":"script","owner":"unknown"}

Метка created_by=script говорит, что контейнер создан не руками,
а разница между «создан» и «запущен» показывает, ждал ли он
своего часа. Пустой пользователь означает root.

  docker events --filter container=p12-suspicious \
      --format '{{.Time}} {{.Action}}'
  docker logs --tail 100 p12-suspicious
  docker diff p12-suspicious

docker diff показывает, какие файлы в контейнере изменились.

КТО ЭТО СДЕЛАЛ: ни inspect, ни events не хранят пользователя
хоста, ответ даёт журнал аудита:

  sudo ausearch -k docker_exec -ts today -i
  sudo ausearch -k docker_socket -ts today

Что закрыть после разбора: сокет демона, проброшенный в другой
контейнер; доступ постороннего к машине; учётную запись в группе
docker, которой там быть не должно; чужой образ (практика 10).

  docker rm -f p12-suspicious

=========================================================================
ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
=========================================================================

ПРОБЛЕМА: после ужесточения приложение упало с ошибкой прав

  «operation not permitted» — не хватает capability, добавьте её
  флагом --cap-add.
  «Read-only file system» — приложение пишет в свой корень, а мы
  включили --read-only. Решение: том (практика 4) или --tmpfs.
  «sudo: effective uid is not 0» — следствие no-new-privileges.

ПРОБЛЕМА: ausearch ничего не находит, хотя события были

  * работает ли служба: systemctl status auditd;
  * загружены ли правила: sudo auditctl -l | grep docker (пустой
    вывод — файла нет в /etc/audit/rules.d или не выполнен
    augenrules --load);
  * не истекло ли окно: -ts recent — это последние десять минут,
    для старых событий укажите период: -ts today;
  * опечатка в ключе: grep -n docker_config
    files/12_host_security/audit/docker.rules.

Самая частая причина — в правиле пропущен ключ -k: событие
в журнал попадает, а привязать его не к чему.

ПРОБЛЕМА: журнал аудита растёт и занимает диск

Признак — строка «audit: backlog limit exceeded»: события
потеряны, и в журнале будет пробел. Проверьте сводку по событиям
(sudo aureport --summary), ротацию в /etc/audit/auditd.conf
(max_log_file, num_logs) и список наблюдаемых каталогов: одно
правило для /var/lib/docker даёт тысячи событий за сборку образа.

  ЧЕГО НЕ ДЕЛАТЬ: не настраивайте logrotate для журнала auditd:
  служба держит файл открытым, и переименование под работающей
  службой приводит к потере событий.

ПРОБЛЕМА: docker events не показывает события за нужный период

  1. сравните время на хосте и внутри контейнера: date -u
     и docker run --rm alpine:3.24 date -u. Расхождение в часы
     означает, что окно ушло в будущее или в прошлое;
  2. не перезапускался ли демон: журнал событий живёт в памяти,
     после перезапуска история начинается заново;
  3. проверьте фильтр: опечатка в имени контейнера даёт пустой
     вывод без сообщения об ошибке. Пустой docker logs при живом
     контейнере означает драйвер none, вывод в файл внутри
     контейнера (практика 4) или убитый из-за памяти процесс.
