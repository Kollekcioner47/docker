Практика 10. Безопасность образов и уязвимости.

ЭТА ПРАКТИКА — ПРО ЧУЖОЙ КОД, КОТОРЫЙ ВЫ ЗАПУСКАЕТЕ.
Образ из интернета — это не только ваше приложение: внутри чужие
пакеты и чужое решение о том, от какого пользователя они работают.


=========================================================================
ЧТО МЫ СДЕЛАЕМ
=========================================================================

Три источника риска, и все три разберём командами:

  * УЯЗВИМОСТИ В ПАКЕТАХ. Чем больше пакетов, тем больше находок:
    в ubuntu:24.04 их 92, в alpine:3.24 — 16;

  * ЛИШНИЕ ПРАВА. По умолчанию процесс в контейнере работает
    от root, а приложению root обычно не нужен;

  * ПОДМЕНА ОБРАЗА. Тег можно переставить на другой образ:
    разворачивая по тегу, вы не знаете, что именно запустили.

Порядок: состав образа → сборка двух образов → скан → дайджест.


=========================================================================
ЧТО ПОНАДОБИТСЯ
=========================================================================

  * машина admin — 10.0.2.5, Docker из практики 1;

  * интернет: скачать образы и один раз — базу уязвимостей для
    сканера, около 60 МБ. Первый запуск — минуты, дальше секунды;

  * около 2 ГБ места: антипример весит 660 МБ; каталог
    files/10_image_security с двумя Dockerfile и приложением.
    Скриптов там нет — команды вы набираете сами.

=========================================================================
ШАГ 1. ЧТО ЛЕЖИТ ВНУТРИ ОБРАЗА
=========================================================================

  docker image ls alpine:3.24
  docker image ls ubuntu:24.04

  docker run --rm --entrypoint sh alpine:3.24 -c 'apk info | wc -l'
  docker run --rm --entrypoint sh ubuntu:24.04 \
      -c 'dpkg -l | grep -c "^ii"'

Alpine — 8.42MB и 16 пакетов, Ubuntu — 78.2MB и 92 пакета. Разница
в пять раз, и вся она в том, по чему сканер считает уязвимости.

Из чего образ собран, видно в истории сборки:

  docker image history python:3.13-slim

Команда печатает слои с размерами и текстом инструкции. Запомните
свойство: СЛОЙ НЕЛЬЗЯ УБРАТЬ ПОСЛЕ ФАКТА — файл, удалённый
в следующем слое, остаётся в нижнем, а сверху появляется только
метка «здесь его нет». В шаге 2 мы это увидим на живом примере.


=========================================================================
ШАГ 2. СОБИРАЕМ ЗАЩИЩЁННЫЙ ОБРАЗ
=========================================================================

  cd files/10_image_security
  ls -l

В каталоге два Dockerfile и приложение app/app.py — программа
на стандартной библиотеке Python, без зависимостей. Оба образа
собираются из одного кода: всё различие создаёт сборка.

  docker build -f Dockerfile.hardened -t p10-hardened:1.0 .

Флаг -f указывает имя файла: их в каталоге два. Главное в файле:
минимальная база python:3.13-slim, многоэтапная сборка, удалённый
установщик пакетов, запуск от пользователя.

  docker run --rm --entrypoint sh p10-hardened:1.0 -c 'command -v pip'

Ответа нет, код возврата 1 — установщика в образе нет. Размер
при этом не изменился:

  docker image ls p10-hardened:1.0
  docker image ls python:3.13-slim

Оба — 118MB: удаление файла в новой инструкции RUN образ
не уменьшает, файлы остаются в нижнем слое. Смысл не в размере,
а в том, что можно запустить: находок у p10-hardened 156 против
159 у python:3.13-slim, и разница в три находки — это pip.

  docker run --rm --entrypoint id p10-hardened:1.0
  → uid=10001(app) gid=10001(app) groups=10001(app)

  docker inspect p10-hardened:1.0 --format '{{.Config.User}}'
  → 10001:10001

  ВАЖНО: смотрят именно это поле образа, а не запущенный
  процесс. Если оно пустое или равно root, политики допуска
  в кластере такой образ не пропустят.


=========================================================================
ШАГ 3. АНТИПРИМЕР: ТО ЖЕ САМОЕ, НО КАК ОБЫЧНО
=========================================================================

  docker build -f Dockerfile.insecure -t p10-insecure:1.0 .

Второй образ собран так, как делают чаще всего: «чтобы всё
работало и было удобно». Во время сборки сборщик предупреждает:

  SecretsUsedInArgOrEnv: Do not use ARG or ENV instructions for
  sensitive data (ENV "API_TOKEN")

Он видит секрет в инструкции ENV: такой образ нельзя отдавать
наружу. Дальше — проверки по пунктам.

ПОЛНЫЙ UBUNTU И ВСЁ «ЧТО МОЖЕТ ПРИГОДИТЬСЯ»:

  docker image ls p10-insecure:1.0

  660MB против 118MB, пакетов 244 против 87. Одной командой
  установлены python3, pip, gcc, make, git, curl, vim и netcat —
  этот слой сборки весит 559MB.

ПРОЦЕСС РАБОТАЕТ ОТ ROOT, ИНСТРУМЕНТЫ ОСТАЮТСЯ ВНУТРИ:

  docker run --rm --entrypoint id p10-insecure:1.0
  → uid=0(root) gid=0(root) groups=0(root)

  docker inspect p10-insecure:1.0 --format '{{.Config.User}}'

  Поле пустое — значит, root. Программа одна и та же, а права
  разные: уязвимость, через которую можно выполнить свой код,
  в первом случае даёт uid 10001, во втором — root.

  docker run --rm --entrypoint sh p10-insecure:1.0 \
      -c 'ls -l /usr/bin/gcc /usr/bin/git /usr/bin/curl'

  Все три на месте. Для того, кто попадёт внутрь, gcc и git —
  готовый набор инструментов.

ЧЕГО НЕ ДЕЛАТЬ: не копируйте из Dockerfile.insecure ни строки.
Он лежит в курсе ради чисел: 660MB против 118MB, uid 0 против
uid 10001, три тысячи находок против полутора сотен.


=========================================================================
ШАГ 4. СКАНИРУЕМ ОБРАЗЫ
=========================================================================

Сканер поставим контейнером: на стенде ничего не устанавливается,
а версия закреплена тегом.

  docker save p10-hardened:1.0 -o /tmp/p10-hardened.tar
  docker run --rm \
      -v /tmp:/work:ro \
      -v p10-trivy-cache:/root/.cache/trivy \
      aquasec/trivy:0.71.2 image \
          --input /work/p10-hardened.tar \
          --severity HIGH,CRITICAL --no-progress

--input заставляет сканер читать файл образа, а не обращаться
к демону Docker: контейнеру со сканером тогда не нужен сокет,
а сокет — это права root на машине (практика 12). Том
p10-trivy-cache хранит базу уязвимостей, --severity выбирает
уровни (CRITICAL, HIGH, MEDIUM, LOW, UNKNOWN).

Первый запуск занимает несколько минут, дальше — секунды.
В конце отчёта сканер печатает:

  Total: 44 (HIGH: 44, CRITICAL: 0)

Для антипримера команда та же: сохранить p10-insecure:1.0
и назвать его в --input.

Числа, полученные на стенде (Docker 28.5.1, Trivy 0.71.2):

  ОБРАЗ              РАЗМЕР    ПАКЕТОВ   CRITICAL  HIGH
  -----------------  --------  --------  --------  ----
  alpine:3.24        8.42MB    16        0         0
  ubuntu:24.04       78.2MB    92        0         0
  python:3.13-slim   118MB     87        0         46
  p10-hardened:1.0   118MB     87        0         44
  p10-insecure:1.0   660MB     244       4         86

Сравните первые три строки: ubuntu:24.04 меньше python:3.13-slim
и даёт ноль находок уровня HIGH против 46. Причина не в размере,
а в том, когда образ обновляли: исправления выходят каждый день,
поэтому сравнивать базовые образы можно только в один день и на
одних версиях. По всем уровням у антипримера 3160 находок против
156, при одном и том же приложении.


=========================================================================
ШАГ 5. КАК ЧИТАТЬ ОТЧЁТ СКАНЕРА
=========================================================================

В таблице отчёта важны четыре столбца: Vulnerability — номер
записи в базе (CVE), Severity — уровень (CRITICAL, HIGH, MEDIUM,
LOW), Status — что с исправлением (affected, fix_deferred,
fixed), Fixed Version — версия с исправлением или пусто.

Посмотрите на номера внимательно: они повторяются. Из исходного
пакета util-linux собирается девять бинарных пакетов — util-linux,
mount, login, libuuid1, libblkid1, libmount1, libsmartcols1,
liblastlog2-2 и bsdutils. Каждый получает все уязвимости
исходного пакета.

  ВАЖНО: 44 записи в отчёте — это 8 разных CVE. «44 уязвимости»
  и «8 уязвимостей» сказано про один и тот же образ. Ошибка
  в прочтении отчёта встречается чаще, чем всё остальное.

Все 44 записи у защищённого образа без исправления: 43 affected
и одна fix_deferred, ни одной fixed. Ключ --ignore-unfixed
в той же команде оставит только исправимое, и находок не
останется вовсе — для конвейера это самая практичная настройка.

ПОЧЕМУ СЧЁТЧИК НЕ РАВЕН РИСКУ

  * 44 записи — это 8 CVE, а не 44 проблемы;
  * исправлений нет ни для одной из них, значит делать нечего;
  * уязвимость в perl-base приложению на Python безразлична:
    perl тянет за собой apt.

У антипримера все 90 находок уровня HIGH и CRITICAL — в одном
пакете linux-libc-dev: это заголовочные файлы ядра, оставшиеся
в образе от компилятора gcc. В работающем контейнере их нет.

Отсюда правило: СЧЁТЧИК ИЗ ОТЧЁТА — ЭТО СПИСОК ПОВОДОВ
ПОСМОТРЕТЬ, А НЕ ОЦЕНКА РИСКА. Смотреть надо на три вещи:
уникальные номера вместо строк, наличие исправления и использует
ли приложение тот пакет, где нашли уязвимость.


=========================================================================
ШАГ 6. ТЕГ И ДАЙДЖЕСТ
=========================================================================

Тег — это указатель, и его можно переставить:

  docker tag alpine:3.24 p10-demo:1.0
  docker image ls p10-demo
  → p10-demo  1.0  320994c3b997  8.42MB

  docker tag ubuntu:24.04 p10-demo:1.0
  docker image ls p10-demo
  → p10-demo  1.0  6232b3879100  78.2MB

Тег тот же, а образ за ним другой. Автор образа может пересобрать
его и переставить тег — тогда завтра по тому же имени приедет
другое содержимое.

Дайджест — отпечаток содержимого, он считается от манифеста
и потому не меняется:

  docker inspect --format '{{index .RepoDigests 0}}' alpine:3.24
  → alpine@sha256:294b683cb724975bec92580e1e685676bd4b50bda...

Подменить образ, загруженный по дайджесту, нельзя: другое
содержимое даст другой дайджест, и загрузка не найдёт манифест.
Поэтому в Dockerfile и в файле Compose рядом с именем образа
указывают дайджест целиком, без сокращений:

  FROM python:3.13-slim@sha256:<дайджест образа>

Цена закрепления — обновления перестают приходить сами: тег
python:3.13-slim со временем начнёт указывать на пересобранный
образ с исправлениями, а дайджест — нет. Поэтому в работе
закрепляют по дайджесту и отдельно следят за новыми версиями.

  ВАЖНО: у локально собранного образа дайджеста нет — он
  появляется только после отправки в реестр (практика 11).
  Попробовав закрепить свежесобранный образ, вы упрётесь
  именно в это.

Уберём за собой:

  docker rmi p10-demo:1.0
  rm -f /tmp/p10-hardened.tar /tmp/p10-insecure.tar

=========================================================================
7. ЗАЩИЩЁННЫЙ ОБРАЗ В РАБОТЕ
=========================================================================

  docker run -d --name p10-run --publish 127.0.0.1:18080:8080 \
      p10-hardened:1.0

Публикация записана как 127.0.0.1:18080:8080, а не 18080:8080:
так порт открыт только на самой машине, а не для всей сети.
Приложение само сообщает, от кого работает:

  curl -s http://127.0.0.1:18080/whoami
  → {"uid": 10001, "gid": 10001, "pid": 1, "is_root": false,
     "version": "1.0"}

Это не украшение: в минимальном образе команды id может не быть,
и спросить приложение — единственный способ узнать ответ.

  docker inspect p10-run --format '{{.State.Health.Status}}'
  → healthy

  docker logs p10-run
  → start uid=10001 gid=10001 version=1.0
    GET /whoami

Первой строкой приложение печатает uid процесса: работай оно
от root, это было бы видно сразу.

ПОЧЕМУ ИМЕННО ТАК: пользователя можно назначить и при запуске,
не меняя образ:

  docker run --rm --user 10001:10001 alpine:3.24 touch /root/test
  → touch: /root/test: Permission denied

Это и есть изоляция: прав на каталог root у процесса нет.
Вторая сторона: приложению, которое пишет файлы, каталог должен
принадлежать тому же uid — создайте его в Dockerfile с chown
или запускайте контейнер с --user $(id -u):$(id -g).

  docker rm -f p10-run


=========================================================================
8. DOCKER SCOUT: ВТОРОЙ СКАНЕР
=========================================================================

Trivy — не единственный сканер: Docker Scout входит в состав
Docker CLI.

  docker scout quickview alpine:3.24
  docker scout cves python:3.13-slim
  docker scout recommendations python:3.13-slim

Часть возможностей Scout работает как сервис Docker Hub, поэтому
без учётной записи команды отвечают так:

  Log in with your Docker ID or email address to use docker scout.

Это ограничение инструмента, а не ошибка установки. Для занятий
основной сканер — Trivy: он работает локально, без учётной записи
и без отправки чего-либо наружу. А recommendations полезнее
всего тем, что подсказывает, какую версию базового образа взять.

  ИСПРАВЛЕНО: в прежней версии курса сканирование показывали
  командой docker scan. Такой команды больше нет — Docker
  отвечает «unknown command: docker scan», а статьи с ней
  устарели.


=========================================================================
9. СКАНЕР В КОНВЕЙЕРЕ И РЕГУЛЯРНАЯ ПРОВЕРКА
=========================================================================

Порядок в сборочном конвейере такой:

  СБОРКА  →  СКАН  →  ПУБЛИКАЦИЯ

Скан после публикации бессмыслен: уязвимый образ уже в реестре.
Скан до сборки невозможен: проверяются пакеты внутри образа.
Останавливает конвейер код возврата — ключ --exit-code 1
заставляет сканер вернуть 1, если находки есть.

Второе: сканировать надо и по расписанию. Образ не меняется,
а база уязвимостей обновляется каждый день, и вчерашний «чистый»
образ сегодня может оказаться уязвимым.

Рядом стоит подпись образа (cosign): она отвечает на вопрос
«то ли это, что я собрал», а не «что внутри». Подробно —
в практике 11. И ещё одно, о чём достаточно знать: distroless —
образы без shell и без менеджера пакетов: находок меньше,
но зайти внутрь для отладки нечем.


=========================================================================
ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
=========================================================================

ПРОБЛЕМА: сборка падает с ошибкой про файл приложения

  ERROR: failed to build: failed to solve: failed to compute
  cache key: failed to calculate checksum of ref ...:
  "/app/app.py": not found

Docker берёт файлы из контекста сборки — каталога, указанного
последним аргументом docker build. Проверьте: сборка идёт
из каталога files/10_image_security, а не из корня курса;
в каталоге есть app/app.py; путь в COPY указан от контекста.

ПРОБЛЕМА: сканер не находит файл образа

  FATAL  Fatal error  run error: ... unable to open /work/nope.tar
  as a Docker image: unable to open the file: open /work/nope.tar:
  no such file or directory

Причина одна из двух: не выполнен docker save или имя файла
в --input не совпадает с сохранённым. Проверьте, что файл есть
(ls -lh /tmp/*.tar), что каталог смонтирован (-v /tmp:/work:ro)
и что путь внутри контейнера начинается с /work/, а не с /tmp/.

ПРОБЛЕМА: приложение не может писать файлы

  PermissionError: [Errno 13] Permission denied: '/app/data.db'

Это следствие работы от непривилегированного пользователя,
и это правильное поведение: каталог принадлежит root. Что делать,
по возрастанию аккуратности: создать каталог данных в Dockerfile
и отдать его приложению (RUN mkdir -p /app/data && chown
10001:10001 /app/data); запускать контейнер с --user $(id -u):$(id -g);
а если пишутся только временные файлы — --tmpfs /tmp.

ЧЕГО НЕ ДЕЛАТЬ: возвращать USER root, «чтобы заработало».
Проблема не в пользователе, а в правах на каталог.

ПРОБЛЕМА: docker scout отвечает, что нужно войти

  Log in with your Docker ID or email address to use docker scout.

Проверьте, установлен ли Scout (docker scout version) и выполнен
ли вход (docker login). Для локального сканирования есть Trivy.
