Практика 6. Docker Compose.

ЭТА ПРАКТИКА — ПРО ПРИЛОЖЕНИЕ ЦЕЛИКОМ. До сих пор параметры
контейнера жили в голове и в истории команд. Здесь они переезжают
в файл, а контейнеры запускаются вместе — как одно приложение.


=========================================================================
ЧТО МЫ СДЕЛАЕМ
=========================================================================

Приложение «Заметки»: веб-часть на Flask и база PostgreSQL. Оба сервиса
описаны одним файлом docker-compose.yml рядом с кодом и поднимаются
одной командой.

Разберём ключи services, image, build, ports, environment, volumes,
depends_on, restart и healthcheck, переменные и .env, а ещё то, почему
depends_on не гарантирует готовность базы и что удаляет down -v.

ЧТО ПОНАДОБИТСЯ

Машина admin (10.0.2.5) со стендом из практики 1; узлы node1 и node2
НЕ НУЖНЫ — Compose работает на одной машине. Проверить:

  docker compose version

Файлы практики скопируйте на машину вместе с курсом:

  mkdir -p ~/docker-lab
  cp -r <курс>/files/06_compose ~/docker-lab/
  cd ~/docker-lab/06_compose/notes

Приложение публикуется на 8080; если порт занят (например, остался
контейнер из практики 5), он меняется в .env — это шаг 4.

=========================================================================
ШАГ 1. ФАЙЛ ВМЕСТО КОМАНДНОЙ СТРОКИ
=========================================================================

  ls -R

  .env.example           образец значений переменных
  docker-compose.yml     описание приложения: что собрать и запустить
  app/                   код приложения и его Dockerfile

ПОЧЕМУ ИМЕННО ТАК, А НЕ ФЛАГАМИ: флаг командной строки нельзя
проверить, не запустив контейнер. Compose разбирает файл и показывает,
что получится, ничего не запуская:

  docker compose config

  name: notes
  services:
    web:
      ports:
        - published: "8080"
          target: 5000
      depends_on:
        db:
          condition: service_healthy

Проверить тут стоит три вещи: переменная NOTES_PORT подставилась;
относительный путь ./app превратился в абсолютный; зависимость записана
с условием.

ЧТО МЫ СОБИРАЕМСЯ ЗАПУСКАТЬ

В каталоге app/ три файла, и два из них стоит набрать вместе
с преподавателем: своё приложение понятнее чужого. Умеет оно две вещи:
сохранить заметку в базу и показать список; третий адрес, /healthz,
нужен Compose для проверки работоспособности (шаг 6).

Вот код приложения, app/app.py. Параметры базы он берёт из переменных
окружения (шаг 4), а её адрес — db, то есть имя сервиса (шаг 3):

  #!/usr/bin/env python3
  """Приложение «Заметки»: Flask и PostgreSQL (практика 6)."""

  import os

  import psycopg
  from flask import Flask, redirect, render_template_string, request, url_for

  app = Flask(__name__)

  DB = {
      "host": os.environ.get("POSTGRES_HOST", "db"),
      "port": os.environ.get("POSTGRES_PORT", "5432"),
      "dbname": os.environ.get("POSTGRES_DB", "notes"),
      "user": os.environ.get("POSTGRES_USER", "notes"),
      "password": os.environ.get("POSTGRES_PASSWORD", ""),
  }

  PAGE = """<h1>Заметки</h1>
  <form method="post"><input name="note" placeholder="Новая заметка" required>
  <button type="submit">Добавить</button></form>
  <ul>{% for note in notes %}<li>{{ note }}</li>{% endfor %}</ul>
  """


  @app.route("/", methods=["GET", "POST"])
  def index():
      with psycopg.connect(**DB) as conn:
          conn.execute("CREATE TABLE IF NOT EXISTS notes (content text)")
          if request.method == "POST":
              conn.execute("INSERT INTO notes (content) VALUES (%s)",
                           (request.form["note"],))
              return redirect(url_for("index"))
          notes = conn.execute("SELECT content FROM notes").fetchall()
      return render_template_string(PAGE, notes=notes)


  @app.route("/healthz")
  def healthz():
      try:
          with psycopg.connect(**DB) as conn:
              conn.execute("SELECT 1")
      except psycopg.Error:
          return "database error\n", 503
      return "ok\n"


  if __name__ == "__main__":
      app.run(host="0.0.0.0", port=int(os.environ.get("PORT", "5000")))

А это файл сборки, app/Dockerfile:

  FROM python:3.13-slim

  ENV PYTHONDONTWRITEBYTECODE=1 \
      PYTHONUNBUFFERED=1

  WORKDIR /app
  COPY requirements.txt ./
  RUN pip install --no-cache-dir -r requirements.txt
  COPY app.py ./

  # Процесс работает не от root, а каталог /app принадлежит root: писать
  # туда он не может, поэтому выше и стоит PYTHONDONTWRITEBYTECODE.
  RUN useradd --create-home --uid 1000 appuser
  USER appuser

  EXPOSE 5000
  CMD ["python", "app.py"]

Третий файл, app/requirements.txt, набирать не нужно — там Flask
и psycopg.

ЧТО В ЭТОМ DOCKERFILE ВАЖНО

Собран он по правилам практики 3: тег базового образа закреплён,
зависимости копируются до кода — слой с pip install пересобирается
только при изменении requirements.txt, а не при каждой правке app.py.

  * PYTHONDONTWRITEBYTECODE нужен из-за работы не от root: каталог /app
    принадлежит root, и без этой переменной питон на каждом запросе
    пытается писать туда __pycache__ и оставляет ошибку в журнале;
  * PYTHONUNBUFFERED — чтобы вывод не буферизовался: иначе
    docker compose logs молчит, пока не заполнится буфер;
  * USER appuser: процессу в контейнере root не нужен, uid 1000
    достаточно, а root ослабляет изоляцию (практика 10). Проверить,
    от кого работает контейнер: docker compose exec web id;
  * CMD записан в exec-форме: сигнал остановки (docker compose stop)
    уходит самому процессу Python, а не промежуточной оболочке, иначе
    контейнер убивают по таймауту.


=========================================================================
ШАГ 2. УСТРОЙСТВО ФАЙЛА COMPOSE
=========================================================================

Файл Compose — обычный YAML, и в нём важны отступы: они задают
вложенность, а табуляция запрещена — Docker ответит ошибкой разбора.

Разделы верхнего уровня: services (что запускаем, обязательный),
volumes (тома), networks (сети), secrets и configs; плюс необязательное
поле name — имя проекта. В нашем файле два раздела: services и volumes.

  ИСПРАВЛЕНО: раньше поле version было обязательным, а команда
  называлась docker-compose, через дефис. Это Compose v1, снятый
  с поддержки в 2023 году. Сейчас Compose — плагин, команда пишется
  через пробел, а схема файла определяется по его составу; version
  вызывает предупреждение «the attribute version is obsolete».

ЧТО БЫВАЕТ В СЕРВИСЕ

  image          готовый образ из реестра: postgres:18-alpine
  build          собрать образ на месте: context — каталог сборки
  ports          опубликовать порт на машину: «хост:контейнер»
  environment    переменные окружения внутри контейнера
  volumes        тома и привязки каталогов
  depends_on     порядок запуска относительно других сервисов
  restart        что делать, когда контейнер завершился
  healthcheck    как проверить, что сервис работоспособен

IMAGE ИЛИ BUILD. image — «возьми готовый образ» (postgres:18-alpine),
build — «собери на месте» плюс context: каталог сборки. Своего image
у приложения нет, поэтому Compose назовёт образ notes-web.

ПОРТЫ. Запись "8080:5000" означает «порт 8080 на машине — порт 5000
в контейнере»; слева всегда то, что снаружи. Перепутать легко, а ошибка
проявляется как «порт занят» или «приложение недоступно».

ПЕРЕМЕННЫЕ. ${ИМЯ:-значение} — значение по умолчанию, если переменной
нет; ${ИМЯ:?текст} — переменная обязательна, и Compose напечатает этот
текст вместо запуска. Двойной $$ в healthcheck означает «оставь как
есть»: одиночный $ Compose подставил бы сам, из .env.

RESTART. В файле стоит restart: unless-stopped: упавший сервис Docker
поднимет сам, а остановленный вами вручную останется остановленным
(разница с always — практика 2).

  ЧЕГО НЕ ДЕЛАТЬ: не добавлять version: и не писать пароли прямо
  в файл — только ${ПЕРЕМЕННАЯ} из .env, а в работе секреты.

ШАГ 3. ПЕРВЫЙ ЗАПУСК
=========================================================================

  cp .env.example .env

Что там написано и почему — шаг 4. Пока важно, что файл нужен: без
него Compose откажется запускаться.

  docker compose config

  docker compose up -d --build

Ключ -d означает «в фоне», --build — «собери образ перед запуском»:

  Network notes_default  Created
  Volume notes_pgdata  Created
  Container notes-db-1  Started
  Container notes-db-1  Waiting
  Container notes-db-1  Healthy
  Container notes-web-1  Started

Сеть notes_default Compose создал сам: у каждого проекта есть сеть
по умолчанию, и адрес базы для приложения — просто db (практика 5).
Том notes_pgdata будет хранить данные базы (шаг 7), а строки Waiting
и Healthy означают, что Compose дождался healthcheck базы (шаг 6).

  docker compose ps

  NAME          IMAGE                SERVICE   STATUS
  notes-db-1    postgres:18-alpine   db        Up 22 seconds (healthy)
  notes-web-1   notes-web            web       Up 11 seconds (healthy)

Столбец PORTS сокращён: у web там 0.0.0.0:8080->5000/tcp, у db —
5432/tcp. Проверим приложение:

  curl -s http://localhost:8080/healthz
  ok

  curl -s -X POST --data-urlencode 'note=Первая заметка' \
      http://localhost:8080/ -o /dev/null -w '%{http_code}\n'
  302

  curl -s http://localhost:8080/ | grep -o 'Первая заметка'
  Первая заметка

Код 302 — перенаправление: форму приняли и вернулись на ту же страницу.
В браузере приложение открывается по адресу http://10.0.2.5:8080/.


=========================================================================
ШАГ 4. ПЕРЕМЕННЫЕ И .ENV
=========================================================================

Compose читает .env из того каталога, где лежит docker-compose.yml.
Подключать его не нужно: значения подставляются в записи вида ${ИМЯ}.

  ports:
    - "${NOTES_PORT:-8080}:5000"
  environment:
    POSTGRES_DB: "${POSTGRES_DB:-notes}"

Здесь три части: значение переменной; значение по умолчанию после :-;
двоеточие с портом 5000, к переменным не относящееся. Значения ищутся
по порядку: переменная окружения в оболочке → файл .env → значение
по умолчанию, поэтому для разовой проверки .env не правят:

  NOTES_PORT=8081 docker compose up -d

В репозитории курса лежит только .env.example — образец. Рабочий .env
создаётся копированием и в репозиторий не попадает: в нём пароли
стенда, а попав в историю git, они остаются там навсегда (практика 9).
Пробелы вокруг знака равенства попадут в значение: NOTES_PORT = 8080
задаст не 8080, а « 8080».

  ВНИМАНИЕ: docker compose config печатает и секреты — те, что
  подставились из .env. Не выкладывайте её вывод в переписку.


=========================================================================
ШАГ 5. КОМАНДЫ COMPOSE: ЖИЗНЕННЫЙ ЦИКЛ
=========================================================================

  docker compose up -d               создать и запустить всё
  docker compose up -d --build       то же, но сначала пересобрать
  docker compose ps                  контейнеры проекта
  docker compose ps -a               включая остановленные
  docker compose logs                журналы всех сервисов
  docker compose logs -f web         следить за журналом сервиса
  docker compose logs --tail=20 web  последние 20 строк
  docker compose stop                остановить, ничего не удаляя
  docker compose start               запустить остановленное
  docker compose restart web         перезапустить сервис
  docker compose down                удалить контейнеры и сеть
  docker compose down -v             ещё и тома проекта
  docker compose ls                  список проектов на машине

  EXEC И RUN: В ЧЁМ РАЗНИЦА

    docker compose exec web id        в УЖЕ ЗАПУЩЕННОМ контейнере
    docker compose run --rm web ...   новый контейнер на один раз

  exec подключается к работающему процессу — так смотрят состояние
  и открывают оболочку; run по умолчанию порты не публикует, иначе
  второй контейнер конфликтовал бы с первым за порт:

    docker compose exec web id
    uid=1000(appuser) gid=1000(appuser) groups=1000(appuser)

  ИСПРАВЛЕНО: базу в учебных примерах часто публикуют на хост «чтобы
  подключаться из клиента» — строкой вида 5432:5432 в сервисе db.
  После этого база доступна всей сети, и её защищает только пароль.
  Заходить в базу нужно изнутри: docker compose exec db psql -U notes
  -c 'select content from notes;'

РАЗНИЦА МЕЖДУ STOP И DOWN: stop оставляет контейнеры на машине вместе
с сетью и томом (start вернёт всё как было), down удаляет контейнеры
и сеть, а тома и образы остаются, если не добавить -v.

=========================================================================
ШАГ 6. DEPENDS_ON НЕ ЖДЁТ ГОТОВНОСТИ БАЗЫ
=========================================================================

Это самая дорогая ошибка новичка в Compose. В нашем файле написано:

  depends_on:
    db:
      condition: service_healthy

Более короткая запись выглядит так:

  depends_on:
    - db

И означает она совсем другое: «запусти контейнер db раньше web».
Не «дождись, пока база готова», а «запусти». Между «контейнер
запущен» и «PostgreSQL принимает соединения» проходит несколько
секунд: идёт инициализация каталога данных, и приложение отвечает 500:

  psycopg.OperationalError: connection failed: connection to server
  at "172.20.0.2", port 5432 failed: Connection refused

Дальше работает политика restart: контейнер поднимается снова, когда
база уже готова, — и всё как будто заработало.

  ЛЕЧАТ ЭТО ДВА ИНСТРУМЕНТА: healthcheck — команда, которую Docker
  выполняет внутри контейнера по расписанию; у сервиса появляется
  состояние healthy, то есть вторая ступень после «просто запущен».
  У базы это pg_isready, и она отвечает нулём, только когда сервер
  принимает соединения. А depends_on с condition: service_healthy
  заставляет Compose ждать результата этой проверки — поэтому в выводе
  запуска (шаг 3) есть строки Waiting и Healthy до старта web.

ПРОВЕРИМ НА ОПЫТЕ, ЧТО ЗНАЧИТ «ГОТОВ»

  docker compose stop db
  curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080/
  500

  docker compose logs web --tail=2
  web-1  | psycopg.OperationalError: failed to resolve host 'db':
          [Errno -2] Name or service not known

  docker compose ps
  NAME          IMAGE       SERVICE   STATUS
  notes-web-1   notes-web   web       Up About a minute (unhealthy)

Статус меняется не сразу: healthcheck идёт раз в десять секунд, и трёх
неудач подряд нужно подождать. Зато видно главное: контейнер работает,
а сервис — нет, и он честно об этом сообщает. Вернём базу на место:

  docker compose start db
  curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080/
  200

ВЫВОД: depends_on — инструмент порядка запуска, а не гарантия
доступности: приложение обязано переживать недоступную базу.

  ЧЕГО НЕ ДЕЛАТЬ: не заменять depends_on паузой в команде запуска
  (command: sh -c "sleep 10 && python app.py") — пауза либо слишком
  коротка, либо слишком велика и ничего не сообщает о причине.


=========================================================================
ШАГ 7. ДАННЫЕ: ТОМ, DOWN И DOWN -V
=========================================================================

Заметка лежит в базе. Проверим, что она переживёт удаление
контейнеров. Уберём проект целиком:

  docker compose down
  Container notes-web-1  Removed
  Container notes-db-1  Removed
  Network notes_default  Removed

Тома в этом выводе нет, и это главное. Поднимем проект заново:

  docker compose up -d
  curl -s http://localhost:8080/ | grep -o 'Первая заметка'
  Первая заметка

Контейнера, который записал заметку, больше не существует — существует
том:

  docker volume ls
  DRIVER    VOLUME NAME
  local     notes_pgdata

А вот down -v удаляет и тома:

  docker compose down -v
  Volume notes_pgdata  Removed

  docker compose up -d
  curl -s http://localhost:8080/ | grep -c 'Первая заметка'
  0

Страница снова пуста: вместе с томом пропали данные базы. Docker удалил
то, что создал сам, и не тронул то, что создали вы.

  ЧЕГО НЕ ДЕЛАТЬ: не убирать проект командой down -v «на всякий
  случай» — она удаляет данные базы.


=========================================================================
ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
=========================================================================

ПРОБЛЕМА: docker: 'compose' is not a docker command

  Плагин Compose ставится пакетом docker-compose-plugin (практика 1).
  Отдельный бинарник docker-compose — это Compose v1: другой синтаксис
  файла и часть ключей не понимает. Проверьте:

    docker compose version

ПРОБЛЕМА: файл не разбирается — yaml: line 5: mapping values are not
allowed in this context

  Проверяйте по порядку:

    1. отступы: только пробелы, никогда табуляция;
    2. одинаковый отступ у ключей одного уровня;
    3. значение с двоеточием берут в кавычки — строка

         POSTGRES_DB: notes: main

       не разберётся: YAML считает «: » началом нового ключа.

  Проверить, ничего не запуская: docker compose config — ошибка разбора
  будет названа с номером строки.

ПРОБЛЕМА: error while interpolating ... required variable is missing
a value

  Полный текст:

    error while interpolating services.db.environment.POSTGRES_DB:
    required variable POSTGRES_DB is missing a value: POSTGRES_DB
    не задан, скопируйте .env.example в .env

  Переменная объявлена обязательной (запись ${ИМЯ:?текст}), но её нет
  ни в окружении, ни в .env:

    grep POSTGRES_DB .env
    env | grep POSTGRES

ПРОБЛЕМА: порт занят — Bind for 0.0.0.0:8080 failed: port is already
allocated

  Порт на машине занят — не обязательно контейнером, возможно службой:

    ss -tlnp | grep 8080
    docker ps --format '{{.Names}}\t{{.Ports}}'

  Лечится остановкой занявшего порт или сменой NOTES_PORT в .env.

ЧТО ДАЛЬШЕ
=========================================================================

Мы описали приложение целиком: два сервиса, том, healthcheck,
переменные и зависимости. Файл Compose не заменяет понимания Docker:
он делает то же самое, но из файла.

  * практика 7 — Docker Swarm: те же файлы, но на трёх машинах,
    реплики и перезапуск на живом узле;
  * практика 8 — ограничение ресурсов контейнера: память, процессор,
    OOM и код 137;
  * практика 9 — секреты: почему .env и переменные окружения — это
    не секрет и чем их заменить;
  * практика 10 — безопасность образов и поиск уязвимостей;
  * практика 11 — свой реестр образов: куда отдать собранный образ;
