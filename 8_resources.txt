Практика 8. Ограничение ресурсов контейнера.

ДО ЭТОЙ ПРАКТИКИ КОНТЕЙНЕР БЫЛ БЕЗ ПРЕДЕЛОВ: он видел всю память
и все ядра машины. Одна утечка памяти в приложении — и вместе с ним
падают база данных, демон и ssh. Здесь мы поставим контейнеру пределы
и увидим, что бывает, когда он в них упирается.


=========================================================================
ЧТО МЫ СДЕЛАЕМ
=========================================================================

Пять ограничений — по одному опыту на каждое:

  * память: --memory;
  * процессор: --cpus;
  * число процессов: --pids-limit;
  * дескрипторы файлов: --ulimit nofile;
  * ограничения в файле Compose: deploy.resources.

Главный опыт практики — убийство контейнера из-за нехватки памяти:
код возврата 137 и отметка OOMKilled рядом с ним. В практике 2 код 137
был одним из нескольких; здесь мы дойдём до его причины.

ЗАЧЕМ СТАВИТЬ ПРЕДЕЛЫ

Docker по умолчанию не ставит ни одного ограничения. Контейнер без
пределов — это обычный процесс на машине: он берёт столько, сколько
дадут. У контейнера, запущенного без ключа --memory, в docker stats
стоит вся память машины. Ограничение нужно не для экономии, а чтобы
одна программа не уронила всё остальное.


=========================================================================
ЧТО ПОНАДОБИТСЯ
=========================================================================

  * машина admin (10.0.2.5) со стендом из практики 1;
  * каталог курса: файлы практики лежат
    в ~/docker-lab/files/08_resources/;
  * образы alpine:3.24 и python:3.13-slim — их скачает Docker при
    первом запуске.

Узлы node1 и node2 не нужны: ограничения ресурсов — тема одной машины.
Сколько на стенде ядер и памяти:

  docker info --format 'ядер={{.NCPU}} памяти={{.MemTotal}}'

На стенде курса ответ — «ядер=2 памяти=8589934592». Другое число
не помешает: опыты построены на сравнении «до и после», а не
на абсолютных значениях.

=========================================================================
ШАГ 1. ПЕРВЫЙ ПРЕДЕЛ И ГДЕ ЕГО ВИДНО
=========================================================================

  cd ~/docker-lab/files/08_resources

  docker run -d --name p8-mem --memory 64m alpine:3.24 sleep 600

Ключ --memory принимает объём: 64m — это 64 мегабайта, 1g — гигабайт.
Посмотрим, что записалось в настройки контейнера:

  docker inspect p8-mem --format 'память={{.HostConfig.Memory}}'

  память=67108864

Шестьдесят четыре мегабайта в байтах: docker inspect отвечает
в байтах, а docker stats печатает мегабайты.

  docker stats --no-stream --format \
      'память={{.MemUsage}} процессов={{.PIDs}}' p8-mem

  память=1.121MiB / 64MiB процессов=1

Правая часть колонки MEM USAGE — это и есть предел. У контейнера,
которому предела не ставили, там стоит вся память машины.

ЗАЧЕМ ЭТО НУЖНО: это самый быстрый ответ на вопрос «а он точно
ограничен?». Настройка может быть записана в файле, а работать при
этом старый контейнер, созданный до правки.

  docker rm -f p8-mem


=========================================================================
ШАГ 2. ЧТО БЫВАЕТ, КОГДА ПАМЯТЬ КОНЧИЛАСЬ
=========================================================================

Главный опыт практики. Запустим контейнер с пределом 64 МБ и программу,
которая просит больше. Файл нагрузки лежит в файлах практики:
files/08_resources/stress/mem-hog.py. Программа просит память блоками
по 16 МБ и записывает по байту в начало каждой страницы. Запись
обязательна: память, которую процесс запросил, но не тронул, ядро
не выделяет, и опыт превратился бы в демонстрацию отсутствия
ограничения.

Ключ --memory-swap 64m запрещает контейнеру swap: без него ядро
вытеснит часть памяти на диск, и опыт будет каждый раз другим.

  docker run --name p8-oom --memory 64m --memory-swap 64m \
      -v "$PWD/stress:/stress:ro" \
      python:3.13-slim python3 /stress/mem-hog.py 16

Вывод обрывается на середине:

  занято 16 МБ
  занято 32 МБ
  занято 48 МБ

Строки «занято 64 МБ» нет: следующий блок перешагнул предел, и ядро
убило процесс сигналом SIGKILL. Ошибку напечатать не успели — убитому
процессу не дают времени ни на что.

Смотрим, что записал Docker:

  docker inspect p8-oom --format \
      'код={{.State.ExitCode}} oomkilled={{.State.OOMKilled}}'

  код=137 oomkilled=true

Вот откуда берётся 137. Сто тридцать семь — это 128 + 9, где 9 — номер
сигнала SIGKILL. Код 137 означает «процесс убит сигналом», а OOMKilled
говорит, каким именно: нехваткой памяти.

ЗАЧЕМ ЭТО НУЖНО: 137 бывает и при docker kill, и при остановке демона.
Сама цифра причину не называет, и разбор начинают с проверки OOMKilled.

В журнале контейнера — только эти три строки:

  docker logs p8-oom

Причина смерти в журнал не попадает: SIGKILL не перехватывается.
Демон пишет о ней отдельное событие oom — им пользуются в практике 12.

  docker rm -f p8-oom


=========================================================================
ШАГ 3. ПРОЦЕССОР: --CPUS
=========================================================================

Сначала посмотрим, сколько контейнер берёт без ограничения. Запустим
бесконечный цикл: он займёт одно ядро целиком.

  docker run -d --name p8-cpu alpine:3.24 sh -c 'while :; do :; done'

  sleep 5
  docker stats --no-stream --format 'CPU={{.CPUPerc}}' p8-cpu

  CPU=98.32%

Числа больше ста — не ошибка: одно полностью занятое ядро
показывается как 100%, поэтому два таких цикла дадут около 200%.

Теперь ограничим. Ключ --cpus задаёт, сколько ядер контейнер может
занять; дробное значение разрешено:

  docker run -d --name p8-cpu05 --cpus 0.5 alpine:3.24 \
      sh -c 'while :; do :; done'

  sleep 5
  docker stats --no-stream --format 'CPU={{.CPUPerc}}' p8-cpu05

  CPU=49.47%

Половина ядра вместо целого. Проверим, что ограничение записано:

  docker inspect p8-cpu05 --format '{{.HostConfig.NanoCpus}}'

  500000000

Процессорное время измеряется в наносекундах, поэтому половина ядра —
это пятьсот миллионов наносекунд.

  docker rm -f p8-cpu p8-cpu05


=========================================================================
ШАГ 4. ЧИСЛО ПРОЦЕССОВ: --PIDS-LIMIT
=========================================================================

Каждый процесс занимает запись в таблице процессов ядра. Программа,
которая порождает процессы и не считает их, исчерпывает эту таблицу,
и после этого на машину нельзя зайти даже по ssh. Предела по умолчанию
нет, поэтому поставим его и проверим, что он записан:

  docker run -d --name p8-pids --pids-limit 20 alpine:3.24 sleep 600

  docker inspect p8-pids --format 'PidsLimit={{.HostConfig.PidsLimit}}'

  PidsLimit=20

Теперь попробуем предел превысить. Эта команда создаёт процессы
в фоне, пока оболочка не получит отказ:

  docker run --name p8-fork --pids-limit 20 alpine:3.24 \
      sh -c 'for i in $(seq 1 50); do sleep 30 & done; wait'

  sh: can't fork: Resource temporarily unavailable

«Resource temporarily unavailable» — стандартный ответ ядра на
исчерпанный предел. Контейнер на этом останавливается:

  docker inspect p8-fork --format 'код={{.State.ExitCode}}'

  код=2

Два — код самой оболочки: она не смогла создать процесс. Нехватка
памяти здесь ни при чём, и машину контейнер не «съел»: он просто
перестал работать.

ВАЖНО: предел считает не только процессы, но и потоки. Веб-сервер
с сотней рабочих потоков упрётся в предел 64, хотя процессов у него
два-три. Поэтому значение берут по числу потоков на пике, а не
по числу запущенных программ.

  docker rm -f p8-pids p8-fork


=========================================================================
ШАГ 5. ДЕСКРИПТОРЫ ФАЙЛОВ: --ULIMIT NOFILE
=========================================================================

Дескриптор — это открытый файл, соединение или сокет. У процесса есть
предел их числа, и когда он исчерпан, приложение получает ошибку
«too many open files». Предел задаётся ключом --ulimit:

  docker run --rm --ulimit nofile=64:64 alpine:3.24 sh -c 'ulimit -n'

  64

Две цифры через двоеточие — мягкий и жёсткий предел. Мягкий действует
на процессы, жёсткий ограничивает, насколько мягкий можно поднять;
обычно их ставят одинаковыми. Так выглядит отказ:

  docker run --rm --ulimit nofile=64:64 python:3.13-slim \
      python3 -c 'f = [open("/tmp/f%d" % i, "w") for i in range(200)]'

  OSError: [Errno 24] Too many open files: '/tmp/f61'

Без ограничения тот же код открывает все двести файлов и молчит:
ошибка «Too many open files» в журнале приложения почти всегда означает
слишком маленький предел.


=========================================================================
ШАГ 6. НАБЛЮДЕНИЕ: DOCKER STATS
=========================================================================

Ограничения поставлены — теперь их нужно видеть. Инструмент один:
docker stats показывает потребление по каждому контейнеру.

  docker run -d --name p8-watch --memory 96m --cpus 0.5 alpine:3.24 \
      sh -c 'while :; do :; done'

  sleep 3
  docker stats --no-stream p8-watch

  CONTAINER ID   NAME       CPU %     MEM USAGE / LIMIT
  0a9ce49bbc2c   p8-watch   50.48%    1.383MiB / 96MiB

Правее в таблице — MEM % (потребление относительно предела), PIDS
(число процессов), обмен с сетью и диском. MEM % считается именно
от предела, а не от памяти машины.

Для разового замера удобнее --format: он печатает одну строку.

  docker stats --no-stream --format \
      '{{.Name}} cpu={{.CPUPerc}} mem={{.MemUsage}} pids={{.PIDs}}' \
      p8-watch

  p8-watch cpu=50.12% mem=1.371MiB / 96MiB pids=1

ЗАЧЕМ ЭТО НУЖНО: --no-stream нужен всегда, когда команду запускает
не человек: без него docker stats обновляет таблицу, пока его
не остановят.

  docker rm -f p8-watch

=========================================================================
ШАГ 7. ОГРАНИЧЕНИЯ В COMPOSE
=========================================================================

В файле Compose ограничения записываются в разделе deploy.resources.
Пример лежит в файлах практики: files/08_resources/compose-limits.yml.

  docker compose -f compose-limits.yml config

Команда config разбирает файл и печатает то, что поняла, — это первое,
что стоит делать при сомнениях в синтаксисе. Главное место файла:

  deploy:
    resources:
      limits:
        cpus: "0.50"
        memory: 96M
        pids: 64
      reservations:
        memory: 48M

limits — жёсткие пределы, reservations — мягкая заявка. Запустим
и проверим, что ограничения применились к контейнеру:

  docker compose -f compose-limits.yml up -d

  docker inspect p8-resources-web-1 --format \
      'память={{.HostConfig.Memory}} процессор={{.HostConfig.NanoCpus}}'

  память=100663296 процессор=500000000

Девяносто шесть мегабайт и половина ядра — ровно то, что в файле.

ЗАЧЕМ ЭТО НУЖНО: deploy.resources — единственный способ записать
ограничения, который переносится из Compose в стек Swarm без правок.
Короткие ключи mem_limit и cpus тоже работают, но только для одного
контейнера и только в Compose.

  docker compose -f compose-limits.yml down


=========================================================================
ШАГ 8. КАК ПОДОБРАТЬ ЗНАЧЕНИЯ
=========================================================================

Главное правило: сначала измерить, потом ограничить. Предел, взятый
из головы, — это отложенная авария.

  1. Дайте приложению поработать без ограничений под настоящей
     нагрузкой: синтетический тест в один поток пика не покажет.
  2. Замерьте потребление — и текущее, и пиковое:
       docker stats --no-stream \
           --format '{{.Name}} mem={{.MemUsage}} cpu={{.CPUPerc}}'
  3. Возьмите запас. Для памяти — не меньше трети к пику: приложение
     может вырасти. Для процессора запас не так важен: превышение
     предела означает ожидание, а не смерть.
  4. Проверьте, что предел выдерживает прогон, а не только запуск.
  5. Запишите значения в файл, а не в историю команд: ограничения
     должны ехать вместе с приложением.

ЧЕГО НЕ ДЕЛАТЬ: не ставьте предел по среднему потреблению. Среднее —
это то, что бывает в обычный день, а предел срабатывает в худший.
Лимит памяти ниже реальной потребности приложения — это расписание,
по которому контейнер будут убивать.


=========================================================================
ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
=========================================================================

ПРОБЛЕМА: контейнер завершился с кодом 137, а в журнале пусто

  137 — это 128 + 9, убийство сигналом SIGKILL. Записать что-либо
  перед смертью приложение не может: этот сигнал не перехватывается.
  Причин две, и различает их одна проверка:

    docker inspect <имя> --format '{{.State.OOMKilled}}'

  true — нехватка памяти, вопрос закрыт. Если false, смотрите события
  демона: там видно, был ли docker kill или остановка демона.

    docker events --since 1h --filter container=<имя>

ПРОБЛЕМА: docker: Error response from daemon: Minimum memory limit
allowed is 6MB

  Ядро не принимает лимит меньше шести мегабайт: это служебный
  минимум, ниже которого не работает и сам контейнер. Нужен меньший
  предел — ограничивайте не память контейнера, а потребление процесса
  внутри него.

ПРОБЛЕМА: sh: can't fork: Resource temporarily unavailable

  Исчерпан предел числа процессов. Смотреть:

    docker inspect <имя> --format '{{.HostConfig.PidsLimit}}'

  Если предел равен единице или двум, контейнер не запустит даже
  оболочку. Но прежде чем поднимать предел, посмотрите, кто создаёт
  процессы: приложение, которое плодит subprocess на каждый запрос,
  надо не ограничивать щедрее, а чинить.

ПРОБЛЕМА: приложение падает с «too many open files»

  Полный текст зависит от языка, но смысл один:

    OSError: [Errno 24] Too many open files: '/tmp/f61'

  Проверяйте по порядку:

    1. предел контейнера:
       docker inspect <имя> --format '{{json .HostConfig.Ulimits}}'
    2. предел внутри работающего контейнера:
       docker exec <имя> sh -c 'ulimit -n'

  Предел, заданный при запуске, у работающего контейнера не изменить:
  его поднимают перезапуском с другим --ulimit.

ПРОБЛЕМА: docker stats показывает в колонке MEM USAGE / LIMIT всю
память машины

  Значит, контейнер работает без ограничения — или ограничение
  применяется не к тому контейнеру. Вторая причина встречается чаще,
  чем кажется: предел задан в файле Compose, а работает контейнер,
  созданный до правки.

    docker inspect <имя> --format '{{.HostConfig.Memory}}'

  Ноль означает «предела нет». Пересоздать контейнер с новыми
  настройками:

    docker compose up -d --force-recreate


=========================================================================
ЧТО ДАЛЬШЕ
=========================================================================

Мы научились ставить контейнеру пределы и проверять, что они
применились. Главное из практики — три вещи. Первая: без ограничений
у контейнера нет ни одного, значение по умолчанию — «вся машина».
Вторая: превышение предела памяти означает смерть, а превышение
предела процессора — только ожидание. Третья: код 137 сам по себе
ничего не объясняет, причину показывает OOMKilled.

Дальше в курсе:

    считать секретом;
  * практика 10 — безопасность образов и сканирование на уязвимости;
  * практика 11 — свой реестр образов: TLS и аутентификация;
  * практика 12 — безопасность хоста и аудит: кто и когда запустил
    контейнер, который съел всю память.
