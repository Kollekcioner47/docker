Практика 7. Docker Swarm.

ЭТА ПРАКТИКА — ЕДИНСТВЕННАЯ В КУРСЕ, КОТОРАЯ ИДЁТ НА ТРЁХ МАШИНАХ.
Одиннадцать практик из двенадцати мы делаем на admin. Здесь мы соберём
кластер и проверим то, ради чего его собирают: что будет, если машина
перестанет отвечать.


=========================================================================
ЧТО МЫ СДЕЛАЕМ
=========================================================================

  * соберём кластер: admin — менеджер, node1 и node2 — рабочие узлы;
  * разберёмся, что такое сервис и задача и почему это не контейнер;
  * развернём стек приложения «Заметки»: файл тот же, что в практике 6,
    но раздел deploy в нём рабочий;
  * вынесем пароль базы из файла стека в секреты Swarm;
  * уведём узел в drain и увидим, куда переехали реплики.

ЗАЧЕМ ЭТО НУЖНО: оркестратор нужен там, где контейнеров больше одного
и машин больше одной. Compose этого не умеет: он описывает контейнеры
на одной машине и о второй не знает ничего.


=========================================================================
ЧТО ПОНАДОБИТСЯ
=========================================================================

ТРИ МАШИНЫ, подготовленные по практике 1: admin (10.0.2.5) — менеджер
кластера и машина, с которой работаем; node1 (10.0.2.13) и node2
(10.0.2.14) — рабочие узлы. Docker на них уже стоит, /etc/hosts
совпадает, вход по SSH с admin идёт без пароля.

ПОРТЫ, открытые между машинами:

  2377/tcp   — управление кластером: менеджер и узлы;
  7946/tcp   — обмен информацией между узлами, он же 7946/udp;
  4789/udp   — overlay-сеть: по ней идёт трафик приложений;
  80/tcp     — опубликованный наружу порт нашего стека.

Если открыть не всё, узел не присоединится к кластеру, а сервис будет
числиться работающим и не будет отвечать. ФАЙЛЫ ПРАКТИКИ лежат
в files/07_swarm/: скопируйте каталог на стенд вместе с курсом.


#########################################################################
ЧАСТЬ 1. БАЗОВАЯ ПРАКТИКА
#########################################################################


=========================================================================
ШАГ 1. ГОТОВИМ УЗЛЫ
=========================================================================

Кластер ломается не в момент создания, а на мелочах: имена в /etc/hosts
не совпадают, часы разошлись, порт закрыт. Проверим заранее — на
КАЖДОЙ из трёх машин:

  hostname
  getent hosts admin node1 node2
  docker info --format '{{.Swarm.LocalNodeState}}'

  * hostname совпадает с записью в /etc/hosts на остальных машинах:
    именно это имя попадёт в вывод docker node ls;
  * getent hosts печатает три строки с адресами. Если node1 не знает
    адреса node2, кластер соберётся не до конца;
  * LocalNodeState равно inactive — машина не состоит в кластере.
    Pending или error означают, что машину уже пытались подключить.

Открываем порты кластера — команды одинаковые на всех трёх машинах:

  sudo ufw allow from 10.0.2.0/24 to any port 2377 proto tcp
  sudo ufw allow from 10.0.2.0/24 to any port 7946
  sudo ufw allow from 10.0.2.0/24 to any port 4789 proto udp
  sudo ufw allow from 10.0.2.0/24 to any port 80 proto tcp

ЧЕГО НЕ ДЕЛАТЬ: выключать файрвол целиком, «чтобы не мешал». Если ufw
у вас выключен, команды ничего не изменят — и это нормально.


=========================================================================
ШАГ 2. СОЗДАЁМ КЛАСТЕР НА МАШИНЕ admin
=========================================================================

Кластер создаётся одной командой, и выполняется она на admin:

  docker swarm init --advertise-addr 10.0.2.5

Демон объявляет эту машину менеджером, создаёт хранилище состояния
кластера (список узлов, сервисы, сети, секреты), создаёт сети ingress
и docker_gwbridge и печатает готовую команду для подключения узлов:

  docker node ls
  docker network ls

В выводе docker node ls одна строка — admin, роль Leader, Active.

ПОЧЕМУ ИМЕННО ТАК: ФЛАГ --advertise-addr

Без него Docker выбирает адрес сам: у машины их несколько, и он может
выбрать не тот. Тогда узлы будут стучаться в никуда, а ошибки
«Timeout was reached» и «connection refused» почти всегда означают
именно неверный адрес.

МЕНЕДЖЕР У НАС ОДИН, И ЭТО КОМПРОМИСС

Менеджеры договариваются голосованием: решение принято, если за него
большинство. Отсюда правило: менеджеров делают нечётное число — три
или пять. Два менеджера хуже одного: отказ любого из них
останавливает управление. У нас менеджер один.

ВАЖНО: потеря управления не останавливает приложение — запущенные
задачи продолжают работать. Нельзя только развернуть сервис,
изменить число реплик, прочитать секрет.


=========================================================================
ШАГ 3. ПОДКЛЮЧАЕМ node1 И node2
=========================================================================

Команду для подключения узлов печатает менеджер:

  docker swarm join-token worker

Вывод — готовая строка: docker swarm join, токен, адрес менеджера
и порт 2377. Выполните её на node1, а затем на node2:

  docker swarm join --token <строка из вывода> 10.0.2.5:2377

Узел отвечает «This node joined a swarm as a worker». Возвращайтесь
на admin и смотрите список узлов:

  docker node ls

Ожидаемый вывод — три строки: admin, node1 и node2. Столбцы:

  * STATUS — Ready, Down или Unknown: Down означает, что менеджер
    перестал получать от узла сообщения о состоянии;
  * AVAILABILITY — можно ли ставить на узел задачи: Active, Pause,
    Drain. Разберём их в шаге 8;
  * MANAGER STATUS — Leader у ведущего голосование менеджера.

Токен менеджера (docker swarm join-token manager) — ключ к кластеру:
получивший его добавит свою машину в менеджеры. Если токен утёк, его
меняют командой docker swarm join-token --rotate worker. Уже
подключённые узлы ротация не выкидывает.


=========================================================================
ШАГ 4. СЕРВИС, А НЕ КОНТЕЙНЕР
=========================================================================

Контейнер — конкретная вещь на конкретной машине: машина упала,
контейнера нет. Сервис — описание желаемого состояния: какой образ,
сколько копий, где их можно запускать. Задачи (tasks) — то, чем
описание становится: по одной задаче на каждую реплику.

  docker service create --name web --replicas 3 \
      --publish 8080:80 nginx:1.30-alpine

  docker service ls
  docker service ps web

docker service ps показывает три задачи на разных узлах, но
контейнера с именем web нет: имена выглядят как web.1.k3n8x2m4p1q0.

Масштабирование — одна команда, и уберём сервис тоже одной:

  docker service scale web=5
  docker service rm web

ПОЧЕМУ ИМЕННО ТАК: сервис заработал на всех трёх машинах, хотя мы
про них не писали. Менеджер сам решает, где разместить задачу,
и пересчитывает решение при каждом изменении: узел ушёл в drain,
задача упала, реплик стало больше. Правила размещения задаются
в файле стека ключом placement — ими мы закрепим базу за узлом.


=========================================================================
ШАГ 5. ГОТОВИМ ОБРАЗЫ ПРИЛОЖЕНИЯ
=========================================================================

Swarm не собирает образы: ключа build в файле стека нет. Сборка —
работа машины, где лежат исходники, а задача может приехать на любой
узел, который про ваш каталог не знает ничего. Значит, образ должен
существовать на каждом узле, где может запуститься задача.

  cd ~/docker-lab/07_swarm
  docker build --tag notes-backend:1.0 ./backend
  docker build --tag notes-frontend:1.0 ./frontend

  docker save notes-backend:1.0 notes-frontend:1.0 -o notes-images.tar
  scp notes-images.tar engineer@node1:~/
  ssh node1 docker load --input notes-images.tar
  scp notes-images.tar engineer@node2:~/
  ssh node2 docker load --input notes-images.tar

ЗАЧЕМ ЭТО НУЖНО: в рабочей среде образы берут из реестра — свой
реестр мы поднимем в практике 11. Перенос файлом годится для стенда,
но после пересборки его нужно повторять на всех узлах.


=========================================================================
ШАГ 6. СОЗДАЁМ СЕКРЕТЫ SWARM
=========================================================================

В файле стека паролей нет — там только имена секретов. Сами значения
создаются один раз на менеджере:

  openssl rand -base64 24 | docker secret create mysql_root_password -
  openssl rand -base64 24 | docker secret create mysql_password -

  * openssl rand -base64 24 печатает 24 случайных байта: такой пароль
    никто не придумывал и не записывал в блокнот;
  * вертикальная черта передаёт его на стандартный вход, а дефис
    в конце означает «читать значение со входа». Поэтому пароль
    не появляется ни в выводе команды, ни в истории оболочки.

  docker secret ls
  docker secret inspect mysql_password --pretty

В выводе имя, дата создания и идентификатор — и всё: прочитать секрет
обратно нельзя даже на менеджере. В контейнер он приходит не
переменной, а файлом /run/secrets/mysql_password, в память и ровно
на время жизни задачи. Откройте files/07_swarm/backend/app.py:
приложение читает именно этот файл, потому что переменную окружения
видно в выводе docker inspect, а путь к файлу — нет.

ЧЕГО НЕ ДЕЛАТЬ: не передавайте значение секрета аргументом команды —
так пароль попадёт в историю команд. Подробный разбор — практика 9.


=========================================================================
ШАГ 7. РАЗВОРАЧИВАЕМ СТЕК
=========================================================================

Перед развёртыванием узел с базой должен быть помечен: без метки
задача базы останется в состоянии pending.

  docker node update --label-add role=db node1

Теперь сам стек. Команда выполняется из каталога с файлом стека:

  cd ~/docker-lab/07_swarm
  docker stack deploy -c docker-stack.yml --resolve-image never notes

Почему именно так:

  * -c — файл стека: синтаксис тот же, что у Compose, но раздел
    deploy здесь рабочий;
  * --resolve-image never — не обращаться в реестр за образами: наши
    образы собраны локально, без флага развёртывание остановится
    с ошибкой «failed to resolve image»;
  * notes — имя стека, оно станет префиксом: сервисы будут называться
    notes_db, notes_backend, notes_frontend, а сеть — notes_appnet.

  docker stack ls
  docker stack services notes
  docker stack ps notes

В столбце REPLICAS стоит «работает / должно быть»: 2/2 у frontend
и backend, 1/1 у базы.

Порт 80 опубликован на каждой ноде кластера, поэтому приложение
открывается по любому адресу, и заметка, записанная через одну ноду,
видна с другой:

  curl -s -X POST --data 'note=первая заметка' http://node2/
  curl -s http://node1/ | grep -o 'первая заметка'

Журналы сервиса читаются не docker logs, а docker service logs:

  docker service logs notes_backend --tail 30

ЧТО СДЕЛАНО В ЧАСТИ 1: кластер работает, стек развёрнут, приложение
отвечает по адресу любой ноды, пароли лежат в секретах.


#########################################################################
ЧАСТЬ 2. ПРОДОЛЖЕНИЕ: ЧТО БУДЕТ ПРИ ОТКАЗЕ МАШИНЫ
#########################################################################


=========================================================================
8. УВОДИМ УЗЕЛ В DRAIN
=========================================================================

Посмотрим, что где стоит, и уведём node1 в drain:

  docker stack ps notes
  docker node update --availability drain node1
  docker stack ps notes

  * задачи backend и frontend с node1 создаются заново на node2 —
    приложение не упало;
  * задача базы тоже останавливается, и здесь начинается главное;
  * новые задачи на node1 не ставятся, пока он в drain.

Возвращаем узел в работу:

  docker node update --availability active node1

Три значения доступности:

  active — обычное состояние: задачи ставятся, упавшие перезапускаются;
  pause  — новые задачи не ставятся, работающие продолжают работать;
  drain  — узел выведен из обслуживания: задачи снимаются и создаются
           заново на других узлах.

ЗАЧЕМ ЭТО НУЖНО: drain — ответ на вопрос «как обслужить машину
в кластере, не уронив сервис»: увести в drain, дождаться переезда
задач, сделать работу, вернуть в active.


=========================================================================
9. ПОЧЕМУ БАЗА С ТОМОМ ПРИВЯЗАНА К ОДНОМУ УЗЛУ
=========================================================================

База тоже переехала — но с пустым каталогом данных. Том db-data
локальный: Docker создал его на диске node1, а на node2 появился
новый, пустой. Приложение поднялось, страница открывается, заметок
нет. Ошибки не будет: сервис в состоянии 1/1, задача running. Отказ
тихий, и заметить его можно только по данным.

Что с этим делать:

  1. закрепить базу за узлом — то, что мы сделали меткой role=db.
     Машина с базой становится единственной точкой отказа, зато данные
     не теряются: для стенда и небольшой системы это нормально;
  2. вынести том на общий носитель — драйвер тома, который умеет
     сетевое хранилище (NFS, облачный диск). Задача переезжает
     вместе с данными;
  3. сделать базу реплицируемой (Galera, InnoDB Cluster) — это
     отдельная специальность, и в курс по Docker она не входит.

ПОЧЕМУ МЕТКА, А НЕ ИМЯ МАШИНЫ: метку узел переживёт — его можно
переименовать, заменить или сделать менеджером, не трогая файл стека.

ЧЕГО НЕ ДЕЛАТЬ: молча переносить базу в кластер, ничего не меняя
в описании сервиса, — именно так теряют данные.

Обновление стека делают так: правят docker-stack.yml и выполняют
docker stack deploy тем же именем стека — Swarm обновит только
изменившиеся сервисы.


=========================================================================
ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
=========================================================================

ПРОБЛЕМА: узел не подключается к кластеру

  Error response from daemon: rpc error: code = Unavailable
  desc = connection error: dial tcp 10.0.2.5:2377: i/o timeout

Проверяйте по порядку:

  1. машина отвечает вообще: ping -c 2 10.0.2.5
  2. порт управления открыт: nc -vz 10.0.2.5 2377
  3. адрес в команде совпадает с тем, что напечатал менеджер:
     docker info --format '{{.Swarm.NodeAddr}}'
  4. на менеджере Docker запущен: systemctl is-active docker

Причина почти всегда одна из двух: закрытый порт или неверный адрес,
который менеджер объявил узлам. Второе — следствие запуска
docker swarm init без флага --advertise-addr. Отдельный случай — узел
уже состоит в кластере: «This node is already part of a swarm. Use
"docker swarm leave" to leave this swarm and join another one». Тогда
выводим его командой docker swarm leave --force и повторяем join.

ПРОБЛЕМА: docker node ls пусто, хотя кластер создавали

Список узлов видит только менеджер: на node1 или node2 вы получите
ответ «This node is not a swarm manager» — это не поломка, а
устройство. Проверьте hostname и повторите команду на admin. Если
машина вообще не состоит в кластере, её состояние покажет:

  docker info --format '{{.Swarm.LocalNodeState}}'

Inactive означает, что узел не подключён — вернитесь к шагу 3.

ПРОБЛЕМА: сервис не запускается, задачи висят в состоянии pending

  docker service ps --no-trunc notes_db

  no suitable node (node label "role" not found on any node)
  no suitable node (insufficient resources on 2 nodes)

Проверяйте: есть ли узел с нужной меткой (docker node inspect node1
--format '{{json .Spec.Labels}}'), не все ли узлы ушли в drain
(docker node ls), хватает ли памяти под резервы из deploy.resources.
Резерв планировщик обязан обеспечить, и «немного не хватает» здесь
означает отказ. Подробнее — практика 8.

ПРОБЛЕМА: развёртывание стека не находит образ

  failed to resolve image / No such image

docker stack deploy по умолчанию идёт в реестр за дайджестом образа,
а наши образы собраны локально. Проверяйте: флаг --resolve-image
never, образ есть на менеджере (docker image ls) и на узлах
(ssh node1 docker image ls). Последнее — самая частая причина:
собрали на admin, а узлам не раздали.

ПРОБЛЕМА: backend перезапускается по кругу, в журнале Access denied

  docker service logs notes_backend --tail 30
  pymysql.err.OperationalError: (1045, "Access denied for user
  'notes'@'10.0.2.13' (using password:
  YES)")

Проверьте, что секрет существует и подключён к сервису: docker secret
ls и docker service inspect notes_backend --pretty. Но самая коварная
причина в другом: образ MySQL применяет пользователя и пароль только
при первой инициализации, когда каталог данных пуст. Если поменять
секрет, а том оставить прежним, в базе останется старый пароль:
секрет и состояние базы меняются вместе.


=========================================================================
ЧТО ДАЛЬШЕ
=========================================================================

Следующие практики идут на одной машине, и кластер будет мешать.
Убираем за собой — сначала стек, потом секреты:

  docker stack rm notes
  docker secret rm mysql_password mysql_root_password
  ssh node1 docker swarm leave
  ssh node2 docker swarm leave
  docker swarm leave --force

Тома при удалении стека остаются: удаление не должно уносить данные.
Убираем их отдельно:

  docker volume ls
  docker volume rm notes_db-data

Дальше в курсе:

  * практика 8 — ограничение ресурсов: память, процессор, лимиты
    и резервы, которые мы уже видели в файле стека;
  * практика 9 — секреты: почему переменная окружения секретом
    не является;
  * практика 10 — безопасность образов и поиск уязвимостей;
  * практика 11 — свой реестр образов: им заменяется перенос
    образов файлом;
  * практика 12 — безопасность машины и аудит.
